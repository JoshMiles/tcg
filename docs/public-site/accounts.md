# Login, sessions and viewer settings

> Read this when you touch Twitch login, sessions, /account basics, notifications page, /settings, feedback form, pronouns.

## Login, sessions and settings

- **daisyUI on account and settings:** settings sections, the feedback form and list, and notification day lists are daisyUI `card` (the navy surface is part of `card`). Settings rows, push kinds are `toggle`. Bio, feedback, the delete confirmation, searches and the accent hex field use `input` / `textarea`; collection view, watch version and pronouns use `select` and `fieldset`. `/account` stays on cheese `.rind`. Filter chips, looking-for chips, accent swatches, the colour box, the sticky save bar and the red delete section stay as they are. Saving, export, deletion and notice behaviour are unchanged.

- **Website login ("Log in with Twitch")**: OAuth authorization-code flow with **no scopes** (reads only the public profile: ID, login, display name, picture). `GET /auth/twitch` stores a random `state` (+ safe `returnTo`) in the short-lived `tcg_oauth` cookie and redirects to Twitch; `GET /auth/twitch/callback` checks the state, trades the code for a token (`lib/twitch-oauth.ts`), reads the profile, **revokes the token immediately (never stored)**, runs `bindAccount` (`lib/account-bind.ts`; creates the same record the Extension does, so web and panel share one identity), and sets the `tcg_session` cookie. `POST /auth/logout` clears it. Failures land on `/auth/error?reason=…`.
- **Account IDs at sign-in (`bindAccount`, shared with `POST /api/twitch/login`)**: profiles are keyed by Twitch login, which can later be taken by a different person, so sign-in compares the Twitch account ID with the one on the profile (`classifySignIn` in `lib/account-id.ts`; only a numeric ID counts, free text in `twitchId` counts as none). What a sign-in does, in order: (1) finish a move of this login that was left half done (`finishMove`); (2) **a different ID on the login (conflict)**: the old profile is moved aside to `<login>~<n>` (`moveAside`, reason "A different Twitch account signed in as <login>") and the new account starts fresh under the login; only if that move fails is the conflict recorded in `acct:conflicts` (login, when, count; Admin → Settings → Data health lists them) and the old profile left alone, and the session check below keeps the newcomer out of it; (3) **this ID already owns a profile under another login** (`acct:ids`): if that profile is a normal login whose profile holds this ID (a Twitch rename) and the new login holds no cards, it is moved onto the new login (`moveAccount` in `rename` mode, `replaceBlank`, reason "Twitch name changed"); if the new login already has cards nothing moves; a `~` owner (an account moved aside) is never moved by sign-in, only its owner can restore it from `/account`; (4) make sure the login has a profile holding the ID: new profile created with it, a profile with no ID claimed (the ID written), and `acct:ids` written once with `hsetnx`. A KV failure anywhere is logged and never blocks sign-in. Sandbox sign-ins (fake IDs) keep the old plain behaviour and record nothing. `POST /api/twitch/login` calls `bindAccount` before it saves the opaque panel link, because a move removes the links to the login it moves.
- **Session check (`getSession`)**: a cookie whose `twitchId` is a valid ID is ignored (the viewer counts as signed out) when the stored profile's `twitchId` is a valid ID and differs, i.e. the login was moved aside or taken over since the cookie was issued; the cookie is not cleared (a server component cannot) and the next sign-in replaces it. One profile read per request (React `cache`). Sandbox sessions, sessions or profiles without a usable ID, and `verifySession` itself (pure) are not affected.
- **"We found your earlier collection" (`/account`, `EarlierCollection`, `lib/account-restore.ts`)**: shown when `acct:ids[<my ID>]` is another login that either is a `~` login whose `acct:aside` record holds my ID and is not `declined`, or is a normal login whose profile holds my ID. It names the original login and the number of cards. With no cards on this login: **Restore it here** (server action; re-checks, then `moveAccount(owner, me, { mode: 'rename', replaceBlank: true, reason: 'Restored by its owner' })`, and `/account?restored=ok|failed` shows the result) and **Keep it separate** (sets `declined: true` on the aside record for a `~` owner and repoints `acct:ids[<my ID>]` at this login, so the notice goes away). With cards on this login: no restore button, the copy says the staff can merge the two, plus **Keep it separate**.
- **Sessions (`lib/session.ts`)**: a signed cookie (HMAC-SHA256 with `SESSION_SECRET`, no database): `{ username, twitchId, displayName, exp }`, 30 days, httpOnly, SameSite=Lax, Secure in production. It is readable but not forgeable. `getSession()` in server components; state-changing endpoints also call `isSameOrigin()`. `SESSION_SECRET` is a random string you invent (NOT the Twitch client secret); changing it logs everyone out.
- **What logged-in viewers get**: nav avatar menu; `/account` (My Stats: rank, score, completion by rarity, most valuable copies, what they can upgrade now, with Upgrade buttons, `lib/user-stats.ts`); on **their own** `/collection/[username]` the card detail gains Upgrade buttons. Upgrades go through `POST /api/account/upgrade` → `upgradeCard()` (same logic as the Extension); the username always comes from the session, never the request body.
- Twitch dev console: add `https://cheesytcg.app/auth/twitch/callback` (i.e. `${SITE_URL}/auth/twitch/callback`) as an OAuth Redirect URL on the Twitch *application* (the one whose Client ID/Secret are in the env vars).
- **Notifications page (`/notifications`, signed-in only, noindex)**: the kept notices (`listNotices`, 30 newest) grouped by day (`lib/notice-list-core.ts`, viewer time zone) with kind filters (All, Unread, Offers, Results, Alerts, Admin), Mark all read (`POST /api/notifications`) and a "See all notifications" link in the bell footer. `scripts/check-notice-list.mts`.
- **Viewer settings (`/settings`, signed-in only, noindex)**: `lib/user-settings.ts` (pure: `UserSettings`, `DEFAULT_SETTINGS`, `sanitizeUserSettings`, `EXPERIMENTS` registry, `wantsNotice`) and `lib/user-settings-store.ts` (KV `user:<u>:settings`, stored sparsely; the set `users:hidden:self`). Saved through `POST /api/account/settings` (viewer from the session, body re-sanitised); `GET /api/account/export` downloads everything held about the viewer (`lib/user-export.ts`). Settings: `bio` (160 chars, on the profile header), `privateProfile` (joins `users:hidden:self`; **it also hides the profile page itself**: `/u/<name>` shows everyone but the owner a "This profile is private" message, with a generic title, `noindex` and a link preview that carries no name or stats (`canSee` in `app/u/[username]/page.tsx`, `opengraph-image.tsx`); `GET /api/trades/holdings` follows the same rule (the owner and staff still can, and a signed-in viewer can read a public profile); the admin-set hide does not; **`getHiddenUsers()` and the leaderboard's reader union it with the admin-set `users:hidden`, but `setHidden` only ever writes the admin list**), `notifyOffers` / `notifyResults` (`notify()` in `lib/trade-notify.ts` drops a switched-off kind; admin notices always arrive), `allowOffers` (`createInLock` refuses direct offers to someone who opted out; the board and counters are unaffected), `motion` (`data-motion="reduce"` on the shell wrapper mirrors prefers-reduced-motion), `hideUncollected` / `compactGrids` (passed to `CollectionGrid`; a choice made on the grid itself, remembered in `localStorage`, still wins) and `experiments`. **Experiments** are opt-in ids in `EXPERIMENTS`; the one so far is `shortcuts` (`PublicKeyboard`, `lib/public-shortcuts.ts`: `g` then h/c/l/s/d/t/a/e, `?` lists them). Add one by adding it to the registry and consuming `hasExperiment(prefs, id)` in `SiteShell`. Add a new setting in `UserSettings` + `DEFAULT_SETTINGS` + `sanitizeUserSettings` (+ `BOOLEAN_KEYS`) and a row in `SettingsForm`. `scripts/check-user-settings.mts` (mock KV) covers validation, notice gating, private profiles and export.

- **Feedback**: `/feedback` (noindex, signed in only, `FeedbackForm`) is suggestions only (title, details). **Problem reports are GitHub issues** on the public repo: `reportProblemUrl(from?)` in `lib/site.ts` builds a link to the bug report issue form with the page URL prefilled in its steps field; `featureRequestUrl()` links the feature request form and is offered next to the idea text on the feedback page and in the FAQ, used by the footer, the beta banner, the error page ("Report this"), the FAQ and the feedback page; there is no daily limit, a GitHub account is needed and the issue is public. `/feedback?kind=bug` (or `?from=` without a kind) redirects there, so old links keep working. The API still accepts `kind: 'bug'` and the admin inbox still shows older ones. `POST /api/feedback` uses the session, the Turnstile gate like trades and 5 sends per viewer per UTC day. The page also lists the viewer's own items with status and reply, and the data export includes them. Entry points: footer, bell menu and the FAQ. See docs/admin.md for the staff side.
- **Pronouns (ROADMAP 8.6)**: `UserSettings.pronouns` is `{ mode: 'none' | 'set' | 'alejo', value? }` (`lib/pronouns.ts`, pure). Off for everyone until they choose; `set` is one pick from a fixed list (`PRONOUN_CHOICES`, no free text); `alejo` shows what they set on pr.alejo.io. It is shown after the name in the profile header (resolved on the server by `pronounsFor` in `lib/pronouns-store.ts`, passed to `ProfileHeader`) and edited in Settings and in the profile's Edit profile (`PronounPicker`). The pr.alejo.io lookup (`GET https://api.pronouns.alejo.io/v1/users/<login>` gives `{ channel_login, pronoun_id, alt_pronoun_id }`, a 404 when none are set; `GET /v1/pronouns` is an object keyed by id with `{ name, subject, object, singular }`) is only made for a collector who chose that mode, cached in KV (`pronouns:<login>` and `pronouns:table`: a day for answers and misses, ten minutes for a failure), gives up after 2 seconds and never throws. `PRONOUNS_API_URL` points it at a fake outside production. Not on the leaderboard and not in the Twitch panel (freeze). Privacy Policy and FAQ say so; `scripts/check-pronouns.mts` covers it.
