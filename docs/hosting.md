# Hosting, environment, backups and data health

> Read this when you touch deployment, environment variables, the build stamp, nightly backups, data health, rate limits or measuring site speed.

## Environment variables
| Variable | Purpose |
|----------|---------|
| `ADMIN_SECRET` | No longer signs the emergency cookie. It used to be that cookie's HMAC key and the secret on `GET /api/admin/import-legacy`. Rotate it if that URL was ever requested, then remove it. A leaked value cannot mint a cookie |
| `ADMIN_COOKIE_SECRET` | Signs the emergency password cookie (16+ characters, not `ADMIN_SECRET` and not `SESSION_SECRET`). Without it the password login cannot start a session. Set it on Production, and a different value on Preview if the password is used there. Twitch staff sign-in does not need it. Wrong passwords are limited to 10 per address every 15 minutes and 20 across the whole site per clock hour (see `docs/staff.md`) |
| `ADMIN_PASSWORD` | Password checked by `/api/auth/login` (the emergency login) |
| `ADMIN_PASSWORD_LOGIN` | Optional. `off` switches the emergency password login off: `/api/auth/login` answers 403, the `/login` page hides the password form and the password cookie stops working |
| `SUPER_ADMIN_TWITCH_IDS` | Optional. Extra super admins (comma-separated numeric Twitch IDs); joshmiles is hard-coded |
| `KV_URL`, `KV_REST_API_URL`, `KV_REST_API_TOKEN`, `KV_REST_API_READ_ONLY_TOKEN` | Vercel KV credentials |
| `BLOB_READ_WRITE_TOKEN` | Vercel Blob credentials |
| `BACKUP_ENCRYPTION_KEY` | 16+ character password the nightly backups are encrypted with; without it no backup is written. Keep a copy: backups cannot be read without it |
| `CRON_SECRET` | 16+ character random string; Vercel sends it to `/api/cron/backup`, `/api/cron/weekly` and `/api/cron/minute`, which refuse any other caller |
| `TWITCH_EXTENSION_SECRET` | Base64 Extension Secret for JWT verification |
| `TWITCH_CLIENT_ID` | Twitch OAuth app Client ID (for Helix API) |
| `TWITCH_CLIENT_SECRET` | Twitch OAuth app Client Secret (for Helix API and website login) |
| `SESSION_SECRET` | Random string (16+ chars, ideally 48+) used to sign website login cookies. Each signed value (viewer session, staff cookie, access cookie, sandbox entry, fake Twitch token) gets its own key derived from it with a purpose label (`lib/signing.ts`); secrets and signatures are compared with `safeEqual` or `timingSafeEqual`. Generate your own, e.g. `openssl rand -base64 48`; not a Twitch value. Website login is hidden/unavailable without it |
| `SITE_URL` | Optional. Public base URL (default `https://cheesytcg.app`); the OAuth redirect URI is built from it, so set it if the domain changes |
| `GITHUB_CHANGELOG_TOKEN` | Recommended. Fine-grained GitHub token for this repo only, Pull requests: read-only; add to Production and Preview. The build reads merged PRs with it to make the What's new page (`scripts/build-changelog.mjs`). Without it the generated part is empty and the build still succeeds |
| `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_BOT_TOKEN` | Recommended. Discord direct message alerts (needs a Discord bot invited to the Cheesygidds server): OAuth client credentials (scope `identify`) and the bot token. All three must be set or the Discord direct messages option is hidden; add `<site>/auth/discord/callback` as a redirect in the Discord developer portal. Listed under Discord on Admin, Settings, Environment |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` | Recommended. Web Push alerts: generate the pair with `npx web-push generate-vapid-keys`, subject is `mailto:` the legal contact address. Without them the alerts option is hidden |
| `LEGAL_OPERATOR_NAME`, `LEGAL_CONTACT_EMAIL`, `LEGAL_GOVERNING_LAW` | Optional. Name the operator, a privacy contact email, and governing law on `/privacy` and `/terms`; neutral wording is used when unset. **Set these before submitting the extension for review** |

## Build version
Every build is stamped so you can tell which deployment you are looking at. `next.config.ts` bakes `BUILD_VERSION` (`deriveVersion()` in `lib/version.ts`, see below), `BUILD_COMMIT`/`BRANCH`/`ENV`/`REPO` (from Vercel's `VERCEL_GIT_*` and `VERCEL_ENV`, falling back to `git` locally) and `BUILD_TIME` into the bundle; `lib/version.ts` (`getBuildInfo()`) reads them. It shows as `v1.437 · 179a138` in the admin sidebar (`BuildBadge`, links to the commit on GitHub, with a `DEV`/`PREVIEW` pill outside production), in a **Build** section on `/admin/settings`, and in the top-right corner of the Twitch panel (fetched from the public `GET /api/version`).

**Version number.** `<major>.<PR number>`: the major is the first part of `package.json`'s `version` (bump it by hand for a big release), the PR number is the `(#N)` at the end of the commit subject (every merge to `main` is a squash merge; `VERCEL_GIT_COMMIT_MESSAGE` on Vercel, `git log -1 --format=%s` locally). A preview build of a PR uses `VERCEL_GIT_PULL_REQUEST_ID` with a `-pr` suffix (`1.438-pr`). With neither, it falls back to the full `package.json` version. No GitHub API call, so it cannot fail a build. It is the PR number, not a count, so closed PRs leave gaps, but it only goes up. `GET /api/version` keeps its fields; only the format of `version` changed.

**Update prompt.** `UpdatePrompt` (`app/components/UpdatePrompt.tsx`, in `SiteShell` and the admin layout) gets the commit baked into the page and compares it with `GET /api/version` when the tab becomes visible and every 10 minutes while it stays visible (never while hidden). When they differ it shows "A new version is available" with **Refresh** (a plain `location.reload()`, so a page's own unsaved-changes guard still asks first) and a close button that hides it until the next new commit. It never reloads by itself, and is off in development (`BUILD_ENV`). Not in the overlay or the Twitch panel. `scripts/check-version.mts` covers the version parsing.

## Backups (nightly)
The project's **first scheduled job**: Vercel Cron (`vercel.json`, 04:00 UTC) calls `GET /api/cron/backup`, which checks `Authorization: Bearer ${CRON_SECRET}` (closed when unset) and runs `runBackup()` (`lib/backup.ts`). It refuses outside production (`VERCEL_ENV`) and inside a sandbox. It SCANs the raw production keyspace, skips everything on the deny-list in `lib/backup-core.ts` (`DENY_PREFIXES`: `sbx:`, `sandbox:`, `stats:`, `twitch:`, `activity:`, locks, cooldowns, queues, `watch:idx:`, per-viewer restore points; **a new key is backed up by default**, add a prefix there only for something rebuildable), reads each key by type (string / hash / list / set, 25 at a time) and writes **one encrypted file** `backups/<YYYY-MM-DD>.json.gz.enc` to Blob (a second run the same day replaces it; the newest 14 are kept, anything not named like a backup is never deleted). **Encrypted on purpose**: the Blob version in use (0.27) only stores public files and a backup holds Twitch IDs and webhook secrets, so the file is AES-256-GCM with a key derived from `BACKUP_ENCRYPTION_KEY` (scrypt, fresh salt; format in `encryptBackup`) and no backup is written without that variable. Keep a copy of the key somewhere safe: without it a backup cannot be read. `scripts/restore-backup.mts <file>` decrypts and, by default, restores into a **sandbox namespace** (`--sandbox <id>`, registered so it opens in Admin → Sandbox); `--raw --i-mean-production` puts keys back where they were (replacing each key, not merging). Admin → Settings → Environment has a **Backups** panel (newest backup, size, red when older than 36 hours, **Back up now**, production only). Pure parts and the format are tested in `scripts/check-backup.mts`; the mock KV tracks key types and supports `type` / `rpush` for it.

**Minute job** (`vercel.json`, every minute): `GET /api/cron/minute`, same `CRON_SECRET` check (`lib/cron-auth.ts`), production only, never in a sandbox. Steps (a failing one never stops the next): `getLiveStatus()` (so went-live / went-offline System notices and the stream recap fire with nobody on the site) and `sweepTrades()` (expired offers refunded).

**Weekly job** (`vercel.json`, Sundays 20:00 UTC): `GET /api/cron/weekly` (`app/api/cron/weekly/route.ts`), same `CRON_SECRET` check, does nothing outside production or in a sandbox. Each step runs once per ISO week and a failing step does not stop the next. Today's only step is the edition of the week (`pickOncePerWeek`, docs/serials.md); ROADMAP 6.3's digest goes at the marked hook in the route. To re-run a week by hand delete `potw:week:<yyyy-Www>`, or use **Pick again now** on Admin -> Prints.

## Data health
`lib/data-health.ts` measures how big the stored data is, so a storage redesign (roadmap 3.2: per-viewer storage) is decided by numbers. A season's collection is ONE JSON value (`tcg_<name>`) read and rewritten whole under a lock on every pull, trade and upgrade; `trades:open` and `trades:history` are single values too. Pure: `jsonBytes`, `formatBytes`, `healthLevel` (ok below `BLOB_WARN_BYTES` = 512 KB, warn from there, high from `BLOB_HIGH_BYTES` = 2 MB), `summarizeCollection`, `sizeAttention`. Server: `loadDataHealth()` per published season (collection bytes, viewers, entries, largest holder; the serial ledger's `idx` / `ret` / `n` hash sizes and the per-viewer ledger hashes for up to 500 viewers; drafts skipped), trade blob sizes, closed offers still marked escrowed (`stuckEscrow`: a refund that failed partway, or a flag left set after the prints moved, see docs/trading.md; shown as a red alert with **Return prints**) and the activity log length. Shown as the **Data health** panel on Admin → Settings → Environment (`DataHealthPanel`) and as a dashboard **Needs attention** line (`data-size`) when the dashboard's season collection passes 512 KB (`computeAttention` gets `jsonBytes(collection)`, so it costs no extra read). The measurement writes nothing. Return prints is the one action on that panel. `scripts/check-data-health.mts` (mock KV) covers it.

## Hosting & deploys
- **Vercel** project `tcg` (team `joshmiles-projects`, Next.js, Node 24.x), connected to the GitHub repo `JoshMiles/tcg`. Pushing a branch builds a **Preview** deployment; merging to `main` deploys **Production** at `https://cheesytcg.app` (moved from `tcg-khaki.vercel.app`; on a domain change update `SITE_URL`, the Twitch OAuth redirect URL and the extension URLs / allowlist, and the overlay URL in OBS) (also aliased `tcg-git-main-joshmiles-projects.vercel.app`). That URL is hardcoded in the Twitch panel setup, the settings page and the overlay URL pasted into OBS. Don't rename the project/domain without updating them. **Vercel SSO protection is on for deployments**, so a Preview URL asks for a Vercel login: it works in your own browser but not as an OBS browser source or from the Twitch panel, test the overlay/panel locally or on production. `vercel.json` holds the crons and `"regions": ["lhr1"]`: functions run in London, next to the KV store (Upstash `eu-west-2`), because a page makes several KV round trips and each one crossed the Atlantic from the default `iad1`. Move both together or neither. There is no `.vercel` link in the repo and nothing here needs the Vercel CLI.
- **Storage** is Vercel KV (Upstash Redis `tcg-kv`, London `eu-west-2`, Free tier: 500K commands a month, Storage tab → one store feeding `KV_URL`, `REDIS_URL`, `KV_REST_API_URL`, `KV_REST_API_TOKEN`, `KV_REST_API_READ_ONLY_TOKEN`) and Vercel Blob. Env vars live in Vercel → Project → Settings → Environment Variables and are **scoped per environment**. State when last checked (2026-10): the KV vars are on Production + Preview + Development; `ADMIN_SECRET`, `ADMIN_PASSWORD`, `TWITCH_CLIENT_ID/SECRET` and `TWITCH_EXTENSION_SECRET` are Production + Preview only (stored as sensitive); a Vercel Blob store was attached on 2026-10-10 (`BLOB_READ_WRITE_TOKEN`, `BLOB_STORE_ID`, `BLOB_WEBHOOK_PUBLIC_KEY`, Production + Preview only, no Development, so local dev has no Blob and the Assets page says "not connected" there; image uploads need a real deployment). Before that, uploads and the Assets Blob inventory reported "Blob storage isn't connected" because the variable didn't exist. The KV vars show Vercel's "Needs Attention" because the integration stores them as readable rather than sensitive; that's cosmetic. **Env var changes only apply to new deployments, redeploy after editing them.** Never paste secret values into chat, commits or docs.
- **Previews are walled off inside the production store** (see "Preview deployments" under Sandbox): a preview deployment reads and writes only its own `sbx:preview:*` namespace and starts empty; Admin → Settings → Environment has a Preview data panel to copy the live setup in or wipe it. It still holds the production KV credentials, so `lib/db.ts` (and the `check-kv-imports` guard) is what keeps it safe. The Blob store is shared: uploads on a preview are real files (they show under Unused).
- Build: `next build` (Node, Next 16, bundled by Turbopack; the Vercel project runs Node 24.x). `next.config.ts` stamps the build version/commit and sets cache headers for card art. Tailwind is 4 (`@tailwindcss/postcss`, theme in `app/globals.css`) with daisyUI 5's `cheesy` theme. `@vercel/blob` is on 2.x (moved from 0.27 in October 2026, which also cleared the `undici` / `@fastify/busboy` advisories; the code needed no changes). Upload, optimise, replace and cleanup only run against a real Blob store, so after any further major bump test them on a Preview deployment first.
- **Rendering: Cache Components** (`cacheComponents` + `partialPrefetching` in `next.config.ts`). Each page is prerendered at build time as far as it can go without the request: the public site's frame (nav layout, footer, page skeleton) is one static shell, the same for every visitor, served from Vercel's CDN, and everything that reads cookies, headers, the session or KV streams into it behind `<Suspense>`. Nothing is cached across requests with `'use cache'` yet. Admin, mod and a few other routes set `export const instant = false` and render fully per request. Code that reads the clock or random numbers during render must come after a request read (`await connection()`), or the build fails. **Soft 404s:** once a page has streamed, `notFound()` and `redirect()` inside the streamed part can't change the status, so a missing card or trade answers 200 with a `noindex` meta and the not-found UI, and a redirect happens in the browser; this is Next's documented behaviour. With no KV variables (CI) the `kv` proxy in `lib/db.ts` reads the request before it throws, so those prerenders stop as dynamic instead of failing the build.
- Static files in `public/` (overlay, widget, Twitch panel, card art, sounds) are served as-is by Vercel, no build step. The overlay/widget are cached by OBS, after a deploy, right-click the browser source → **Refresh cache of current page**.
- **Twitch Extension** is configured at dev.twitch.tv (see "Twitch Extension Panel"); it loads the panel from the production URL, so panel changes only reach viewers after a production deploy, and Twitch's iframe can cache the old JS for a short while.

## Security headers and the CSP trial
`lib/security-headers.ts` holds the rules; `next.config.ts` spreads them into `headers()`, and `scripts/check-security-headers.mts` asserts which header goes on which path.
- **Every path:** `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera, microphone, geolocation, payment, usb off), `Strict-Transport-Security: max-age=63072000` (no `includeSubDomains` or `preload`, which would commit other subdomains).
- **Framing:** `X-Frame-Options: SAMEORIGIN` on everything except `/overlay*`, `/widget*` and `/twitch-panel/*`. SAMEORIGIN, not DENY, because the admin overlay previews frame our own `/overlay.html`; the overlay and the panel stay open to OBS and Twitch's iframe. Add a new embeddable path to `EMBEDDED_PATHS`, not a per-path header.
- **CSP trial (security audit X-1):** the website's pages (not `/api`, the overlay or the panel) send `Content-Security-Policy-Report-Only`, so nothing is blocked. Violations are posted to `/api/csp-report` (`app/api/csp-report/route.ts`), which writes one `csp-violation` log line each (directive, blocked URI, page, source file), drops bodies over 8 KB and logs at most 60 a minute per server instance. Nothing is stored in KV.
- **Reading the reports:** Vercel -> the `tcg` project -> Logs (Production), search `csp-violation`. A real page that violates the policy shows its own URL in `page`; ignore `blocked` values of `eval`, `inline` or `chrome-extension://` from one-off visitors (browser extensions cause most noise). A week with no violations from real pages means the policy is ready.
- **Switching to enforcing:** in `securityHeaderRules()` change the key `Content-Security-Policy-Report-Only` to `Content-Security-Policy`, update the two assertions in the check that insist it stays report-only, and deploy to a Preview first. `script-src` still has `'unsafe-inline'` (Next.js hydration scripts); dropping it needs nonces. A violation seen in the logs means adding that host to the matching directive in `cspPolicy()`.

## Rate limits
One limiter, `lib/rate-limit.ts`: `rateLimit(name, key, max, windowS)` counts each call with an `INCR` on `rl:<name>:<key>` and starts the window with `EXPIRE` on the first call (a fixed window; one KV command per call, two on the first of a window), and says whether the call is allowed. Counts live in the production namespace (`prodKv`; on a preview deployment, its own), so a sandbox cookie or header never starts a fresh count. The caller is `clientIp` (`x-real-ip`, else the right-most `x-forwarded-for` entry). The route guards fail open: if the counter itself errors, the call goes through. A limited call answers **429** with `{ "error": "..." }` and a `Retry-After` header; the panel's existing JSON keys are untouched.

| Where | Name and key | Limit | Why this number |
|-------|--------------|-------|-----------------|
| `POST /api/auth/login` (wrong passwords only) | `login-fails` per address, `login-fails-hour` for the site | 10 per 15 minutes per address, 20 per clock hour in all (`lib/login-limit.ts`, see docs/staff.md) | Unchanged by the shared limiter |
| `/api/webhooks/*` (incoming Mix It Up calls and the overlay's notify call; the queue poll counts only callers without the overlay key) | `webhooks` per address | 600 per minute | The overlay asks for events every 2 seconds (30 a minute) and a busy stream sends a few triggers a second at most |
| `/api/twitch/*` (the panel) | `twitch` per address | 300 per minute | A panel makes a handful of calls when opened and one per button press |

The guard is the first line of each handler, except the queue poll, where it runs only after a failed overlay-key check (`limitWebhook` / `limitTwitch`; for the secret-checked webhooks it sits inside `parseIncomingWebhook`), so a refused call costs one KV command and never reads the body. A new webhook or panel route must call it too. Change a limit in `lib/rate-limit.ts` and in this table together; `scripts/check-rate-limit.mts` covers the helper, the login numbers and both route families.

### Vercel Firewall trial (log only, one week)
The limits above are in code. The Vercel Firewall can watch the same paths in front of the functions, but it is only worth keeping if it never flags real traffic, so first run it in log-only mode. This cannot be done from code: set it up in the dashboard (Project `tcg` → Firewall → Configure → Custom Rules → Add New Rule, rule type Rate Limit). Make three rules, each keyed on IP address, fixed window 60 seconds, action **Log** (not Deny, not Challenge):

| Rule name | If the request path | Requests per 60 s |
|-----------|---------------------|-------------------|
| `trial-login` | equals `/api/auth/login` | 30 |
| `trial-webhooks` | starts with `/api/webhooks/` | 1200 |
| `trial-panel` | starts with `/api/twitch/` | 600 |

Each number is double what the app allows itself, so the in-app limiter still acts first and the firewall only logs. Publish the changes, then leave them for one week that includes at least a few streams. Check Firewall → Traffic, filtered by each rule name, after the first stream and at the end of the week.

- **Success:** no real overlay, panel or webhook traffic is flagged. The overlay's 2-second poll, Mix It Up triggers and a panel opening on a busy stream stay under every rule, and only the login rule ever fires, from someone guessing at it.
- **If real traffic is flagged:** raise that rule's number, or drop the rule, and run another week. Do not switch any rule to Deny while real traffic shows up in the log.
- **After a clean week:** either delete the three rules (the in-app limiter is enough) or switch them to Deny with the same numbers. Delete the trial rules you do not keep.

## Measuring site speed
- **Field numbers** come from Speed Insights through the Vercel MCP: `create_observability_query` on `vercel.speed_insights.*`, grouped by route and device. Only busy routes (home) collect enough samples over 30 days to read.
- **Lab numbers** come from Lighthouse against `next build` / `next start` on the seeded mock KV, with ad blockers off: `npx -y lighthouse@12.8.2 <url> --throttling-method=devtools`. The default simulated mode overstates LCP on localhost. `next start` serves HTTP/1.1, so the lab also overstates how long the CSS file waits behind the JS (Vercel serves HTTP/2).
- **Bundles:** `next build` no longer prints route sizes or First Load JS. `npm run analyze` (`next build --webpack`, because `@next/bundle-analyzer` is a webpack plugin; the normal build is Turbopack) writes a treemap of every JS bundle to `.next/analyze/client.html`; Lighthouse gives per-page numbers.
- **CSS:** the main stylesheet is about 300 kB raw (47 kB gzipped, about 120 kB of it daisyUI components, nearly all used); Tailwind scans only `app/` and `lib/`. `experimental.inlineCss` was tried and set aside: it is experimental, puts the whole sheet in every page's HTML twice (about 96 kB more per full load, never cached), and most of its lab gain came from HTTP/1.1. Check home's first paint in Speed Insights before trying critical CSS.

## GitHub and Vercel changes in Discord
No server code: GitHub posts these itself, and Vercel reports every deployment to GitHub as a deployment status, so one GitHub webhook covers both. The same steps show in Settings → Webhooks → "Deploys & code".
1. In Discord make a webhook for the channel (Channel settings → Integrations → Webhooks → New Webhook → Copy Webhook URL).
2. In the GitHub repository: Settings → Webhooks → Add webhook. Payload URL: the Discord webhook URL with `/github` added on the end. Content type: `application/json`.
3. Choose individual events: Pushes, Pull requests, Releases and **Deployment statuses**.
