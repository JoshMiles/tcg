# Sandboxes and preview deployments

> Read this when you touch `lib/db.ts`, sandboxes, the fake Twitch page or anything that must stay isolated from production data.

## Sandbox (test without touching production)
A **sandbox** is a key namespace in the same KV (`sbx:<id>:*`) plus an entry in `sandbox:registry` (production namespace). Enter one at `/admin/sandbox`; while in it, every admin page and website page in that browser reads and writes only that sandbox, and a purple **Sandbox pill** (`SandboxPill`, in `AdminLayout` and `SiteShell`) is always visible.
- **Isolation is one choke point.** `lib/db.ts` wraps the KV client: `currentSandboxId()` resolves the sandbox from (1) a `runInSandbox()` override (AsyncLocalStorage), (2) the `x-tcg-sandbox` request header (the overlay, when its URL has `?sandbox=<token>`), (3) the `tcg_sandbox` cookie (set when an admin enters one), and prefixes every key. **Entry is a signed token, never a bare id**: `lib/sandbox-token.ts` makes `<id>.<hmac>` (`signSandboxId`, HMAC-SHA256 over the id with a key derived for this purpose from `SESSION_SECRET`) and `verifySandboxToken` checks it in constant time; only the admin sandbox actions mint one, and entering a sandbox needs `SESSION_SECRET`. `resolveSandbox` (what `currentSandboxId` calls) maps no value to production, and **a value that is not a valid token for an existing sandbox (junk, a bare id, tampered, deleted) to a dead `__missing__` namespace, never to production**; sandbox ids carry a random base36 suffix (`makeId`) on top of the readable slug; commands that aren't key-first are refused in a sandbox rather than risk an un-prefixed key (`eval` is the one exception: its key list is prefixed, the script and arguments are not; only the lock release uses it). Because it reads headers/cookies, anything using KV renders per request (under Cache Components a KV read is never part of the prerendered shell). **Never cache a KV read with `'use cache'` unless `currentSandboxId()` is passed in as an argument**, or one sandbox's data would be served to production. **The sandbox is not an overlay credential**: `isOverlayRequest` has no sandbox shortcut, so the overlay inside a sandbox presents the key from the sandbox namespace (`getOverlayKey()` run in it, made on first use, never copied from production), like on production; a staff session still passes. `scripts/check-sandbox.mts` (needs the mock KV) proves production is byte-identical after sandbox writes, test tools, resets and deletes, and covers signed entry and the overlay key.
- **The outside world is silenced**: `recordActivity` skips Discord (decided before `after()`, where the request's sandbox isn't visible), `fireOutgoing` doesn't call outgoing webhooks, and `deleteUnusedBlobs` refuses to delete files (the Blob store is shared and a sandbox's data can lag production). Images/sounds are shared; the Twitch Extension panel always talks to production (test on the website instead).
- **Creating one** (`createSandbox`): copy production's setup (seasons, packs, cards, overlay + scoring settings; optionally every viewer's collection) INTO the namespace by reading production and writing prefixed keys, or start empty. Discord / webhook settings and sessions are never copied. **Reset** wipes the namespace (`wipeKeys`, SCAN + a prefix check before every delete) and re-copies; **Clear test data** drops only viewer data; **Delete** wipes and unregisters.
- **Driving it** (`lib/sandbox-tools.ts`): `simulatePulls` (pack by weight → card by odds → variant roll with `effectiveWeights`, exactly like the overlay), `grantCopies` (e.g. exactly enough Regulars for an upgrade), test users, and **Log in as**. A signed `tcg_session` with `sandbox: <id>` that `getSession()` ignores anywhere else, so no Twitch login is needed to test /account, upgrades and (later) trades. Each sandbox action re-checks the admin cookie itself (`requireAdmin`) because server actions can be invoked outside their page. `POST /api/sandbox/exit` (public, harmless) clears the sandbox and session cookies and redirects to `to` through `safeReturnTo` (a same-site path, else `/`). **Seed a crowd** (`seedUsers`): up to 300 test viewers with realistic pull histories (a long tail of light collectors and a few heavy ones, or an even spread), drawn in memory and written in ONE locked read-modify-write (so 100 users is instant, not thousands of per-pull locks). **Card values** (`listCardValues`) shows every card's pull odds, copies out there per variant and points per variant, so you can see rarity × variant at work (base values, before serial bonuses). **Preview the upgrade animation** plays the viewer-facing ceremony for any card and step without a real upgrade.
- **Fake Twitch (`/admin/sandbox/[id]/twitch`)**: tests the Twitch Extension panel without Twitch. It stands in for a channel page (a pretend stream with the sandbox's overlay) and runs the REAL `panel.html` / `mobile.html` / `video_component.html` in an iframe with `?mock=1`, which makes `public/twitch-panel/mock-twitch-ext.js` (loaded after Twitch's helper; a no-op without `?mock`) replace `window.Twitch.ext` with a pretend helper: `onAuthorized`, `onError`, and `actions.requestIdShare` (a stand-in for Twitch's share-identity prompt, after which it re-authorises like the real helper). Tokens come from `POST /api/admin/sandbox/ext-token` (admin only, needs a sandbox): `signMockTwitchJwt` signs with a key derived from `SESSION_SECRET` (never the extension secret) and names the sandbox, and the Extension routes (`login`, `link`, `unlink`, `upgrade`) verify with `verifyExtensionAuth`, which accepts a fake token ONLY while the request is inside that same sandbox (so it can never touch production). The fake login names the user in the token (no Helix call). The panel's own API calls reach the sandbox through the `tcg_sandbox` cookie because the iframe is same-origin; the pretend stream's overlay iframe loads the sandbox overlay link (signed `?sandbox=` plus the sandbox's key). Viewer choices: not logged in to Twitch (login screen, nothing to share), a test user who must share their identity (the prompt), or the broadcaster (direct login, as on the real channel); views: panel 318×500, mobile 375×667, video component over the stream. `scripts/check-sandbox.mts` covers token scoping. New panel features can be tested here before they ever reach Twitch.
- **Sandbox admin (tabs: Overview / Users / Simulate / Card values / Compare / Activity / Settings & reset)**: the list page shows each sandbox's viewers, copies, active season, last use (`touchSandbox`) and expiry. **Scenarios** (`lib/sandbox-scenarios.ts`): `planScenario` is pure (given the active season's cards and upgrade costs it names exactly who gets which copies: `upgrade_ready` / `upgrade_one_short`, `one_card_short`, `completionist`, `trader_a` / `trader_b`, `shiny_hunter`, plus a 100-viewer crowd); `applyScenario` writes the plan in one locked pass. **Users tab**: `SandboxUsers` (client) with search / sort / selection, rank and score from the leaderboard, Log in as, and Clear / Delete (`removeTestUsers`). **Compare** (`lib/sandbox-diff.ts`, pure `diffSetup`; `readSetup` takes a key reader so production and a sandbox are read the same way): seasons, packs, cards and the overlay / scoring settings against production, never viewers; read-only. **Activity + undo** (`lib/sandbox-log.ts`): `withUndo(id, label, usernames, fn)` snapshots every season's collection (and the named viewers' profiles) before a viewer-data change, then logs it (newest 60, key `sandbox:log`, undo point `sandbox:undo`, both INSIDE the sandbox namespace so reset / delete wipe them); `undoLast` is one step and refuses if trades happened since (`tradeStamp`), because escrowed copies would be counted twice. New actions go through `guarded()` in `app/admin/sandbox/actions.ts` (admin check, the sandbox must exist, report on the right tab) and should use `withUndo` when they change viewer data. **Safety**: at most `MAX_SANDBOXES` (10), optional auto-expiry (7 / 30 days, `expiresAt`; `sweepExpiredSandboxes` runs lazily when the Sandbox page loads, there is no background job), and `SandboxPill` adds a purple bar across the top of every page (and sits at the bottom on phones). `scripts/check-sandbox-admin.mts` (mock KV) covers scenarios, removal, undo, compare, expiry and the cap; `scripts/check-sandbox.mts` still proves isolation.
- **Preview deployments (`VERCEL_ENV=preview`)**: `currentSandboxId()` always returns the reserved id `preview` (`PREVIEW_ID`, in `RESERVED_IDS`, which `makeId` never hands out and `listSandboxes` hides): the cookie, header and `runInSandbox` override are ignored, and so is "outside a request" (which means production everywhere else). So everything silenced in a sandbox is silenced on previews (Discord, outgoing webhooks, Blob deletes). `prodKv` is **fenced** there: reads pass (the staff list, seeding), but any write outside `sbx:preview:` is rejected and pipelines are refused (`isPreview()` is read per call). Staff can sign in to a preview with their real roles; `touchStaffLogin` is skipped and add / change / remove staff is refused. Sandboxes are switched off on previews (`PreviewOff`, `admin()` in the sandbox actions, the ext-token route). `SandboxPill` shows an amber "Preview deployment" bar. Seeding: `seedPreviewFromProduction` (the same `cloneFromProduction` / `SETUP_SETTINGS_KEYS` a sandbox uses), `wipeKeys('preview')`, both from the `PreviewDataPanel` actions. `scripts/check-sandbox.mts` has a preview section.
- **Future features**: build them against `kv` from `lib/db.ts` and they are testable in a sandbox for free. Anything that reaches outside (HTTP calls, Blob deletes, Discord DMs) must check `inSandbox()` first.
