# Staff: admin and mod panels

> Read this when you touch staff roles, Twitch sign-in for the admin / mod panels, the mod panel or who-did-it attribution.

## Staff: admin and mod panels (Twitch login)
Staff sign in with **Log in with Twitch** (the same OAuth as viewers) and get a role from the staff list. **Roles** (`lib/staff-core.ts`, pure and edge-safe): `super` (the owner, hard-coded by Twitch ID in `SUPER_ADMINS` plus any IDs in `SUPER_ADMIN_TWITCH_IDS`; matched by ID, never by name; can't be removed or changed), `admin` (whole admin panel; can add / change / remove mods) and `mod` (the `/mod` panel only). Only the super admin can add or remove admins (`canManage`, `roleCan`). The staff list is the KV hash `staff:members` (login -> `StaffRecord`) with a capped log `staff:log`, stored with `prodKv` so it is the same inside a sandbox (`lib/staff.ts`: `addStaff` / `setStaffRole` / `removeStaff` / `touchStaffLogin`, all enforcing the rules and logging who did it). A record is bound to the account's Twitch ID the first time they sign in (or from their viewer profile when added) and then only that ID matches, so a renamed or re-claimed login can't inherit access. A sign-in never rewrites the staff record: `touchStaffLogin` stores the last sign-in time and display name in the hash `staff:seen` (login -> `{ lastLogin, displayName }`, one field per write) and binds the Twitch ID with a write-once `hsetnx` into `staff:ids` (login -> `{ id }`). `getStaffRecord` and `listStaff` overlay those onto the record (the record's own `twitchId`, `displayName` and `lastLogin` are the fallback for people who have not signed in since), so a role change or removal can't be undone by a sign-in. `addStaff` clears both entries for the login.
- **Sign-in flow**: login page (`/login`) -> `/auth/twitch?returnTo=/admin` -> middleware sees a viewer session but no staff cookie -> `/auth/staff` (`app/auth/staff/route.ts`) looks the account up and issues the one-hour signed `tcg_staff` cookie (`lib/staff-token.ts`, Web Crypto HMAC, edge-safe, keyed by its own key derived from `SESSION_SECRET`: `lib/signing.ts`) -> the panel. The same route silently renews the cookie hourly while the role stays valid, and turns a removed person away (`/login?error=not-staff`). `requireStaff` and `hasStaffCapability` also slide the cookie forward (re-issued with the live role when under 30 minutes are left, never past 12 hours after the first issue, `iat`), so an open activity feed keeps working; on a 401 the feed calls `/auth/staff?silent=1` (JSON, no redirects) and retries once, else shows "Sign in again". A fresh Twitch sign-in and website logout clear the staff cookie. **Panel Log out** (`/api/auth/logout`) clears the staff and emergency cookies but keeps the website login, so it also sets a 12-hour `tcg_staff_out` marker: while it is there `/auth/staff` sends the next panel visit to `/login` (and the silent renewal answers 401) instead of re-issuing the staff cookie from the site login. Pressing "Log in with Twitch" (`/auth/twitch`) clears it. The sign-in page then shows "Log out of the website too". The emergency generation only moves when the posted emergency cookie is valid.
- **Enforcement (defence in depth)**: `middleware.ts` (matcher `/admin`, `/mod`) reads the signed cookies and sends admins/super to either panel, mods to `/mod` only, strangers to `/login`. The staff cookie needs no database. The emergency password cookie also checks its expiry and generation (one read, only when that cookie is present). The authoritative check is `getStaff()` / `requireStaff(cap)` in `lib/staff-guard.ts`, which reads the staff list (cached for 15 s per instance, see below): both panel layouts, every panel page (`staffPage`), every server action (`requireAdmin()` = `requireStaff('admin')`) and every `/api/admin/*` route (`isAuthenticated()` / `hasStaffCapability`) call it, so removing someone stops their changes and their page loads at once. Mods may use only: `saveTagsAction`, `saveFlagsAction`, `cancelUserTradeAction` (`app/admin/users-actions.ts`), `cancelOneTradeAction`, `blockViewerTradingAction`, `reverseTradeAction` (`app/admin/trade-actions.ts`), `updateFeedbackAction` (the feedback inbox) and read `/api/admin/activity`; those call `requireStaff('mod')`. **A new admin action must call `requireAdmin()`; give it `requireStaff('mod')` only if mods should be able to use it.**
- **Who may moderate whom (`canModerate`)**: one pure rule in `lib/staff-core.ts`, `canModerate(actor, target, action)`, asked before every mod action acts, once per person it touches (`checkModerate` in `lib/staff.ts` looks the target up: their staff role and who set the restrictions they carry). Actions are `tags`, `flags`, `cancel-offer`, `block-trading`, `reverse-trade`. The rules: nobody moderates themselves (the emergency login is not an account, so it is exempt); staff targets follow `canManage` (an admin acts on mods and viewers, only the super admin on admins, nobody on the super admin, a mod on no staff at all); the streamer's account (`CHANNEL_LOGIN`, staff or not) only the super admin; and a mod can't change restrictions an admin or the super admin set (`flags.by`; the emergency login counts as the super admin). `saveTagsAction`, `saveFlagsAction` and `blockViewerTradingAction` call `checkModerate` with the viewer's name. `cancelTrade` (opts `actor`) checks the offerer and `reverseTrade(id, actor, reason)` checks both people in the trade, so the target comes from the stored trade, never from the browser. A refusal comes back as the action's `{ ok: false, message }`. A new mod action must call `checkModerate` / `canModerate`; the cases are in `scripts/check-moderation.mts`.
- **Emergency password**: the old `ADMIN_PASSWORD` login still works as a break-glass super admin (shown as "(password)") unless `ADMIN_PASSWORD_LOGIN=off` (`isPasswordLoginEnabled` in `lib/admin-token.ts`; the middleware and `getStaff` both honour it). The cookie is signed with `ADMIN_COOKIE_SECRET` (not `ADMIN_SECRET`), lasts 7 days, and the server rejects it after that. Each cookie is stamped with a generation in KV (`admin:auth-gen:<env>`, or `sbx:preview:admin:auth-gen` on a preview). Signing out while that cookie is set bumps the generation, so a copied cookie stops working. `ADMIN_SECRET` no longer signs anything; rotate it if the old import URL was ever opened. **Wrong passwords are limited** (`lib/login-limit.ts`, on the shared limiter in `lib/rate-limit.ts`, see docs/hosting.md): 10 per caller address in 15 minutes, and 20 from all addresses together per clock hour. Once either limit is reached `/api/auth/login` answers 429 "Too many attempts" even for the right password (the site-wide limit until the hour ends); Twitch staff sign-in is not affected. Failures are counted in the production namespace (`prodKv`; on a preview deployment, its own namespace), so a sandbox cookie or `x-tcg-sandbox` header, valid or junk, never starts a fresh count. The caller address is `x-real-ip`, else the right-most `x-forwarded-for` entry, never the left-most one the caller can set; behind a proxy that hides the caller (an orange-cloud Cloudflare record) every caller shares one address bucket, and the site-wide limit still applies.
- **Moves by Twitch ID do not touch staff**: staff records are keyed by login with the Twitch ID bound on first sign-in (`staff:ids`, login -> ID) and staff cookies carry their own ID, so a sign-in that moves a player account aside or onto a new login (docs/public-site/accounts.md) does not change who is staff. A staff member whose Twitch login was renamed has to be added again under the new login; the old record is not moved by a rename. The session check in `getSession` also applies to staff signing in as viewers, but the staff cookie path does not use it.
- **Who did it (attribution)**: anything a staff member does to a viewer names them. `currentStaffLogin()` (`lib/staff-actor.ts`, never throws, null outside a panel request) feeds: the audit trail (`AuditEntry.by`, `recordAudit`), the activity log (`ActivityEvent.staff`, set in `recordActivity` only for events staff cause, `isStaffAction`: admin grants, removals, resets, deletes, admin-sent packs and admin cancels of offers, never a viewer's own pull / upgrade / trade even if that viewer is staff), cancelled trades (`Trade.staff`, set in `closeTrade` when `resolvedBy === 'admin'`; shown in the trade log detail) and a viewer's restrictions (`flags.by`). `plainText()` appends "(by <login>)" so the feed, search, CSV and the user timelines show it. Restrictions, tag changes, offer cancels, trade blocks and reversals (with the reason) and every emergency password login also post one line to the Discord admin log, naming the staff login (docs/admin/discord.md). The staff login is staff-only: the public profile Activity tab, Discord posts and viewer trade pages don't render it. A new admin action that records activity or audit gets this for free; one that stores its own record should save `await currentStaffLogin()` alongside it.
- **Timed trade block (ROADMAP 51.3, TRIAL for one season: keep or drop at season end; success is fewer manual lifts)**: "Block trading" may carry `flags.until` (ms), chosen as "Lifts after" (1, 3, 7 or 30 days, or none) in the moderation panel and validated server-side (`untilFromDays`; anything else means no end; "Keep current end" keeps a live one). It lifts lazily: every trading-block reader goes through `tradeBlockedNow` / `liveUntil` in `lib/restriction.ts` (the trade guard in `lib/trades.ts`, `isTradeBlocked`, `/trade/new`, the copy page's Offer button, the mod and admin viewer pages and lists), so a past `until` reads as not blocked with no sweep and no write; the stored flag is tidied on the next save. Only the trade block expires, never "Hide from public boards". The end shows as "No trading until <date>" on the viewer pages and on `/trade/new` for the viewer, and the audit line (and so the Discord admin log) says "no trading until <date>". Blocking from the Trades page (`blockViewerTradingAction`) has no end.
- **Panel link on the public site**: `SiteShell` calls `staffPanelLink(session)` (`lib/staff-guard.ts`: the signed-in viewer is looked up in the staff list, so staff see it without having opened a panel; a password-only admin is recognised from their cookie) and passes `staff` to `SiteNav`, which shows a purple **Admin panel** (admins and the super admin) or **Mod panel** (mods) button in the top bar, the account menu and the phone menu. Nobody else sees it. It is only a convenience link (`prefetch={false}`): clicking it goes through the middleware and `/auth/staff`, and the panels check access again themselves.
- **Staff page** (`/admin/staff`, nav key `f`; `app/admin/staff/` + `staff-actions.ts`): the fixed super admin(s), a table to add by Twitch name (autocompletes viewers), change role and remove, and the change log. The audit trail (`recordAudit`) now records who (`by`) made each change, shown on a viewer's audit panels.
- **Mod panel** (`/mod`, `app/mod/`): its own slim layout (`ModNav`), Overview (a **stream desk** strip first, then tiles: events in the last hour, open offers, **Hidden by staff** = the admin-hidden set, **Private profiles** = viewers who chose it, season), **Activity** (the admin `ActivityFeed` with `mod` = read-only: no gift / grant / remove, viewer links go to `/mod/users/...`), **Viewers** (search, restricted-only filter, sort by A to Z / last seen / most pulls (`?sort=`; each row shows pulls and last seen, from `stats:last` and the collections already read, no new index); profiles are read for the 80 rows shown, or for everyone matching when "Restricted only" is on, since there is no index of restricted viewers; a viewer page with restrictions, tags, trades (open offers in either direction can be cancelled and refunded; each row names its own season and the card names come from that season, with a season filter once the viewer has traded in more than one), recent activity and the staff audit; restrictions only apply on the "Save restrictions" button, which stays disabled (with a note saying why) until a switch or the reason changes and turns yellow when it has, so a restriction always carries its reason; reuses `ModerationPanel` / `TagsEditor` / `TradesPanel` from `app/admin/users/[username]/UserPanels.tsx`) and **Trades** (the admin `TradeLog` with `mod` = no Extend; the trade detail has a Block button for each party and opens in the shared `Dialog`, so it traps focus, closes on Escape and returns focus; data from the shared `loadTradeAdminData()` in `lib/trade-admin-data.ts`, which the admin Trades page uses too). Also **Feedback** (the viewer inbox: answer and change status; deletion requests stay admin-only, see below), **Testers** (read-only: only admins change the tester list) and **What's new** (mod-panel changes, newest first). `/mod` is noindex and disallowed in robots. `scripts/check-staff.mts` (mock KV) covers roles, the ID binding, the signed cookie and the staff list rules.
- **Deletion requests are admin-only**: `deleteViewerForRequestAction` and `declineDeletionAction` call `requireAdmin()`, and `updateFeedbackAction` (the one mod action on the feedback inbox) calls `requireAdmin()` as well when the item is a deletion request.
- **The staff record is cached for 15 s per server instance** (ROADMAP 48.5): `getStaffRecord` (what `getStaff`, `staffPanelLink`, `/auth/staff`, the settings page and `lib/access.ts` read) keeps each login's record, "not staff" included, in `createTtlCache` memory for `STAFF_CACHE_TTL_MS`. Every write in `lib/staff.ts` (`addStaff`, `setStaffRole`, `removeStaff`, the Twitch ID pin and bind) calls `forgetStaffCache()`, so this instance shows the change at once; **another instance can show the old role for up to 15 s** (a removed mod can still pass a guard there for that long). A failed read is never cached. Code that is about to write (add, change, remove, pin, the moderation checks) reads with `readStaffRecord`, never the cache. A script that writes `staff:members` or `staff:ids` directly must call `forgetStaffCache()`.
- **Stream desk (TRIAL, ROADMAP 51.2, four weeks)**: `app/mod/StreamDesk.tsx`, a read-only strip at the top of `/mod`: overlay connected, stream live (from OBS, when it shares that), whether pulls are paused and the pull queue length. It polls `/api/admin/overlay-status` every 5 s while the tab is visible (the same poll as the admin status; the route now also answers mods, as `/api/admin/activity` does). "Pulls paused" is the only-when-live switch (`liveGate('pull')`, returned as `pullsBlocked`): there is no separate pause switch. No buttons, a mod still cannot change anything. Success: mods use it during streams; remove it if they do not.
- **Every panel page guards itself**: the layouts check the live staff list, but a layout does not render again on in-panel navigation, so each `/admin` and `/mod` page starts with `await staffPage('admin' | 'mod')` (`lib/staff-guard.ts`: re-reads the live list, sends a mod to `/mod` and anyone else to the login page, returns the `StaffContext`). `requireAdmin()` / `requireStaff()` also count. A new page must start with one; `staffPage` redirects, the `require*` calls throw.
- **Route and page audit** (`scripts/check-route-guards.mts`, part of `npm run verify`): fails if an `/admin` or `/mod` page has no guard (an admin page needs an admin-level one), if any `app/**/route.ts` is not listed in the check's route table, or if a listed route's source lacks the guard it is listed with (`viewer` session or Extension token, `staff`, `cron` secret, incoming `webhook` secret, `overlay` key) or is gone. Open-by-design routes are listed as `public` with the reason. Everything under `/api/admin` must call a staff check without being listed. A new route therefore has to be classified on purpose.
- **Guard audit** (`scripts/check-staff-guards.mts`, part of `npm run check`): reads the source and fails if any exported admin server action (every `'use server'` file under `app/admin` and `app/mod`, whatever its name) does not call `requireAdmin()` / `requireStaff()` (directly or through a helper in its file), if a viewer action does not read the session, if an `/api/admin/*` route has no staff check, or if the set of actions / routes a mod may use differs from the documented list (`saveTagsAction`, `saveFlagsAction`, `cancelUserTradeAction`, `cancelOneTradeAction`, `blockViewerTradingAction`, `reverseTradeAction` (reverse a completed trade, ROADMAP 9.2), and the activity feed route). Server actions are public POST endpoints, so the page middleware is not a substitute. A bare `requireStaff()` defaults to mod and counts as a mod action. Adding a mod action means updating `DOCUMENTED_MOD_ACTIONS` in that check on purpose.
- **Back to the public site (mod panel)**: the top bar has a Public site link (`/`). The admin sidebar footer has the matching pair, **Public site** and **Mod view** (`/mod`), so an admin can move between the panels and the site (`app/admin/layout.tsx`; the mod bar links back to the admin panel for admins, as an icon-only link on phones).
- **Staff wiki** (`/admin/wiki`, sidebar and dashboard link, shortcut `g` then `k`): topics rendered from `content/wiki/*.md`. It sits in the admin layout, so only an admin or the super admin can open it. Mods stay on `/mod` and have no link.

## Middleware matcher (closed alpha / beta)
The middleware matcher covers the whole site (`'/((?!_next/|assets/|brand/|icons/|twitch-panel/|.*\..*).*)'`), not just the panels. The order in `middleware()` matters: `/api/twitch/*` and `/api/version` return `extensionCors` first and never meet the access gate (Twitch panel freeze); `/admin` and `/mod` keep the staff gate above; everything else goes through `publicGate` (see "Closed alpha / beta" in docs/public-site.md). A valid staff cookie, or the emergency password cookie, passes the access gate in every mode. `scripts/check-access.mts` runs the matcher against every exempt and gated path, so change `isExemptPath` and that check together.

## Staff badges on public pages (ROADMAP 17.1)
`lib/staff-badge.ts`: pure `staffBadgeFor(login, staff, settings, superLogins)` (Streamer = the channel's own login (`CHANNEL_LOGIN`, staff or not), super admins show Admin, then the staff list's Admin / Mod; null when `UserSettings.hideStaffBadge`) and `getStaffBadges()` (React `cache`, one live read of `listStaff()` per request, login -> badge). Shown by `app/components/StaffBadge.tsx` (a daisyUI `badge`) in `ProfileHeader`, the leaderboard `Board` rows (shield only) and `/trade/<id>` next to each named user. A staff member hides their own in Settings ("Show my staff badge", shown only to staff). Never in the Twitch panel (freeze). Check: `scripts/check-staff.mts`.
