# Mix It Up

> Read this when you touch paid pulls, webhook grants or Mix It Up chat commands.

## Mix It Up paid pulls (Mix It Up page)
Viewers can pay a currency (Brie Bucks) for a pack. Settings live in KV `mixitup:settings` (`lib/mixitup-core.ts`, pure; `lib/mixitup.ts`, KV and calls; page `app/admin/mixitup/` (tabs Paid pulls, Log; Commands), form in `MixItUpConfig.tsx`, actions in `mixitup-actions.ts`). Off by default; while off nothing below happens. Design and decisions: ROADMAP Track 12.
- **Flow**: `POST /api/webhooks/pull` reserves the pull (`reservePaidPull`: viewer's pulls this stream, then a `balance` request to Mix It Up, counting pulls already in flight) and queues it with `paid: true`. The overlay sends the event id back as the pull's ticket; `POST /api/collection` claims the ticket and then the payment (once each; a reused payment = 409, nothing saved), sends the `deduct` request with the custom message **before** the print is written (so the edition number is not known yet and `{serial}` is empty), and only then adds the print. If Mix It Up does not confirm, no print is made, the pull allowance comes back and the System Discord channel is told (`noticeUnpaid`); if the print then cannot be saved, the charge is paid back through the add address (`refundPaidPull`, the same call the currency-grant buff uses) and staff are told to refund by hand when that fails too. Refusals queue nothing and answer `{ ok: true, ignored: true, reason, message }` (`insufficient_balance | limit_reached | mixitup_unavailable | bad_balance`) so the Mix It Up command can post `message` to chat.
- **Mix It Up answers in the HTTP reply** (a Webhook Response action). Balance: JSON with a number at the balance field. Deduct: any 2xx counts unless the body sets `ok`, `success` or `applied` to false.
- **Limit per stream**: Paid pulls has a number for regular, subscriber, VIP, moderator and broadcaster (all 0, no limit, until staff change them). The old single `limit` is the fallback when a role has no number, so a save from before role limits keeps working. The pull webhook may send `role` (`regular | subscriber | vip | moderator | broadcaster`); missing or unknown counts as regular, and `CHANNEL_LOGIN` is always the broadcaster. The site does not ask Twitch which role someone is. A gifted sub earns a pack and does not change a limit. A viewer's own limit (`user:<name>:pulllimit`, user page → Admin tab → Pull limit) replaces the role, and their temporary bonuses still add (ROADMAP 12.4). A base of 0 stays unlimited. **This stream, everyone:** Set / Clear on the same tab stores `{ amount, streamKey, by, at }` at `pulls:stream-buff`. It adds for every viewer only while `currentStreamKey()` still matches, and amount 0 deletes it. Counter `mixitup:cnt:<stream>:<viewer>` where the stream is the live Twitch stream's start (`getLiveStatus`), else the UTC day. Raised on reserve, lowered when a reservation fails or a pull is revoked. In-flight pulls: `mixitup:pending:<viewer>`; reservation `mixitup:pay:<id>` (1 h).
- Gifts from the dashboard, the extension and sandboxes never charge. Addresses are saved through `checkWebhookUrl` (public https only) and every call goes through `sendWebhook` (`lib/webhook-send.ts`: see ux-conventions, outgoing webhook addresses; an http address saved earlier still sends, a localhost one never does, so Mix It Up on the streamer's own machine needs an https tunnel); the last 20 requests are in KV `mixitup:log` and shown on the Log tab. `scripts/check-mixitup.mts` covers it with a fake Mix It Up. **Copy setup** (`paidPullSetup` in `lib/mixitup-setup.ts`) shows the balance and deduct bodies from the saved settings, the addresses, which action should answer `{ "balance": n }` (the saved balance field), and which action takes the currency. An empty deduct address is the balance address, told apart by `action`.
- **Add address** (`addUrl`, optional): the Mix It Up command that gives currency, used only by the `currency-grant` buff (Buff Editor). `grantCurrency` in `lib/mixitup.ts` sends `{ action: 'add', secret, username, amount, currency }` and, like a deduct, counts a 2xx unless the body sets `ok`, `success` or `applied` to false; it is logged as `add`. **Chat viewers address** (`viewersUrl`, optional): answers `{ users: string[] }` (or a bare array); `fetchChatViewers` sends `{ action: 'viewers', secret, currency }`, lowercases, drops @, dedupes and caps at 5000. Community `score-bonus` and `currency-grant` buffs go to those viewers (players with no cards included, who have no leaderboard row until they pull) and fail with a clear error when Mix It Up is off, the address is empty, or the call fails. A `currency-grant` writes a record `buffgrant:<id>` first (user to pending/paid/failed), pays one viewer at a time saving after each, and never pays a viewer marked paid; unpaid grants are listed in `buffgrants:open` and shown on the Buff Editor with **Retry unpaid** (`runGrant`, `retryGrantAction`). The trigger (card) is spent once; a partial result tells the player some are unpaid. The buff refuses to apply (and the Buff Editor warns) while Mix It Up is off or `addUrl` is empty; sandboxes never call it.
- **Connection health** (`lib/mixitup-health.ts`, `scripts/check-mixitup-health.mts`): a chip row above the tabs on every tab of the Mix It Up page. Two small hashes, written fire-and-forget (a failed write never touches the request). `mixitup:seen`: field = incoming route (`/api/webhooks/*` only), value `{ okAt?, badAt? }`; `incomingSecretValid` sets `okAt` on a right secret and `badAt` on a non-empty wrong one (the other field is kept; a missing secret records nothing). `mixitup:out`: field = `balance | deduct | add | viewers`, value `{ at, ok, detail }`; `callMixItUp` records the last result by the payload's `action` (`ok` = Mix It Up answered 2xx, `detail` = `HTTP <status>` or the plain-words error; a `test` message is not recorded). The chips: when Mix It Up last reached the site and through which route (`!pack`, chat commands, show-off, card reward, collection, stream start/end), a warning for any route whose `badAt` is newer than its `okAt`, and one chip per address (not set / set, not used yet / working / failing with the reason; an empty deduct address shows "uses the balance address"). `healthChips` is the pure part.
- `/api/collection` is locked down by server-rolled pulls (docs/overlay.md, ROADMAP 13.1).

## TCG Bridge (site side)
ROADMAP 55.0. Mix It Up cannot answer an HTTP request with custom JSON, so the four outgoing addresses cannot work against stock Mix It Up. In **bridge mode** (the default for new settings) the site never calls Mix It Up: a desktop app on the stream PC, TCG Bridge (55.6), long-polls the site for jobs, runs them through Mix It Up's local Developer API and posts the results. `lib/bridge-core.ts` is pure (shapes, pair codes, token hashing, result to reply); `lib/bridge.ts` is the KV side; the routes are thin.
- **Settings**: `connection: 'bridge' | 'addresses'` and `currencyId` (the Mix It Up currency GUID; `currency` stays the display name, and the save copies it from the bridge's `hello` list). Settings saved with no `connection` read as `addresses` when any of the four addresses is set, else `bridge`, so an existing setup does not change. The Paid pulls form (`ConnectionSwitch`) shows either the currency select (filled from the last `hello`, "Pair TCG Bridge first" before one) or the four addresses, secret, balance field and currency name; both groups stay in the form so a save keeps the other mode's values. Switching on needs a currency in bridge mode and the balance address in addresses mode. `hasBalanceRoute / hasAddRoute / hasViewersRoute` (`mixitup-core.ts`) are the "is this possible" checks the buffs and the Try it buttons use.
- **Transport**: every outgoing call in `lib/mixitup.ts` goes through `callOut`, which is `callBridge` in bridge mode and `callMixItUp` otherwise; callers keep their logic and parse the same `Reply`. `callBridge` pushes a job (RPUSH `bridge:jobs`), then reads `bridge:result:<id>` every 250 ms for up to 8 s. No result is `ok: false`, "TCG Bridge did not answer", exactly like Mix It Up not answering, so a reservation is refused and released and nothing is charged. The balance is read from `balance` whatever the balance field says. Health (`noteOutgoing`) is noted as before. A sandbox or preview never creates a job. `bridgeSay(text)` queues a fire-and-forget `say` job; nothing calls it yet. The Try it "Send test message" sends a `say` job with the rendered message and waits, so the bridge must post a result for `say` too.
- **Jobs** (`bridge:jobs`, a list): `{ id, kind: 'balance' | 'deduct' | 'add' | 'viewers' | 'say', username?, amount?, currencyId?, text?, at }`. `text` is the chat message of a deduct, or the line of a say. A job older than 10 s is dropped when it is claimed (the waiter gave up after 8 s, and a late deduct must not run), as is anything malformed.
- **Results**: `POST /api/bridge/result` `{ id, ok, balance?, users?, error? }` writes `bridge:result:<id>` for 60 s. A `balance` result needs `balance` (a number, 0 or more), a `viewers` result needs `users` (strings, capped at 5000); `ok: false` carries `error`.
- **Endpoints** (Node, all POST JSON): `/api/bridge/pair` `{ code, name }` returns `{ token }` once; `/api/bridge/poll` `{ version? }` holds the request up to 25 s and returns `{ jobs }` (empty on timeout; LPOP is atomic, so a job reaches one poller; `maxDuration` 40); `/api/bridge/result`; `/api/bridge/hello` `{ version, currencies: [{ id, name }] }`. The OBS report route belongs to 55.6b and is not built.
- **Auth**: every route but `pair` needs `Authorization: Bearer <token>`; the sha256 of the token must be a field of `bridge:tokens` (value `{ id, name, createdAt, lastSeen }`; the token itself is never stored). Unknown, missing or revoked is a 401. All routes call `limitWebhook` first; `pair` also allows 10 tries per address per 10 minutes. A poll notes `lastSeen` and `mixitup:bridge` at most every 10 s and ends with a 401 if its token is revoked meanwhile.
- **Pairing**: the TCG Bridge card on the Paid pulls tab makes a code (`createPairCodeAction`: `requireAdmin`, audited, shown as `ABCD-EFGH` with its expiry, never put in a URL). `bridge:pair:<code>` lasts 600 s and the delete is the claim, so a code works once. Paired bridges list with name, paired and last seen, and **Revoke** (`ArmedButton`, `revokeBridgeAction`, audited; revoked by the record's `id`, so no token or hash reaches the page).
- **KV keys**: `bridge:jobs`, `bridge:result:<id>`, `bridge:pair:<code>`, `bridge:tokens` (hash), `mixitup:bridge` (hash: `at`, `version`, `currencies`; the health chip and the select).
- **Health row**: in bridge mode one chip replaces the four address chips: "TCG Bridge connected (...)" when `mixitup:bridge.at` is within 60 s, else "TCG Bridge not connected" (with the last seen time when there is one). The incoming chips stay.
- `scripts/check-bridge.mts` covers the settings default, pairing, auth, claiming, stale jobs, a fake bridge answering a reserve / charge / refund, and the timeout.

## Webhook grants look like pulls
The incoming webhooks only accept a real Twitch login as `username` (3 to 25 letters, digits and underscores; a leading `@` is dropped; anything else is a 400), and the grant-card webhook only grants a card number that exists in a published pack of the active season (404 otherwise), so a bad Mix It Up variable fails loudly instead of creating a ghost viewer.

A card granted by the grant-card webhook (a Mix It Up reward) is recorded as `grant` with `source: 'webhook'` plus the facts of a pull (name, stars, pack, new or not, copies, collected, edition). It counts as a **pull** in the Live Activity categories and the Discord Pulls category (with the star and new-only filters), reads "X pulled Y (granted by webhook)" in the live feed and on the dashboard's Recent activity, and posts the same embed as a pull with a "Granted by webhook" line (`pullEmbed` in `lib/discord.ts`). The Live Activity numbers, the stream recap (`asPullEvent` in `lib/activity-view.ts`; there it is listed as a reward rather than a pack opened) and the stats counters behind the weekly digest and the dashboard charts (`recordStats`, from the day this shipped) count it as a pull too. Admin grants are unchanged (Grants & removals, the Cards Discord category, the `grant` counter). Events recorded before this change lack the extra facts and still post, with the card's stars looked up.

## Mix It Up chat commands (Mix It Up page, Commands tab)
ROADMAP 19.2. One incoming webhook, `POST /api/webhooks/command` (`{ secret, command, username, args? }`, the incoming secret), answers every chat command: `{ ok, message, vars }` plus each variable at the top level for Mix It Up's "JSON to special identifiers". A refusal is `{ ok: false, message }` with the command's own error text; an unknown or switched-off command is `{ ok: false, message: '' }` (silent). `/api/webhooks/show-card` still works unchanged.
- **Pure core** `lib/commands-core.ts`: the `ChatCommand` shape, the fixed action registry `COMMAND_ACTIONS` (each action's variables, sample values and error kinds: `showoff`, `card-stats`, `my-stats`, `collection`, `leaderboard`, `pulls-left`, `text`), `matchCommand` (name or alias, without the `!`), `interpolate` (unknown placeholders dropped), `tidyReply` (no Markdown marks, 400 characters), `cleanCommands` (max 30, unique names). **KV** `lib/commands.ts`: commands in `mixitup:commands` (the defaults `!showoff` and `!stats` are seeded on first read), run counts in `mixitup:cmdstats`, the last 20 runs in `mixitup:cmdlog` (shown on the Log tab, never posted to Discord), cooldowns `cmd:cd:<id>` and `cmd:ucd:<id>:<viewer>` with a TTL. `runCommand` is used by the webhook and by Try it.
- **Dry run**: Try it (the builder) runs the editor's draft with `dry`: no overlay event, no cooldown spent, no log line. `showoff` calls `prepareShowOff(user, args, { dry })`. A sandbox never queues an overlay event either.
- **Privacy**: hidden and private collectors (`getHiddenUsers`) show as "a private collector" in `topHolder` / `firstPulledBy`, are left out of `collectors`, and `my-stats` for them answers "This collector keeps their stats private" unless they ask about themselves.
- **FAQ**: the "Chat commands" section lists the enabled commands from `getCommands()`, then a fixed `!pack` line (it asks the stream to open a pack, and it is set up in Mix It Up rather than the command builder). `scripts/check-commands.mts` covers the builder. **Copy setup** (`commandSetups` in `lib/mixitup-setup.ts`) lists every switched-on command: the `!` name, `POST /api/webhooks/command`, the JSON body (the real incoming secret, `$username`, `$allargs`) and the `message` field for the Chat Message.

**Stream start / end** (`POST /api/webhooks/stream`, `{ secret, event: 'live' | 'offline' }`, the incoming secret): wire Mix It Up's Stream Start and Stream End events to it. `setLiveFromHint` (`lib/twitch-live.ts`) marks the stream live or offline at once (System notice, stream-start marker, recap on offline) and stores `twitch:live:hint`; for 5 minutes a Helix answer that disagrees is overridden, since Twitch's API lags a stream's start and end. The minute cron keeps checking Helix as a fallback.
