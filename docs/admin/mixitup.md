# Mix It Up

> Read this when you touch paid pulls, webhook grants or Mix It Up chat commands.

## Mix It Up paid pulls (Mix It Up page)
Viewers can pay a currency (Brie Bucks) for a pack. Settings live in KV `mixitup:settings` (`lib/mixitup-core.ts`, pure; `lib/mixitup.ts`, KV and calls; page `app/admin/mixitup/` (tabs Paid pulls, Log; Commands), form in `MixItUpConfig.tsx`, actions in `mixitup-actions.ts`). Off by default; while off nothing below happens. Design and decisions: ROADMAP Track 12.
- **Flow**: `POST /api/webhooks/pull` reserves the pull (`reservePaidPull`: viewer's pulls this stream, then a `balance` request to Mix It Up, counting pulls already in flight) and queues it with `paid: true`. The overlay sends the event id back as the pull's ticket; `POST /api/collection` claims the ticket and then the payment (once each; a reused payment = 409, nothing saved), sends the `deduct` request with the custom message **before** the print is written (so the edition number is not known yet and `{serial}` is empty), and only then adds the print. If Mix It Up does not confirm, no print is made, the pull allowance comes back and the System Discord channel is told (`noticeUnpaid`); if the print then cannot be saved, the charge is paid back through the add address (`refundPaidPull`, the same call the currency-grant buff uses) and staff are told to refund by hand when that fails too. Refusals queue nothing and answer `{ ok: true, ignored: true, reason, message }` (`insufficient_balance | limit_reached | mixitup_unavailable | bad_balance`) so the Mix It Up command can post `message` to chat.
- **Mix It Up answers in the HTTP reply** (a Webhook Response action). Balance: JSON with a number at the balance field. Deduct: any 2xx counts unless the body sets `ok`, `success` or `applied` to false.
- **Limit per stream**: Paid pulls has a number for regular, subscriber, VIP, moderator and broadcaster (all 0, no limit, until staff change them). The old single `limit` is the fallback when a role has no number, so a save from before role limits keeps working. The pull webhook may send `role` (`regular | subscriber | vip | moderator | broadcaster`); missing or unknown counts as regular, and `CHANNEL_LOGIN` is always the broadcaster. The site does not ask Twitch which role someone is. A gifted sub earns a pack and does not change a limit. A viewer's own limit (`user:<name>:pulllimit`, user page → Admin tab → Pull limit) replaces the role, and their temporary bonuses still add (ROADMAP 12.4). A base of 0 stays unlimited. **This stream, everyone:** Set / Clear on the same tab stores `{ amount, streamKey, by, at }` at `pulls:stream-buff`. It adds for every viewer only while `currentStreamKey()` still matches, and amount 0 deletes it. Counter `mixitup:cnt:<stream>:<viewer>` where the stream is the live Twitch stream's start (`getLiveStatus`), else the UTC day. Raised on reserve, lowered when a reservation fails or a pull is revoked. In-flight pulls: `mixitup:pending:<viewer>`; reservation `mixitup:pay:<id>` (1 h).
- Gifts from the dashboard, the extension and sandboxes never charge. Addresses are saved through `checkWebhookUrl` (public https only) and every call goes through `sendWebhook` (`lib/webhook-send.ts`: see ux-conventions, outgoing webhook addresses; an http address saved earlier still sends, a localhost one never does, so Mix It Up on the streamer's own machine needs an https tunnel); the last 20 requests are in KV `mixitup:log` and shown on the Log tab. `scripts/check-mixitup.mts` covers it with a fake Mix It Up. **Copy setup** (`paidPullSetup` in `lib/mixitup-setup.ts`) shows the balance and deduct bodies from the saved settings, the addresses, which action should answer `{ "balance": n }` (the saved balance field), and which action takes the currency. An empty deduct address is the balance address, told apart by `action`.
- **Add address** (`addUrl`, optional): the Mix It Up command that gives currency, used only by the `currency-grant` buff (Buff Editor). `grantCurrency` in `lib/mixitup.ts` sends `{ action: 'add', secret, username, amount, currency }` and, like a deduct, counts a 2xx unless the body sets `ok`, `success` or `applied` to false; it is logged as `add`. **Chat viewers address** (`viewersUrl`, optional): answers `{ users: string[] }` (or a bare array); `fetchChatViewers` sends `{ action: 'viewers', secret, currency }`, lowercases, drops @, dedupes and caps at 5000. Community `score-bonus` and `currency-grant` buffs go to those viewers (players with no cards included, who have no leaderboard row until they pull) and fail with a clear error when Mix It Up is off, the address is empty, or the call fails. A `currency-grant` writes a record `buffgrant:<id>` first (user to pending/paid/failed), pays one viewer at a time saving after each, and never pays a viewer marked paid; unpaid grants are listed in `buffgrants:open` and shown on the Buff Editor with **Retry unpaid** (`runGrant`, `retryGrantAction`). The trigger (card) is spent once; a partial result tells the player some are unpaid. The buff refuses to apply (and the Buff Editor warns) while Mix It Up is off or `addUrl` is empty; sandboxes never call it.
- **Connection health** (`lib/mixitup-health.ts`, `scripts/check-mixitup-health.mts`): a chip row above the tabs on every tab of the Mix It Up page. Two small hashes, written fire-and-forget (a failed write never touches the request). `mixitup:seen`: field = incoming route (`/api/webhooks/*` only), value `{ okAt?, badAt? }`; `incomingSecretValid` sets `okAt` on a right secret and `badAt` on a non-empty wrong one (the other field is kept; a missing secret records nothing). `mixitup:out`: field = `balance | deduct | add | viewers`, value `{ at, ok, detail }`; `callMixItUp` records the last result by the payload's `action` (`ok` = Mix It Up answered 2xx, `detail` = `HTTP <status>` or the plain-words error; a `test` message is not recorded). The chips: when Mix It Up last reached the site and through which route (`!pack`, chat commands, show-off, card reward, collection, stream start/end), a warning for any route whose `badAt` is newer than its `okAt`, and one chip per address (not set / set, not used yet / working / failing with the reason; an empty deduct address shows "uses the balance address"). `healthChips` is the pure part.
- `/api/collection` is locked down by server-rolled pulls (docs/overlay.md, ROADMAP 13.1).

## TCG Bridge (site side)
ROADMAP 55.0. Mix It Up cannot answer an HTTP request with custom JSON, so the four outgoing addresses cannot work against stock Mix It Up. In **bridge mode** (the default for new settings) the site never calls Mix It Up: a desktop app on the stream PC, TCG Bridge (55.6), long-polls the site for jobs, runs them through Mix It Up's local Developer API and posts the results. `lib/bridge-core.ts` is pure (shapes, pair codes, token hashing, result to reply); `lib/bridge.ts` is the KV side; the routes are thin.
- **Settings**: `connection: 'bridge' | 'addresses'` and `currencyId` (the Mix It Up currency GUID; `currency` stays the display name, and the save copies it from the bridge's `hello` list). Settings saved with no `connection` read as `addresses` when any of the four addresses is set, else `bridge`, so an existing setup does not change. The Paid pulls form (`ConnectionSwitch`) shows either the currency select (filled from the last `hello`, "Pair TCG Bridge first" before one) or the four addresses, secret, balance field and currency name; both groups stay in the form so a save keeps the other mode's values. Switching on needs a currency in bridge mode and the balance address in addresses mode. `hasBalanceRoute / hasAddRoute / hasViewersRoute` (`mixitup-core.ts`) are the "is this possible" checks the buffs and the Try it buttons use.
- **Transport**: every outgoing call in `lib/mixitup.ts` goes through `callOut`, which is `callBridge` in bridge mode and `callMixItUp` otherwise; callers keep their logic and parse the same `Reply`. `callBridge` pushes a job (RPUSH `bridge:jobs`), then reads `bridge:result:<id>` every 250 ms for up to 8 s. No result is `ok: false`, "TCG Bridge did not answer", exactly like Mix It Up not answering, so a reservation is refused and released and nothing is charged. The balance is read from `balance` whatever the balance field says. Health (`noteOutgoing`) is noted as before. A sandbox or preview never creates a job. `bridgeSay(text)` queues a fire-and-forget `say` job; nothing calls it yet. The Try it "Send test message" sends a `say` job with the rendered message and waits, so the bridge must post a result for `say` too.
- **Jobs** (`bridge:jobs`, a list): `{ id, kind: 'balance' | 'deduct' | 'add' | 'viewers' | 'say' | 'obs-refresh' | 'run-command', username?, amount?, currencyId?, text?, commandId?, args?, at }`. `text` is the chat message of a deduct, or the line of a say; `commandId` and `args` are a `run-command` (below). A job older than 5 s is dropped when it is claimed (the waiter gives up after 8 s, so a claimed job has at least 3 s to run), as is anything malformed.
- **Results**: `POST /api/bridge/result` `{ id, ok, balance?, users?, error? }` writes `bridge:result:<id>` for 60 s. A `balance` result needs `balance` (a number, 0 or more), a `viewers` result needs `users` (strings, capped at 5000); `ok: false` carries `error`.
- **Late results**: when the waiter gives up (8 s) it writes `{ id, ok: false, error, late: true }` to `bridge:result:<id>` with NX, and a result that arrived first (the NX write fails) is used instead. The result route also writes with NX, so a result posted after the waiter gave up gets `409 { error, late: true }` and is dropped; a repeat of a stored result is a plain 200. The app's rule on a 409: for a `deduct` job it undoes the deduct (adds the amount back), for an `add` job it takes the amount back; `balance`, `viewers` and `say` need nothing. The site has already refused the pull (no print, allowance returned) or marked the grant unpaid, so this keeps the viewer from paying twice.
- **Endpoints** (Node, all POST JSON): `/api/bridge/pair` `{ code, name }` returns `{ token }` once; `/api/bridge/poll` `{ version? }` holds the request up to 25 s and returns `{ jobs }` (empty on timeout; LPOP is atomic, so a job reaches one poller; `maxDuration` 40); `/api/bridge/result`; `/api/bridge/hello` `{ version, currencies: [{ id, name }], commands?: [{ id, name }] }` (commands since 0.4.0; see Big pulls) answers `{ ok, channel, currencyId }` (the channel name from `CHANNEL_NAME` and the chosen currency's id, which the app's self-tests use; an older app ignores both); `/api/bridge/report` (55.6b, below).
- **OBS report** (ROADMAP 55.6b): `POST /api/bridge/report` takes `{ type: 'stream', live }` (the stream output started or stopped, and once when the app connects to OBS) and `{ type: 'obs', connected, scene, overlay: { found, inProgram, visible, sourceName } }`; anything else is a 400. A stream report goes through `setLiveFromBridge` (`lib/twitch-live.ts`): it calls `setLiveFromHint` only when it differs from the current `twitch:live:hint`, so a reconnect does not refresh the 5 minute override and Mix It Up's own stream webhook still works the same way. An OBS snapshot is validated by `cleanObs` (strings capped at 100) and stored with the time in `bridge:obs`; the overlay address and key are never sent, only the source's name. The Mix It Up page chip row and Admin > Settings > OBS Overlay > Connection show it through `obsChip`: "OBS: overlay visible in <scene>", "OBS: overlay not in the current scene (<scene>)", "OBS: overlay hidden in <scene>", "OBS: overlay source not found", or "OBS not connected" (the snapshot says so, or the last one is over 60 s old; the app resends an unchanged snapshot every 30 s). Nothing shows until a bridge has reported OBS once, so a setup that never turns OBS on sees no change.
- **Refresh overlay in OBS**: the Connection panel on Admin > Settings > OBS Overlay has a button (only when a bridge is paired) that queues an `obs-refresh` job (`refreshOverlayInObs`, waits like `callBridge`) and shows the answer in words: refreshed, or "OBS is switched off in TCG Bridge", "TCG Bridge is not connected to OBS", "The overlay browser source was not found in OBS", "TCG Bridge did not answer". `requireAdmin`, audited. It is the same as right-clicking the browser source and choosing Refresh cache of current page, which is needed after a deploy.
- **Auth**: every route but `pair` needs `Authorization: Bearer <token>`; the sha256 of the token must be a field of `bridge:tokens` (value `{ id, name, createdAt, lastSeen }`; the token itself is never stored). Unknown, missing or revoked is a 401. All routes call `limitWebhook` first; `pair` also allows 10 tries per address per 10 minutes. A poll notes `lastSeen` and `mixitup:bridge` at most every 10 s and ends with a 401 if its token is revoked meanwhile.
- **Pairing**: the TCG Bridge card on the Paid pulls tab makes a code (`createPairCodeAction`: `requireAdmin`, audited, shown as `ABCD-EFGH` with its expiry, never put in a URL). `bridge:pair:<code>` lasts 600 s and the delete is the claim, so a code works once. Paired bridges list with name, paired and last seen, and **Revoke** (`ArmedButton`, `revokeBridgeAction`, audited; revoked by the record's `id`, so no token or hash reaches the page).
- **KV keys**: `bridge:jobs`, `bridge:result:<id>`, `bridge:pair:<code>`, `bridge:tokens` (hash), `mixitup:bridge` (hash: `at`, `version`, `currencies`, `commands`; the health chip, the currency select and the Big pulls command select), `bridge:obs` (the last OBS snapshot with `at`).
- **Health row**: in bridge mode one chip replaces the four address chips: "TCG Bridge connected (...)" when `mixitup:bridge.at` is within 60 s, else "TCG Bridge not connected" (with the last seen time when there is one). The incoming chips stay.
- `scripts/check-bridge.mts` covers the settings default, pairing, auth, claiming, stale jobs, a fake bridge answering a reserve / charge / refund, the timeout and late results, the report route (shapes, caps, the live hint changing once) and the OBS chips.

## Big pulls (Mix It Up commands on big pulls)
ROADMAP 55.6d. A rule runs one of the streamer's own Mix It Up commands (a sound, lights, a chat line of Mix It Up's own) when a pull on stream is big. Page: the **Big pulls** card on the Paid pulls tab (`PullRules.tsx`; 55.7 will move it). Pure part `lib/pull-rules-core.ts` (`matchRule`, `cleanRulesInput`, `rulesFromForm`, `pullArgs`), firing in `firePullRules` (`lib/mixitup.ts`), the queue call `bridgeRunCommand` (`lib/bridge.ts`), actions in `mixitup-actions.ts`, `scripts/check-pull-rules.mts`.
- **Rules** live in the Mix It Up settings (`mixitup:settings`, `pullRules`): up to 10, each `{ id, on, when: { minRarity?, variants?, newToDex? }, commandId }`. There are none by default and a new rule starts switched on in the form. A pull meets a rule when it meets every condition that is set (`minRarity` = at least that many stars, 2 to 5, 1 star is every card so it is stored as nothing; `variants` = one of the ticked versions, none = any; `newToDex` = the viewer's first copy of that card). A rule with no condition meets every pull. **The first switched-on rule that matches runs and the rest are skipped.** The Paid pulls form does not carry the rules, so saving it keeps them; the settings are read through `normalizeRules`, which drops anything unusable.
- **Saving** (`savePullRulesAction`: `requireAdmin`, audited, `revalidatePath`): a command must be one of the ids TCG Bridge last reported (`mixitup:bridge.commands`); while that list is empty (the app is off for a moment) a rule may keep the command it already had but no new command is taken. Rarity must be 1 to 5, versions known, at most 10 rules, no repeated rule id. The card has one row per rule (rarity at least, run, versions, new to the dex, On, **Test**, **Delete**) plus an empty "Add a rule" row; a row with no command is skipped. With no command list the Run select says "Pair TCG Bridge to choose a command". **Test** queues the saved rule's command once with a made-up pull (`cheesyviewer`, Gouda Goat, Epic, Full Art Holo) and does not wait; **Delete** removes the saved rule and keeps no other edit on the form.
- **When it fires**: on the reveal. The overlay queues pulls in the browser and saves each one with `POST /api/collection` when it starts showing it, so the server-side moment is the save that claims a pull ticket, which is a few seconds BEFORE the card flips. So the command is held back to land on the flip: the overlay sends `revealInMs` (save to reveal, `at(R.reveal)` in `public/widget.js`, so it follows the style, speed and start delay), the route clamps it to 0..15000 (3000 when an old cached overlay sends none, `revealDelay` in `lib/pull-rules-core.ts`) and puts it in the job as `delayMs`; the Test button sends none. `POST /api/collection` calls `firePullRules` from the same `after()` as the `cardPulled` webhook, with the facts it already worked out for the activity event: the ticket's stars, the variant and `isNew` (no copy of that card before). So a pull saved without a ticket, a test-panel or "Don't save" pull (never saved), a refused or revoked paid pull and a webhook grant (`grant-card`) never fire, and a ticket works once, so a pull queues one job at most. A sandbox queues nothing and neither does a site with no paired bridge (checked with `listBridges`). The save never waits on it and a failure is swallowed.
- **The job**: `{ id, kind: 'run-command', commandId, args: [viewer, card name, rarity label, version label], delayMs?, at }`, at most 10 args of 200 characters. The app waits `max(0, min(delayMs, at + delayMs - now))` (at most 15 s, so time already spent in transit counts) before it runs the command, and a waiting `run-command` is handled apart from the job loop (`commandWait` in `bridge/src/jobs.ts`, `pollLoop` in `service.ts`) so a balance or deduct never queues behind a sound. It still posts its result when it has run; stopping the app cancels a wait. A 0.4.0 app from before this change ignores `delayMs` and runs at once. The site does not wait for a result (the app still posts one, which expires). A job older than 5 s is dropped when claimed, which is fine for fire and forget. TCG Bridge before 0.4.0 does not know the kind and ignores the job.
- **The command list**: since 0.4.0 the app sends `commands: [{ id, name }]` in `hello` (enabled Mix It Up commands with a name and a GUID id, at most 500, names cut at 100; `cleanHello` enforces the same) on start, every 5 minutes and when Mix It Up comes back. `storeHello` keeps it beside the currencies in `mixitup:bridge`; an older app sends none and the stored list stays.

## TCG Bridge app (the stream PC side)
ROADMAP 55.6a. `bridge/` is a small Windows app (Electron + TypeScript, its own `package.json`, app id `app.cheesytcg.bridge`) that sits in the tray on the stream PC, long-polls the site for jobs, runs them against Mix It Up's Developer API on `http://localhost:8911` and posts the results. It never fetches any address but the paired site and `localhost:8911`, and ignores job kinds it does not know. Since 0.2.0 (55.6b) it can also talk to OBS on the same PC; see "OBS in the app" below. Since 0.3.0 (55.6c) it also alerts, tests itself, can start Mix It Up and keeps a log; see "Reliability and self-help" below.
- **Install**: the TCG Bridge card on the Mix It Up page has **Download TCG Bridge** (the GitHub releases tagged `bridge-v*`). The installer is **not code-signed**: Windows SmartScreen shows "More info", then "Run anyway". Per-user install, no admin rights. It starts with Windows (on by default, a checkbox in the window) and, once paired, starts minimised in the tray.
- **Pair**: in the app type the site address (default `https://cheesytcg.app`) and the code from **Pair TCG Bridge** (ABCD-EFGH, works once, 10 minutes). The app sends the computer name as its name. The token is stored with Electron `safeStorage` (Windows encryption, tied to the Windows user) in the app's user data folder and never leaves the PC. **Unpair** in the app forgets it there; **Revoke** on the site makes the app show "Pair again".
- **Statuses**: tray icon green = site and Mix It Up both fine, amber = one of them, red = neither. The window shows Site (address, paired as, last poll, state: Connecting, Connected, Cannot reach the site, Pair again), Mix It Up (found, version, the currency the site last used) and the last 50 jobs with their results. "Mix It Up: No" means nothing answers on port 8911: Mix It Up is closed, or its Developer API is off (Mix It Up > Services > Developer API > Connect). The app checks every 5 s and sends `hello` (version, currencies) on start and each time Mix It Up comes back.
- **Loop**: after a normal answer the app polls again at once; after an error it backs off 1 s, doubling to 30 s. A 401 anywhere stops the loop ("Pair again"). A result is posted with up to 3 quick retries (network error or 5xx). A 409 `late` means the site gave up on the job: a `deduct` that went through is given back, an `add` is taken back, the others need nothing. Mix It Up not running answers each job "Mix It Up is not running" at once.
- **Jobs to Mix It Up** (V1 Developer API, PascalCase JSON; `username` is lowercased and must be a Twitch login, `currencyId` a GUID): `balance` = `GET /api/users/twitch/{name}`, the `CurrencyAmounts` entry with that `ID` (404 = 0). `deduct` = the same lookup, refused with "Not enough <currency>" when the balance is short (never negative), then `PUT /api/users/{user ID}/currency/{currencyId}/adjust` `{ "Amount": -n }`; the user ID from the lookup is used because that route resolves a name on the streamer's default platform, not necessarily Twitch. After a good deduct the job's `text` is posted to chat. `add` = the same adjust with `+n` (a viewer Mix It Up does not know is refused). `viewers` = `GET /api/chat/users`, the users with a `TwitchID`, lowercased and deduped. `say` = `POST /api/chat/message` `{ "Message", "SendAsStreamer": false }`. `hello` currencies = `GET /api/currency` (`ID`, `Name`); the version = `GET /api/status/version`.
- **Updates**: `electron-updater` checks the latest GitHub release on start (in the start-up window, installed at once) and every 6 hours (installed on quit). To release: bump `version` in `bridge/package.json`, merge, push the tag `bridge-v<version>`; `.github/workflows/bridge.yml` builds on `windows-latest` and attaches the installer, its blockmap and `latest.yml` to a release of that tag. The updater reads the repo's latest non-prerelease, so every full release in this repo must be a bridge release (mark anything else a pre-release). The window shows the app version and a **Check for updates** button (answers "You are up to date", "Downloading version x.y.z" or "Version x.y.z is ready ... (restart to update)"; only in the installed app). The last version the window saw is kept in the settings; after an update the window shows "Updated to x.y.z" with **See what changed** (opens `https://github.com/JoshMiles/tcg/releases/tag/bridge-vx.y.z` in the default browser) and **Dismiss**, until one of them is used. The first run ever says nothing.
- **OBS in the app** (0.2.0, ROADMAP 55.6b; `bridge/src/obs.ts`, no Electron imports): off by default. The window's OBS card has a "Talk to OBS" switch, the address (default `ws://127.0.0.1:4455`; only `ws://localhost:<port>` or `ws://127.0.0.1:<port>` is accepted) and the password, which is stored with `safeStorage` like the token and never sent to the site. In OBS (28 or newer) it is Tools > WebSocket Server Settings > Enable WebSocket server, Server Password (leave the app's field empty if authentication is off). While on, the watcher uses obs-websocket v5 (JSON subprotocol) and reconnects with a 1 s to 30 s backoff; the window shows connected or why not ("Wrong OBS WebSocket password", "OBS is not running, or its WebSocket server is switched off"), the program scene, the stream state and the overlay check. The tray goes amber when OBS is on but not connected; OBS off does not count.
  - **Requests**: `GetStreamStatus`, `GetCurrentProgramScene`, `GetInputList` (`inputKind: browser_source`), `GetInputSettings`, `GetSceneItemList`, `GetGroupSceneItemList` and, for the refresh, `PressInputPropertiesButton` (`propertyName: refreshnocache`). **Events** (subscriptions Scenes, Inputs, Outputs, SceneItems): `StreamStateChanged` (only `OBS_WEBSOCKET_OUTPUT_STARTED` and `..._STOPPED` count), `CurrentProgramSceneChanged`, `SceneItemEnableStateChanged`, `InputSettingsChanged`, `InputCreated`, `InputRemoved`, `InputNameChanged`; the last six trigger a re-check after a 1 s debounce.
  - **The overlay check**: a browser source is the overlay when its URL is on the paired site's host (a leading `www.` ignored) with the path `/overlay.html`; the key and other parameters are ignored and never sent. It counts as in the program when it is an item of the current scene, or of a group in it (one level), and as visible when the item (and its group) is enabled. If several sources match, a visible one in the scene is reported. **Not seen**: an overlay inside a nested scene (a scene used as a source) counts as not in the scene.
  - **Reports** (`POST /api/bridge/report`, see above): `stream` when the output starts or stops and once on connect; `obs` on connect, on disconnect, on any change, at most once a second, and unchanged every 30 s as a heartbeat. Turning OBS off in the app or quitting sends a disconnected snapshot. A failed report is not retried; the next change or heartbeat tells the site.
  - **The `obs-refresh` job** presses "Refresh cache of current page" on every matching browser source and answers `ok`, or `ok: false` with a reason in words when OBS is off, not connected, or no overlay source exists. It gives up after 4 s.
- **Mix It Up commands** (0.4.0, ROADMAP 55.6d): `GET /api/commands` (`CommandV1Controller`, route `api/commands`) lists `[{ ID, Name, IsEnabled, Category, GroupName }]`; the app keeps the enabled, named ones and sends `{ id, name }` in `hello`. A `run-command` job is `POST /api/commands/{id}` with a JSON array of strings as the body (the command's arguments, `$arg1text` to `$arg4text`); Mix It Up queues the command and answers 200 at once. The app runs a `run-command` only for an id it reported itself in the last `hello` (case-insensitive) and answers anything else, a bad id or a missing one with "That Mix It Up command is not in the list this app reported"; non-string args are dropped. If the list cannot be read the last good one is kept. A site that sends a kind an older app does not know is skipped without an answer; the kinds are fixed.
- **Reliability and self-help** (0.3.0, ROADMAP 55.6c; plain modules `alerts.ts`, `selftest.ts`, `launch.ts`, `log.ts`, `diagnostics.ts`, `update.ts`; `main.ts` only wires them):
  - **Alerts**: a Windows notification when the site link, Mix It Up or OBS goes from up to down, and one when it comes back. A part counts as down only after 15 s down, so a missed poll never alerts; at most one drop alert per part every 2 minutes (a drop inside that time is shown once the 2 minutes pass, if it is still down); the "back" notice only follows a drop that was shown. Only while the stream is live: "live" is what OBS last said (kept if OBS is then lost; OBS never connected counts as not live). With OBS switched off in the app there is no live signal, so every drop alerts. A part that never came up since the app started, or a revoked site, is not a drop. The window's "Alert me when a link drops while live" switch (saved, on by default) only mutes the notification; the log still records the alert. The decision is the pure `Alerts` class, fed snapshots and a clock.
  - **Self-tests** (each answers in words next to its button): **Test Mix It Up** checks the Developer API answers (and its version), finds the currency the site chose by id and reads its name, then reads the balance of a Twitch name (the box is prefilled with the channel name from the `hello` answer; a viewer Mix It Up does not know has 0). **Send test chat message** posts "TCG Bridge test message" through `/api/chat/message`. **Check OBS** runs the overlay check now and shows the scene, the stream state and the overlay, or why it cannot (OBS off, not connected).
  - **Start Mix It Up**: when Mix It Up is not found the Mix It Up card shows **Start Mix It Up**. It launches only the saved path, else the default `%LocalAppData%\MixItUp\MixItUp.exe` (where Mix It Up's own installer puts it: `MixItUp.Installer/MainWindowViewModel.cs`, `DefaultInstallDirectory`, in github.com/MixItUpBot/Desktop), and only an existing file named `MixItUp.exe`, detached, with no shell. **Choose MixItUp.exe...** opens a file dialog and saves the path (refused unless the file is called `MixItUp.exe`). **Start Mix It Up with TCG Bridge** (off by default) starts it when the app starts and nothing answers on port 8911.
  - **Diagnostics**: one log file a day in the app's logs folder (`bridge-YYYY-MM-DD.log` under Electron's `logs` path), files older than 7 days deleted on start. It records starts, pairing, the site, Mix It Up and OBS going up or down, each job (kind, ok, error, ms), alerts and errors. Every line goes through `Logger.log()`, which first removes the pairing token, the OBS password and the pair code (remembered while the app runs) and then, by pattern, overlay addresses, `Bearer` values and `key=`, `secret=`, `token=` and `password=` values. **Open log folder** opens it; **Copy diagnostics** puts on the clipboard the app, Electron and Windows versions, the statuses and the last 20 jobs as plain text, through the same redaction.
  - New IPC channels, all with fixed names in `preload.ts` and validated in `main.ts`: `alerts`, `test-mix` (the name must be a Twitch login), `test-chat`, `test-obs`, `start-mix`, `choose-mix`, `start-mix-with-bridge`, `open-logs`, `copy-diagnostics`, `check-update`, `open-release` (the address is built in the main process from the app version), `dismiss-updated`.
- **Look and start-up updater** (0.5.0, ROADMAP 55.6e; `bridge/src/startup.ts`, no Electron imports; `main.ts` wires it to `electron-updater`): every start opens a small frameless start-up window first (`renderer/splash.*`, its own sandboxed preload `splash-preload.ts` that can only listen), also when Windows starts the app minimised (it then leaves only the tray). The `Startup` state machine is fed the updater events and a clock: "Checking for updates", then "Downloading update x.y.z" with a bar, then "Installing update" (`quitAndInstall(true, true)`, so the app restarts by itself) or "Starting". No internet, or no answer after 8 s: it starts and the main window shows "Couldn't check for updates" (dismissible). A failed or stalled (30 s) download starts the current version and the 6-hour check tries again. An update found after the hand-over is never installed at start-up: it only sets "Version x.y.z is ready ... (restart to update)". In development (`npm start`) there is no check. The main window is frameless with its own minimise and close-to-tray buttons (quit stays in the tray menu), a rail (Status, Settings, About) and a card per link (Site, Mix It Up, OBS) with a status dot and a one-line state; the renderer is still plain HTML, CSS and JS, with Fredoka and Nunito bundled locally (SIL OFL) and Lucide icons inline (`renderer/LICENSES.txt`). The app icon and the three tray PNGs are drawn by `npm run icons` from `build/icon.svg` and `build/tray.svg`; tray states differ by badge shape (dot, half ring, cross) as well as colour. Dev only: `npm start -- --demo-startup [--shots=<folder>]` (`src/demo.ts`, excluded from the installer).
- **Checks**: `bridge/scripts/check.ts` (a fake Mix It Up, a fake obs-websocket v5 server in `bridge/scripts/fake-obs.ts` and a fake site on local ports; `cd bridge && npm run check`). It also covers the start-up state machine with fake events (no update, update with progress, offline, slow check, failed download, late update) and the alert rules with a fake clock, the self-tests, the launcher (a fake `spawn`), log pruning, and greps the log file and the diagnostics text for the token, the OBS password, the overlay key and the pair code, failing if any appears. `scripts/check-bridge-app.mts` runs it with the root checks (and prints `skipped:` when `bridge/` has no `node_modules`, as in the root CI job), and the workflow typechecks and runs it on pull requests that touch `bridge/`. The root `tsconfig.json` excludes `bridge/`. Not run against a real OBS.

## Webhook grants look like pulls
The incoming webhooks only accept a real Twitch login as `username` (3 to 25 letters, digits and underscores; a leading `@` is dropped; anything else is a 400), and the grant-card webhook only grants a card number that exists in a published pack of the active season (404 otherwise), so a bad Mix It Up variable fails loudly instead of creating a ghost viewer.

A card granted by the grant-card webhook (a Mix It Up reward) is recorded as `grant` with `source: 'webhook'` plus the facts of a pull (name, stars, pack, new or not, copies, collected, edition). It counts as a **pull** in the Live Activity categories and the Discord Pulls category (with the star and new-only filters), reads "X pulled Y (granted by webhook)" in the live feed and on the dashboard's Recent activity, and posts the same embed as a pull with a "Granted by webhook" line (`pullEmbed` in `lib/discord.ts`). The Live Activity numbers, the stream recap (`asPullEvent` in `lib/activity-view.ts`; there it is listed as a reward rather than a pack opened) and the stats counters behind the weekly digest and the dashboard charts (`recordStats`, from the day this shipped) count it as a pull too. Admin grants are unchanged (Grants & removals, the Cards Discord category, the `grant` counter). Events recorded before this change lack the extra facts and still post, with the card's stars looked up.

## Mix It Up chat commands (Mix It Up page, Commands tab)
ROADMAP 19.2. One incoming webhook, `POST /api/webhooks/command` (`{ secret, command, username, args? }`, the incoming secret), answers every chat command: `{ ok, message, vars }` plus each variable at the top level for Mix It Up's "JSON to special identifiers". A refusal is `{ ok: false, message }` with the command's own error text; an unknown or switched-off command is `{ ok: false, message: '' }` (silent). `/api/webhooks/show-card` still works unchanged.
- **Pure core** `lib/commands-core.ts`: the `ChatCommand` shape, the fixed action registry `COMMAND_ACTIONS` (each action's variables, sample values and error kinds: `showoff`, `card-stats`, `my-stats`, `collection`, `leaderboard`, `pulls-left`, `text`), `matchCommand` (name or alias, without the `!`), `interpolate` (unknown placeholders dropped), `tidyReply` (no Markdown marks, 400 characters), `cleanCommands` (max 30, unique names). **KV** `lib/commands.ts`: commands in `mixitup:commands` (the defaults `!showoff` and `!stats` are seeded on first read), run counts in `mixitup:cmdstats`, the last 20 runs in `mixitup:cmdlog` (shown on the Log tab, never posted to Discord), cooldowns `cmd:cd:<id>` and `cmd:ucd:<id>:<viewer>` with a TTL. `runCommand` is used by the webhook and by Try it.
- **Dry run**: Try it (the builder) runs the editor's draft with `dry`: no overlay event, no cooldown spent, no log line. `showoff` calls `prepareShowOff(user, args, { dry })`. A sandbox never queues an overlay event either.
- **Privacy**: hidden and private collectors (`getHiddenUsers`) show as "a private collector" in `topHolder` / `firstPulledBy`, are left out of `collectors`, and `my-stats` for them answers "This collector keeps their stats private" unless they ask about themselves.
- **FAQ**: the "Chat commands" section lists the enabled commands from `getCommands()`, then a fixed `!pack` line (it asks the stream to open a pack, and it is set up in Mix It Up rather than the command builder). `scripts/check-commands.mts` covers the builder. **Copy setup** (`commandSetups` in `lib/mixitup-setup.ts`) lists every switched-on command: the `!` name, `POST /api/webhooks/command`, the JSON body (the real incoming secret, `$username`, `$allargs`) and the `message` field for the Chat Message.

**Stream start / end** (`POST /api/webhooks/stream`, `{ secret, event: 'live' | 'offline' }`, the incoming secret): wire Mix It Up's Stream Start and Stream End events to it. `setLiveFromHint` (`lib/twitch-live.ts`) marks the stream live or offline at once (System notice, stream-start marker, recap on offline) and stores `twitch:live:hint`; for 5 minutes a Helix answer that disagrees is overridden, since Twitch's API lags a stream's start and end. The minute cron keeps checking Helix as a fallback.
