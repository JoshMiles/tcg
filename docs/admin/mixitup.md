# Mix It Up

> Read this when you touch paid pulls, webhook grants or Mix It Up chat commands.

## The Mix It Up page, tab by tab
ROADMAP 55.7. `/admin/mixitup` (`app/admin/mixitup/page.tsx`, `export const instant = false`) has seven tabs, in this order, selected by `?tab=`: **Overview** (default), **Connection**, **Paid pulls**, **Big pulls**, **Chat and Brie Bucks**, **Commands**, **Log**. The old `?tab=paid` link still opens Paid pulls. Every action keeps `requireAdmin`, `revalidatePath` and its audit line; the settings shape in KV is unchanged.
- **Overview** (`Overview.tsx`, `OverviewActions.tsx`, `overview-actions.ts`): three status cards (Incoming from Mix It Up, Outgoing to Mix It Up, OBS), each with a state, a few rows, and for anything not green a "What to do" line with a link to the fix. The cards are `statusCards` in `lib/mixitup-page.ts` (pure, `scripts/check-mixitup-page.mts`), built from the same health row, bridge row and OBS snapshot as the chips. A "Set up Mix It Up" button (to Connection) shows while any card is not green (`needsSetup`; a muted OBS card counts). **This stream** numbers come from the two request logs only (`streamNumbers`): paid pulls and currency taken (confirmed `deduct` lines), "Added back" (every `add` line, so refunds and Bonus Brie Bucks payouts together, they cannot be told apart), commands run, refusals with the most common reason. The request log keeps its last 50 lines and the command log its last 20, so when one is full and every line falls inside the window the numbers are lower bounds ("at least"). The window starts at `twitch:live:since` (that marker is deleted when the recap is handled) and falls back to the last 24 hours, labelled so. Nothing new is counted or stored. **Quick actions** show their answer inline: balance check (for the channel login), test chat message, refresh the overlay in OBS (only when a bridge is paired) and **This stream, everyone** extra pulls (`setStreamExtraAction`, the same buff as before). Then the last 5 log lines with "See all". The health chips are not shown here, the cards say the same.
- **Connection** (`ConnectionTab.tsx`): the TCG Bridge card (`BridgeCard`: download, pair code, paired apps, Revoke), the connection form (`saveConnectionAction`: `ConnectionSwitch` with the bridge or direct addresses, and the currency select in bridge mode; the direct addresses sit under a closed "Advanced: direct addresses" that opens by default only in addresses mode), the Copy setup block (`PaidPullSetup`, only with direct addresses) and **Try it** (check balance, send test message; they redirect back to this tab).
- **Paid pulls** (`MixItUpConfig.tsx`, `PaidPullFields.tsx`, `saveMixItUpAction`): the charging switch and how a pull goes, a Price and limits card (price, fallback limit, one limit per role, and a price for subscribers and for VIPs) and a Messages card (payment message with its preview, plus the editable chat replies, each an input showing today's text as its placeholder with a live preview from `renderReply` and `replySample` in `mixitup-core.ts`, which follow the price and fallback limit being typed). The form does not carry the connection or the rules, so saving it keeps them (`saveSettings` merges onto the stored settings).
- **Big pulls** (`PullRules.tsx`): the rules, see Big pulls below. Its actions redirect back to this tab.
- **Chat and Brie Bucks** (`ChatBucks.tsx`, `saveChatAction`): see Chat and Brie Bucks below.
- **Commands** (`CommandsPanel.tsx`): the chat command builder, see Mix It Up chat commands below.
- **Log** (`MixItUpLog.tsx`): the two logs merged, newest first, as `LogRows` (also used by Overview). Filters All, Incoming (chat commands), Outgoing (balance, deduct, add, test) and Refusals only (refused, revoked and failed commands) are URL params, `?tab=log&filter=<id>` (`pickLogFilter`, `filterLog`; anything unknown is All). Times show in the viewer's own time zone with "x ago" (`LocalTime.tsx`, UTC on the server render until it mounts).
- **Health chips** (below) sit above the tabs on every tab except Overview.

## Mix It Up paid pulls
Viewers can pay a currency (Brie Bucks) for a pack. Settings live in KV `mixitup:settings` (`lib/mixitup-core.ts`, pure; `lib/mixitup.ts`, KV and calls; the page is described above, actions in `mixitup-actions.ts`). Off by default; while off nothing below happens. Design and decisions: ROADMAP Track 12.
- **Flow**: `POST /api/webhooks/pull` reserves the pull (`reservePaidPull`: viewer's pulls this stream, then a `balance` request to Mix It Up, counting pulls already in flight) and queues it with `paid: true`. The overlay sends the event id back as the pull's ticket; `POST /api/collection` claims the ticket and then the payment (once each; a reused payment = 409, nothing saved), sends the `deduct` request with the custom message **before** the print is written (so the edition number is not known yet and `{serial}` is empty), and only then adds the print. If Mix It Up does not confirm, no print is made, the pull allowance comes back and the System Discord channel is told (`noticeUnpaid`); if the print then cannot be saved, the charge is paid back through the add address (`refundPaidPull`, the same call the currency-grant buff uses) and staff are told to refund by hand when that fails too. Refusals queue nothing and answer `{ ok: true, ignored: true, reason, message }` (`insufficient_balance | limit_reached | mixitup_unavailable | bad_balance`) so the Mix It Up command can post `message` to chat.
- **The direct addresses answer in the HTTP reply** (Mix It Up has no action that answers a request; there is no Webhook Response action, so use TCG Bridge or a service of your own). Balance: JSON with a number at the balance field. Deduct: any 2xx counts unless the body sets `ok`, `success` or `applied` to false.
- **Price per role** (ROADMAP 55.4b): `priceByRole` in `mixitup:settings` holds an optional whole-number price for `subscriber` and `vip` (the same `role` the pull webhook sends for limits). Blank or missing = the base `cost`; 0 = free. `pullPrice(settings, { role })` in `lib/mixitup-core.ts` is the one place a price is worked out (a viewer with several roles pays the lowest); its comment lists the full price order the later 55.4 items add to (pack price, else role price, else base; then happy hour; first free makes 0). `reservePaidPull` works the price out once and stores it as `amount` on `mixitup:pay:<id>`; the balance check, the deduct, the refund, `{cost}` in replies and the `balance` / `left` fields all use that stored price, so a settings change while a pack waits on the overlay changes nothing. A reservation from before has no price and is charged the current `cost`. A price of 0 skips the balance request and sends no `deduct`, but still counts toward the viewer's limit. In-flight pulls: `mixitup:pending:<viewer>` is now the sum of the prices in flight (it was a count), and `decide` compares the balance with that sum.
- **Happy hour** (ROADMAP 55.4c): KV `mixitup:happyhour` = `{ kind: 'discount', percent } | { kind: 'free' }, endsAt (ms), by`, a live state apart from `mixitup:settings` (`lib/happyhour.ts`; the pure shape, `activeHappyHour`, `cleanHappyHourInput` and the price step are in `lib/mixitup-core.ts`). It ends by time: the key's TTL matches `endsAt` and a read after `endsAt` counts as off, so there is no cron. `pullPrice(settings, { role, happyHour, now })` takes it as an argument (it stays pure) and applies it after the role price: discount = price x (100 - percent) / 100 rounded up to a whole number, free = 0. `reservePaidPull` reads it with `getHappyHour()` and stores the result as `amount`, so `{cost}` in replies shows the happy hour price and a happy hour ending while a pack waits on the overlay changes nothing; a free one skips the balance check and the deduct but still counts toward the limit. Start (minutes 1 to 240, free or discount, percent 1 to 99) and End now are in the Happy hour box at the top of the Paid pulls tab (`HappyHourBox.tsx`, `happyhour-actions.ts`, admin only); starting while one runs replaces it. Starting or ending, from the page or the Stream Deck, writes one audit entry (`everyone`) and so one post to the Discord admin log (`startHappyHour` / `endHappyHour`).
- **Limit per stream**: Paid pulls has a number for regular, subscriber, VIP, moderator and broadcaster (all 0, no limit, until staff change them). The old single `limit` is the fallback when a role has no number, so a save from before role limits keeps working. The pull webhook may send `role` (`regular | subscriber | vip | moderator | broadcaster`); missing or unknown counts as regular, and `CHANNEL_LOGIN` is always the broadcaster. The site does not ask Twitch which role someone is. A gifted sub earns a pack and does not change a limit. A viewer's own limit (`user:<name>:pulllimit`, user page → Admin tab → Pull limit) replaces the role, and their temporary bonuses still add (ROADMAP 12.4). A base of 0 stays unlimited. **This stream, everyone:** Set / Clear on the same tab stores `{ amount, streamKey, by, at }` at `pulls:stream-buff`. It adds for every viewer only while `currentStreamKey()` still matches, and amount 0 deletes it. Counter `mixitup:cnt:<stream>:<viewer>` where the stream is the live Twitch stream's start (`getLiveStatus`), else the UTC day. Raised on reserve, lowered when a reservation fails or a pull is revoked. In-flight pulls: `mixitup:pending:<viewer>`; reservation `mixitup:pay:<id>` (1 h).
- Gifts from the dashboard, the extension and sandboxes never charge. Addresses are saved through `checkWebhookUrl` (public https only) and every call goes through `sendWebhook` (`lib/webhook-send.ts`: see ux-conventions, outgoing webhook addresses; an http address saved earlier still sends, a localhost one never does, so Mix It Up on the streamer's own machine needs an https tunnel); the last 50 requests (out and in) are in KV `mixitup:log` and shown on the Log tab. `scripts/check-mixitup.mts` covers it with a fake Mix It Up. **Copy setup** (`paidPullSetup` in `lib/mixitup-setup.ts`) shows the balance and deduct bodies from the saved settings, the addresses, which action should answer `{ "balance": n }` (the saved balance field), and which action takes the currency. An empty deduct address is the balance address, told apart by `action`.
- **Add address** (`addUrl`, optional): the Mix It Up command that gives currency, used only by the `currency-grant` buff (Buff Editor). `grantCurrency` in `lib/mixitup.ts` sends `{ action: 'add', secret, username, amount, currency }` and, like a deduct, counts a 2xx unless the body sets `ok`, `success` or `applied` to false; it is logged as `add`. **Chat viewers address** (`viewersUrl`, optional): answers `{ users: string[] }` (or a bare array); `fetchChatViewers` sends `{ action: 'viewers', secret, currency }`, lowercases, drops @, dedupes and caps at 5000. Community `score-bonus` and `currency-grant` buffs go to those viewers (players with no cards included, who have no leaderboard row until they pull) and fail with a clear error when Mix It Up is off, the address is empty, or the call fails. A `currency-grant` writes a record `buffgrant:<id>` first (user to pending/paid/failed), pays one viewer at a time saving after each, and never pays a viewer marked paid; unpaid grants are listed in `buffgrants:open` and shown on the Buff Editor with **Retry unpaid** (`runGrant`, `retryGrantAction`). The trigger (card) is spent once; a partial result tells the player some are unpaid. The buff refuses to apply (and the Buff Editor warns) while Mix It Up is off or `addUrl` is empty; sandboxes never call it.
- **Connection health** (`lib/mixitup-health.ts`, `scripts/check-mixitup-health.mts`): a chip row above the tabs on every tab of the Mix It Up page except Overview (its status cards use the same data). Two small hashes, written fire-and-forget (a failed write never touches the request). `mixitup:seen`: field = incoming route (`/api/webhooks/*` only), value `{ okAt?, badAt? }`; `incomingSecretValid` sets `okAt` on a right secret and `badAt` on a non-empty wrong one (the other field is kept; a missing secret records nothing). `mixitup:out`: field = `balance | deduct | add | viewers`, value `{ at, ok, detail }`; `callMixItUp` records the last result by the payload's `action` (`ok` = Mix It Up answered 2xx, `detail` = `HTTP <status>` or the plain-words error; a `test` message is not recorded). The chips: when Mix It Up last reached the site and through which route (`!pack`, chat commands, show-off, card reward, collection, stream start/end), a warning for any route whose `badAt` is newer than its `okAt`, and one chip per address (not set / set, not used yet / working / failing with the reason; an empty deduct address shows "uses the balance address"). `healthChips` is the pure part.
- `/api/collection` is locked down by server-rolled pulls (docs/overlay.md, ROADMAP 13.1).

## Replies and the request log (ROADMAP 55.3)
Every incoming route answers JSON with a `message` a Mix It Up Chat Message can say. Existing keys are unchanged.
- **`/api/webhooks/pull`**: queued `{ ok: true, message: "Opening a pack for <name>", left?, balance? }`. `left` = paid pulls left this stream after this one (only when the viewer has a limit); `balance` = what Mix It Up said just before (the price is taken when the pack is revealed). Neither is there for a free pull or an extra-pack credit; no extra Mix It Up call is made to learn them. Refused `{ ok: true, ignored: true, reason, message, balance? }` (`insufficient_balance | limit_reached | mixitup_unavailable | bad_balance | blocked | paused | no_packs`, or the live gate's text with an empty `message`).
- **Editable replies** (ROADMAP 55.4a): `replies` in `mixitup:settings`, one optional text per key of `REPLY_DEFAULTS` in `lib/mixitup-core.ts`: `queued`, `insufficient_balance`, `limit_reached`, `mixitup_unavailable`, `no_packs`. That table is also where today's text lives; a key that is missing or blank uses it, so a save from before keeps working. A new reply is one more entry there plus a label. `renderReply(template, values)` fills `{username}`, `{cost}`, `{currency}`, `{balance}`, `{limit}` and `{left}`, drops a placeholder that has no value (a free pull has no `{left}`) and the double space it leaves, and caps the text at 400 characters. The Paid pulls form posts `reply_<key>` fields (trimmed, 400 characters each; a blank field clears a saved text). Only `message` changes: `reason` and every other key of the answer are as before, and the texts that were already empty (the live gate) or fixed (`bad_balance`, `blocked`, `paused`) are not editable. Checks: `scripts/check-mixitup.mts` (pure), `scripts/check-two-way.mts` (a saved text comes back from `/api/webhooks/pull`).
- **`grant-card`**: `{ ok: true, username, cardNumber, variant, message: "<name> got <card>" }`; errors (400, 404) `{ error, message }`. **`collection`**: `{ ok: true, message }`, or ignored with `message: ''`. **`stream`**: `{ ok: true, live, message }`. **`show-card`**, **`command`**, **`buff`** already answered with `message`. A wrong secret (401) or bad username (400) is `{ error, message }`.
- **`requestId`** (optional, on `pull`, `grant-card`, `buff`; `lib/webhook-reply.ts`): the first request claims `webhook:req:<route>:<id>` with SET NX (10 minutes), runs, and stores its status and body; a repeat inside 10 minutes answers that stored result and does nothing (a repeat arriving while the first still runs waits up to 3 s, then answers "already being handled"). If the first request throws the claim is dropped. No `requestId` always runs. The `!pack` and Stream Deck cards and files send `"requestId": "$randomnumber1:2000000000"` (`REQUEST_ID` in `lib/mixitup-setup.ts`): in Mix It Up's source `$randomnumber<min>:<max>` is drawn again every time a command reads it (`SpecialIdentifierStringBuilder`), so it differs per run; a duplicate is a 1 in 2 billion chance. Never a fixed word, which would ignore every request after the first.
- **Log tab**: each request on those three routes adds a `pull`, `grant` or `buff` line to the Mix It Up log (viewer, result, `reason: message` for a refusal, "repeat of an earlier request" for a replay). The log keeps the last 50 lines (incoming and outgoing together), never goes to Discord, and the Incoming and Refusals filters include the new lines.
- **Outgoing calls** time out after 5 seconds; the Log tab and the connection chip say "Mix It Up did not answer in 5 seconds". If the balance address fails 3 times in a row while the stream is live, the System Discord channel gets one "Mix It Up is not answering" post (`watchBalance` in `lib/mixitup-health.ts`; counter `mixitup:balance-fails`, one post per streak, a success resets both). In bridge mode a missing answer shows "TCG Bridge did not answer" after 8 s instead.
- Check: `scripts/check-two-way.mts`.

## TCG Bridge (site side)
ROADMAP 55.0. Mix It Up cannot answer an HTTP request with custom JSON, so the four outgoing addresses cannot work against stock Mix It Up. In **bridge mode** (the default for new settings) the site never calls Mix It Up: a desktop app on the stream PC, TCG Bridge (55.6), long-polls the site for jobs, runs them through Mix It Up's local Developer API and posts the results. `lib/bridge-core.ts` is pure (shapes, pair codes, token hashing, result to reply); `lib/bridge.ts` is the KV side; the routes are thin.
- **Settings**: `connection: 'bridge' | 'addresses'` and `currencyId` (the Mix It Up currency GUID; `currency` stays the display name, and the save copies it from the bridge's `hello` list). Settings saved with no `connection` read as `addresses` when any of the four addresses is set, else `bridge`, so an existing setup does not change. The Connection tab's form (`ConnectionSwitch`) shows either the currency select (filled from the last `hello`, "Pair TCG Bridge first" before one) or the four addresses, secret, balance field and currency name; both groups stay in the form so a save keeps the other mode's values. Switching on needs a currency in bridge mode and the balance address in addresses mode. `hasBalanceRoute / hasAddRoute / hasViewersRoute` (`mixitup-core.ts`) are the "is this possible" checks the buffs and the Try it buttons use.
- **Transport**: every outgoing call in `lib/mixitup.ts` goes through `callOut`, which is `callBridge` in bridge mode and `callMixItUp` otherwise; callers keep their logic and parse the same `Reply`. `callBridge` pushes a job (RPUSH `bridge:jobs`), then reads `bridge:result:<id>` every 250 ms for up to 8 s. No result is `ok: false`, "TCG Bridge did not answer", exactly like Mix It Up not answering, so a reservation is refused and released and nothing is charged. The balance is read from `balance` whatever the balance field says. Health (`noteOutgoing`) is noted as before. A sandbox or preview never creates a job. `bridgeSay(text)` queues a fire-and-forget `say` job (the stream start and end posts use it, see Chat and Brie Bucks). The Try it "Send test message" sends a `say` job with the rendered message and waits, so the bridge must post a result for `say` too.
- **Jobs** (`bridge:jobs`, a list): `{ id, kind: 'balance' | 'deduct' | 'add' | 'viewers' | 'say' | 'obs-refresh' | 'run-command' | 'pull-event' | 'backup' | 'ledger', username?, amount?, currencyId?, text?, commandId?, args?, phase?, at }`. `text` is the chat message of a deduct, or the line of a say; `commandId` and `args` are a `run-command` (below). A job older than 5 s is dropped when it is claimed (the waiter gives up after 8 s, so a claimed job has at least 3 s to run), as is anything malformed.
- **Results**: `POST /api/bridge/result` `{ id, ok, balance?, users?, error? }` writes `bridge:result:<id>` for 60 s. A `balance` result needs `balance` (a number, 0 or more), a `viewers` result needs `users` (strings, capped at 5000); `ok: false` carries `error`.
- **Late results**: when the waiter gives up (8 s) it writes `{ id, ok: false, error, late: true }` to `bridge:result:<id>` with NX, and a result that arrived first (the NX write fails) is used instead. The result route also writes with NX, so a result posted after the waiter gave up gets `409 { error, late: true }` and is dropped; a repeat of a stored result is a plain 200. The app's rule on a 409: for a `deduct` job it undoes the deduct (adds the amount back), for an `add` job it takes the amount back; `balance`, `viewers` and `say` need nothing. The site has already refused the pull (no print, allowance returned) or marked the grant unpaid, so this keeps the viewer from paying twice.
- **Endpoints** (Node, all POST JSON): `/api/bridge/pair` `{ code, name }` returns `{ token }` once; `/api/bridge/poll` `{ version? }` holds the request up to 25 s and returns `{ jobs }` (empty on timeout; LPOP is atomic, so a job reaches one poller; `maxDuration` 40); `/api/bridge/result`; `/api/bridge/hello` `{ version, currencies: [{ id, name }], commands?: [{ id, name }] }` (commands since 0.4.0; see Big pulls) answers `{ ok, channel, currencyId }` (the channel name from `CHANNEL_NAME` and the chosen currency's id, which the app's self-tests use; an older app ignores both); `/api/bridge/report` (55.6b, below).
- **OBS report** (ROADMAP 55.6b): `POST /api/bridge/report` takes `{ type: 'stream', live }` (the stream output started or stopped, and once when the app connects to OBS) and `{ type: 'obs', connected, scene, overlay: { found, inProgram, visible, sourceName } }`; anything else is a 400. A stream report goes through `setLiveFromBridge` (`lib/twitch-live.ts`): it calls `setLiveFromHint` only when it differs from the current `twitch:live:hint`, so a reconnect does not refresh the 5 minute override and Mix It Up's own stream webhook still works the same way. An OBS snapshot is validated by `cleanObs` (strings capped at 100) and stored with the time in `bridge:obs`; the overlay address and key are never sent, only the source's name. The Mix It Up page chip row and Admin > Settings > OBS Overlay > Connection show it through `obsChip`: "OBS: overlay visible in <scene>", "OBS: overlay not in the current scene (<scene>)", "OBS: overlay hidden in <scene>", "OBS: overlay source not found", or "OBS not connected" (the snapshot says so, or the last one is over 60 s old; the app resends an unchanged snapshot every 30 s). Nothing shows until a bridge has reported OBS once, so a setup that never turns OBS on sees no change.
- **Refresh overlay in OBS**: the Connection panel on Admin > Settings > OBS Overlay has a button (only when a bridge is paired) that queues an `obs-refresh` job (`refreshOverlayInObs`, waits like `callBridge`) and shows the answer in words: refreshed, or "OBS is switched off in TCG Bridge", "TCG Bridge is not connected to OBS", "The overlay browser source was not found in OBS", "TCG Bridge did not answer". `requireAdmin`, audited. It is the same as right-clicking the browser source and choosing Refresh cache of current page, which is needed after a deploy.
- **Auth**: every route but `pair` needs `Authorization: Bearer <token>`; the sha256 of the token must be a field of `bridge:tokens` (value `{ id, name, createdAt, lastSeen, by?, staff? }` (`by` = the admin who paired it, `staff` = the per-PC staff switch, off by default); the token itself is never stored). Unknown, missing or revoked is a 401. All routes call `limitWebhook` first; `pair` also allows 10 tries per address per 10 minutes. A poll notes `lastSeen` and `mixitup:bridge` at most every 10 s and ends with a 401 if its token is revoked meanwhile.
- **Pairing**: the TCG Bridge card on the Connection tab makes a code (`createPairCodeAction`: `requireAdmin`, audited, shown as `ABCD-EFGH` with its expiry, never put in a URL). `bridge:pair:<code>` lasts 600 s and the delete is the claim, so a code works once. Paired bridges list with name, paired and last seen, and **Revoke** (`ArmedButton`, `revokeBridgeAction`, audited; revoked by the record's `id`, so no token or hash reaches the page).
- **KV keys**: `bridge:jobs`, `bridge:result:<id>`, `bridge:pair:<code>`, `bridge:tokens` (hash), `mixitup:bridge` (hash: `at`, `version`, `currencies`, `commands`; the health chip, the currency select and the Big pulls command select), `bridge:obs` (the last OBS snapshot with `at`).
- **Health row**: in bridge mode one chip replaces the four address chips: "TCG Bridge connected (...)" when `mixitup:bridge.at` is within 60 s, else "TCG Bridge not connected" (with the last seen time when there is one). The incoming chips stay.
- `scripts/check-bridge.mts` covers the settings default, pairing, auth, claiming, stale jobs, a fake bridge answering a reserve / charge / refund, the timeout and late results, the report route (shapes, caps, the live hint changing once) and the OBS chips.

## Big pulls (Mix It Up commands on big pulls)
ROADMAP 55.6d. A rule runs one of the streamer's own Mix It Up commands (a sound, lights, a chat line of Mix It Up's own) when a pull on stream is big. Page: the **Big pulls** tab (`PullRules.tsx`). Pure part `lib/pull-rules-core.ts` (`matchRule`, `cleanRulesInput`, `rulesFromForm`, `pullArgs`), firing in `firePullRules` (`lib/mixitup.ts`), the queue call `bridgeRunCommand` (`lib/bridge.ts`), actions in `mixitup-actions.ts`, `scripts/check-pull-rules.mts`.
- **Rules** live in the Mix It Up settings (`mixitup:settings`, `pullRules`): up to 10, each `{ id, on, when: { minRarity?, variants?, newToDex? }, commandId }`. There are none by default and a new rule starts switched on in the form. A pull meets a rule when it meets every condition that is set (`minRarity` = at least that many stars, 2 to 5, 1 star is every card so it is stored as nothing; `variants` = one of the ticked versions, none = any; `newToDex` = the viewer's first copy of that card). A rule with no condition meets every pull. **The first switched-on rule that matches runs and the rest are skipped.** The Paid pulls form does not carry the rules, so saving it keeps them; the settings are read through `normalizeRules`, which drops anything unusable.
- **Saving** (`savePullRulesAction`: `requireAdmin`, audited, `revalidatePath`): a command must be one of the ids TCG Bridge last reported (`mixitup:bridge.commands`); while that list is empty (the app is off for a moment) a rule may keep the command it already had but no new command is taken. Rarity must be 1 to 5, versions known, at most 10 rules, no repeated rule id. The card has one row per rule (rarity at least, run, versions, new to the dex, On, **Test**, **Delete**) plus an empty "Add a rule" row; a row with no command is skipped. With no command list the Run select says "Pair TCG Bridge to choose a command". **Test** queues the saved rule's command once with a made-up pull (`cheesyviewer`, Gouda Goat, Epic, Full Art Holo) and does not wait; **Delete** removes the saved rule and keeps no other edit on the form.
- **When it fires**: on the reveal. The overlay queues pulls in the browser and saves each one with `POST /api/collection` when it starts showing it, so the server-side moment is the save that claims a pull ticket, which is a few seconds BEFORE the card flips. So the command is held back to land on the flip: the overlay sends `revealInMs` (save to reveal, `at(R.reveal)` in `public/widget.js`, so it follows the style, speed and start delay), the route clamps it to 0..15000 (3000 when an old cached overlay sends none, `revealDelay` in `lib/pull-rules-core.ts`) and puts it in the job as `delayMs`; the Test button sends none. `POST /api/collection` calls `firePullRules` from the same `after()` as the `cardPulled` webhook, with the facts it already worked out for the activity event: the ticket's stars, the variant and `isNew` (no copy of that card before). So a pull saved without a ticket, a test-panel or "Don't save" pull (never saved), a refused or revoked paid pull and a webhook grant (`grant-card`) never fire, and a ticket works once, so a pull queues one job at most. A sandbox queues nothing and neither does a site with no paired bridge (checked with `listBridges`). The save never waits on it and a failure is swallowed.
- **The job**: `{ id, kind: 'run-command', commandId, args: [viewer, card name, rarity label, version label], delayMs?, at }`, at most 10 args of 200 characters. The app waits `max(0, min(delayMs, at + delayMs - now))` (at most 15 s, so time already spent in transit counts) before it runs the command, and a waiting `run-command` is handled apart from the job loop (`commandWait` in `bridge/src/jobs.ts`, `pollLoop` in `service.ts`) so a balance or deduct never queues behind a sound. It still posts its result when it has run; stopping the app cancels a wait. A 0.4.0 app from before this change ignores `delayMs` and runs at once. The site does not wait for a result (the app still posts one, which expires). A job older than 5 s is dropped when claimed, which is fine for fire and forget. TCG Bridge before 0.4.0 does not know the kind and ignores the job.
- **The command list**: since 0.4.0 the app sends `commands: [{ id, name }]` in `hello` (enabled Mix It Up commands with a name and a GUID id, at most 500, names cut at 100; `cleanHello` enforces the same) on start, every 5 minutes and when Mix It Up comes back. `storeHello` keeps it beside the currencies in `mixitup:bridge`; an older app sends none and the stored list stays.

### OBS actions on big pulls
ROADMAP 55.8, TCG Bridge 0.6.0. A rule can also act in OBS (all optional, all off until chosen; a rule may have only OBS actions and no command): **Save a clip**, **Switch scene** (to a chosen scene for N seconds, default 8, at most 60, then back) and **Show a source** (while the pack opens, hidden again at the reveal). Scene and source names are picked from the lists the app reports with each OBS snapshot (`scenes`, and `sources` = the items of the scene on air, overlay sources left out, capped at 100 and 200), and `cleanRulesInput` refuses any other name; the job carries only a name and the app checks it against its own last-read list again.
- **Timing**: `POST /api/collection` (the save, when the card starts to show) returns an `eventId`. `firePullRules(pull, delay, eventId)` runs the Mix It Up command as before (queued at save time with `delayMs`, left alone) and `bridgePullStart` queues a fire-and-forget `pull-event` job `{ phase: 'start', source, holdMs }` and keeps the scene and clip part under `bridge:pullevent:<eventId>` (120 s). When the overlay reveals the card, `public/widget.js` posts `{ id, reveal: eventId }` to `/api/overlay/heartbeat` (overlay key as always; it records no heartbeat). The route claims the key (the `DEL` count, so a repeat queues nothing) and queues `{ phase: 'reveal', scene, secs, clip }`. An old overlay never reports, so only the source part runs. Nothing waits for a result; a failure shows only in the app's log.
- **In the app** (`ObsWatcher.showSource / switchScene / saveClip`): the source is enabled in the scene on air and disabled again after `holdMs`; the scene is changed and put back after N seconds only if nobody changed it meanwhile; a clip is `SaveReplayBuffer` 5 s after the reveal, and when the replay buffer is off the job answers `The OBS replay buffer is off, so no clip was saved`. The OBS card has a switch **Start the replay buffer when the stream starts** (off by default; `obsStartReplay` in settings.json; applied when the stream goes live or on connecting to a live OBS).
- **Test** on a rule queues both phases at once (source for 3 s, then the scene switch and clip).
- **Overlay watchdog** (the switch **Refresh the overlay in OBS when it goes quiet**, `overlayWatchdog`, off by default; `lib/overlay-watchdog.ts`): while the stream is live, if the newest overlay heartbeat is over 30 s old and the last OBS snapshot shows the overlay source visible in the scene on air, the site queues an `obs-refresh` itself, at most once per 5 minutes (a `SET NX EX 300` lock, `mixitup:watchdog:lock`), writes a Log line (`watchdog`), and the health row says when it last did (`mixitup:watchdog`). It runs from `POST /api/bridge/report`, which the app calls at least every 30 s while connected, so there is no cron; with the switch off it costs one settings read per report.
- Checks: `scripts/check-big-pulls-obs.mts` (names, reveal path, once-only claim, watchdog rules) and, in `bridge/scripts/check.ts`, the fake OBS answering `SaveReplayBuffer`, `SetCurrentProgramScene` and `SetSceneItemEnabled`.

## Chat and Brie Bucks
ROADMAP 55.10, TCG Bridge 0.8.0. The **Chat and Brie Bucks** tab (`ChatBucks.tsx`, `saveChatAction`: `requireAdmin`, audited, `revalidatePath`) holds four switches, `chat` in the Mix It Up settings (`ChatSettings` in `lib/bridge-chat-core.ts`, pure). **All are off by default**, and nothing below runs in a sandbox or without a paired bridge. Server side `lib/bridge-chat.ts`, check `scripts/check-bridge-chat.mts`, app side `bridge/src/bucks.ts`.
- **Stream start and end** (`streamStarted`, `streamEnded`, called from `lib/twitch-live.ts` through a dynamic import because this file reads the Mix It Up settings): the start is the first sighting of a stream (`applyStatus` sets `twitch:live:since` with NX, so it happens once however many reports say "live"); the end is `finishStream`, after its lock. **Start post** is a `say` job, default "Packs are open: type !pack" (variable `{channel}`). **End post** is a `say` job with `{topPull}` (the rarest pull, "card by viewer"), `{topPullers}` ("name (packs), ..." for the top three, `topPullers` in the recap) and `{channel}`; it is skipped when nobody pulled. Wording is editable (300 characters, a blank falls back to the default, an unknown `{variable}` stays as typed).
- **Big pull shout**: a Big pulls rule has an optional **Say in chat** line (`say`, 300 characters, variables `{viewer} {card} {rarity} {edition}`; `{edition}` is the copy number as `#12`, empty when the pull has none). A rule may be only a chat line. It rides the 55.8 reveal path: `firePullRules` renders it and `bridgePullStart` keeps it as `text` under `bridge:pullevent:<eventId>`, the overlay's reveal report queues it in the `pull-event` reveal job, and the app says it before the scene and clip. It is never sent at the save, so chat never spoils a card the overlay has not shown. An old overlay that never reports a reveal says nothing. Test on a rule sends the line with the sample pull.
- **Brie Bucks backup**: at the start and end the site queues a `backup` job (`phase` `start` or `end`, `currencyId`; bridge mode with a currency only). The app reads every viewer from Mix It Up (`GET /api/users/top?count=100000`, 60 s timeout; Mix It Up has no list-all route and leaves bots out) and writes `brie-bucks-YYYYMMDD-HHMMSS-<start|end>.csv` (`username,twitch_id,amount`, only viewers with some) to `Documents\TCG Bridge\backups`, keeping the newest 30. The app's Settings tab has **Open backups**. It runs apart from the job loop so a charge never queues behind it.
- **Brie Bucks check**: the app keeps a ledger (`ledger.json` in its data folder, the last 2000 rows) of every deduct and add it ran: job id, viewer, signed amount, the time the site queued it and Mix It Up's answer (a deduct it undid after a late result adds an `<id>:undo` row). The site keeps its own record, `bridge:charges` (a list, 2000 rows: id, viewer, signed amount, time), written by `callBridge` for every deduct and add (the Mix It Up log keeps only 20). At the end of a stream the site writes `bridge:check:pending` (the stream's window, 1 h) and queues a `ledger` job; the app answers by posting `{ entries }` to `POST /api/bridge/ledger` (bridge token, like every bridge route). `receiveLedger` claims the pending key (so one check per stream), compares the two lists for that window by job id and lists the jobs one side has and the other lacks, or has with another amount (`compareLedgers`). Balances are not compared. The result is `bridge:check:last`, shown on the tab ("Last Brie Bucks check") and written to the Log as a `check` line. A switched-off app, a bridge that is offline for the 5 s a job stays fresh, or a missing answer means no check that stream, silently.

## TCG Bridge app (the stream PC side)
ROADMAP 55.6a. `bridge/` is a small Windows app (Electron + TypeScript, its own `package.json`, app id `app.cheesytcg.bridge`) that sits in the tray on the stream PC, long-polls the site for jobs, runs them against Mix It Up's Developer API on `http://localhost:8911` and posts the results. It never fetches any address but the paired site and `localhost:8911`, and ignores job kinds it does not know. Since 0.2.0 (55.6b) it can also talk to OBS on the same PC; see "OBS in the app" below. Since 0.3.0 (55.6c) it also alerts, tests itself, can start Mix It Up and keeps a log; see "Reliability and self-help" below.
- **Install**: the TCG Bridge card on the Mix It Up page's Connection tab has **Download TCG Bridge** (the GitHub releases tagged `bridge-v*`). The installer is **not code-signed**: Windows SmartScreen shows "More info", then "Run anyway". Per-user install, no admin rights. It starts with Windows (on by default, a checkbox in the window) and, once paired, starts minimised in the tray.
- **Pair**: in the app type the site address (default `https://cheesytcg.app`) and the code from **Pair TCG Bridge** (ABCD-EFGH, works once, 10 minutes). The app sends the computer name as its name. The token is stored with Electron `safeStorage` (Windows encryption, tied to the Windows user) in the app's user data folder and never leaves the PC. **Unpair** in the app forgets it there; **Revoke** on the site makes the app show "Pair again".
- **Statuses**: tray icon green = site and Mix It Up both fine, amber = one of them, red = neither. The window shows Site (address, paired as, last poll, state: Connecting, Connected, Cannot reach the site, Pair again), Mix It Up (found, version, the currency the site last used) and the last 50 jobs with their results. "Mix It Up: No" means nothing answers on port 8911: Mix It Up is closed, or its Developer API is off (Mix It Up > Services > Developer API > Connect). The app checks every 5 s and sends `hello` (version, currencies) on start and each time Mix It Up comes back.
- **Loop**: after a normal answer the app polls again at once; after an error it backs off 1 s, doubling to 30 s. A 401 anywhere stops the loop ("Pair again"). A result is posted with up to 3 quick retries (network error or 5xx). A 409 `late` means the site gave up on the job: a `deduct` that went through is given back, an `add` is taken back, the others need nothing. Mix It Up not running answers each job "Mix It Up is not running" at once.
- **Jobs to Mix It Up** (V1 Developer API, PascalCase JSON; `username` is lowercased and must be a Twitch login, `currencyId` a GUID): `balance` = `GET /api/users/twitch/{name}`, the `CurrencyAmounts` entry with that `ID` (404 = 0). `deduct` = the same lookup, refused with "Not enough <currency>" when the balance is short (never negative), then `PUT /api/users/{user ID}/currency/{currencyId}/adjust` `{ "Amount": -n }`; the user ID from the lookup is used because that route resolves a name on the streamer's default platform, not necessarily Twitch. After a good deduct the job's `text` is posted to chat. `add` = the same adjust with `+n` (a viewer Mix It Up does not know is refused). `viewers` = `GET /api/chat/users`, the users with a `TwitchID`, lowercased and deduped. `say` = `POST /api/chat/message` `{ "Message", "SendAsStreamer": false }`. `hello` currencies = `GET /api/currency` (`ID`, `Name`); the version = `GET /api/status/version`.
- **Updates**: `electron-updater` checks the latest GitHub release on start (in the start-up window, installed at once) and every 6 hours (installed on quit). To release: bump `version` in `bridge/package.json`, merge, push the tag `bridge-v<version>`; `.github/workflows/bridge.yml` builds on `windows-latest` and attaches the installer, its blockmap and `latest.yml` to a release of that tag. The updater reads the repo's latest non-prerelease, so every full release in this repo must be a bridge release (mark anything else a pre-release). The window shows the app version and a **Check for updates** button (answers "You are up to date", "Downloading version x.y.z" or "Version x.y.z is ready ... (restart to update)"; only in the installed app). The last version the window saw is kept in the settings; after an update the window shows "Updated to x.y.z" with **See what changed** (opens `https://github.com/JoshMiles/tcg/releases/tag/bridge-vx.y.z` in the default browser) and **Dismiss**, until one of them is used. The first run ever says nothing.
- **OBS in the app** (0.2.0, ROADMAP 55.6b; `bridge/src/obs.ts`, no Electron imports): off by default. The window's OBS card has a "Talk to OBS" switch, the address (default `ws://127.0.0.1:4455`; only `ws://localhost:<port>` or `ws://127.0.0.1:<port>` is accepted) and the password, which is stored with `safeStorage` like the token and never sent to the site. In OBS (28 or newer) it is Tools > WebSocket Server Settings > Enable WebSocket server, Server Password (leave the app's field empty if authentication is off). While on, the watcher uses obs-websocket v5 (JSON subprotocol) and reconnects with a 1 s to 30 s backoff; the window shows connected or why not ("Wrong OBS WebSocket password", "OBS is not running, or its WebSocket server is switched off"), the program scene, the stream state and the overlay check. The tray goes amber when OBS is on but not connected; OBS off does not count.
  - **Requests**: `GetStreamStatus`, `GetCurrentProgramScene`, `GetInputList` (`inputKind: browser_source`), `GetInputSettings`, `GetSceneItemList`, `GetGroupSceneItemList` and, for the refresh, `PressInputPropertiesButton` (`propertyName: refreshnocache`). **Events** (subscriptions Scenes, Inputs, Outputs, SceneItems): `StreamStateChanged` (only `OBS_WEBSOCKET_OUTPUT_STARTED` and `..._STOPPED` count), `CurrentProgramSceneChanged`, `SceneItemEnableStateChanged`, `InputSettingsChanged`, `InputCreated`, `InputRemoved`, `InputNameChanged`; the last six trigger a re-check after a 1 s debounce.
  - **The overlay check**: a browser source is the overlay when its URL is on the paired site's host (a leading `www.` ignored) with the path `/overlay.html`; the key and other parameters are ignored and never sent. It counts as in the program when it is an item of the current scene, or of a group in it (one level), and as visible when the item (and its group) is enabled. If several sources match, a visible one in the scene is reported. **Not seen**: an overlay inside a nested scene (a scene used as a source) counts as not in the scene.
  - **Reports** (`POST /api/bridge/report`, see above): `stream` when the output starts or stops and once on connect; `obs` on connect, on disconnect, on any change, at most once a second, and unchanged every 30 s as a heartbeat. Turning OBS off in the app or quitting sends a disconnected snapshot. A failed report is not retried; the next change or heartbeat tells the site.
  - **The `obs-refresh` job** presses "Refresh cache of current page" on every matching browser source and answers `ok`, or `ok: false` with a reason in words when OBS is off, not connected, or no overlay source exists. It gives up after 4 s.
- **Mix It Up commands** (0.4.0, ROADMAP 55.6d): `GET /api/commands` (`CommandV1Controller`, route `api/commands`) lists `[{ ID, Name, IsEnabled, Category, GroupName }]`; the app keeps the enabled, named ones and sends `{ id, name }` in `hello`. A `run-command` job is `POST /api/commands/{id}` with a JSON array of strings as the body (the command's arguments, `$arg1text` to `$arg4text`); Mix It Up queues the command and answers 200 at once. The app runs a `run-command` only for an id it reported itself in the last `hello` (case-insensitive) and answers anything else, a bad id or a missing one with "That Mix It Up command is not in the list this app reported"; non-string args are dropped. If the list cannot be read the last good one is kept. A site that sends a kind an older app does not know is skipped without an answer; the kinds are fixed.
- **Reliability and self-help** (0.3.0, ROADMAP 55.6c; plain modules `alerts.ts`, `selftest.ts`, `launch.ts`, `log.ts`, `diagnostics.ts`, `update.ts`; `main.ts` only wires them):
  - **Alerts**: a Windows notification when the site link, Mix It Up or OBS goes from up to down, and one when it comes back. A part counts as down only after 15 s down, so a missed poll never alerts; at most one drop alert per part every 2 minutes (a drop inside that time is shown once the 2 minutes pass, if it is still down); the "back" notice only follows a drop that was shown. Only while the stream is live: "live" is what OBS last said (kept if OBS is then lost; OBS never connected counts as not live). With OBS switched off in the app there is no live signal, so every drop alerts. A part that never came up since the app started, or a revoked site, is not a drop. The window's "Alert me when a link drops while live" switch (saved, on by default) only mutes the notification; the log still records the alert. The decision is the pure `Alerts` class, fed snapshots and a clock.
  - **Self-tests** (each answers in words next to its button): **Test Mix It Up** checks the Developer API answers (and its version), finds the currency the site chose by id and reads its name, then reads the balance of a Twitch name (the box is prefilled with the channel name from the `hello` answer; a viewer Mix It Up does not know has 0). **Send test chat message** posts "TCG Bridge test message" through `/api/chat/message`. **Check OBS** runs the overlay check now and shows the scene, the stream state and the overlay, or why it cannot (OBS off, not connected).
  - **Start Mix It Up**: when Mix It Up is not found the Mix It Up card shows **Start Mix It Up**. It launches only the saved path, else the default `%LocalAppData%\MixItUp\MixItUp.exe` (where Mix It Up's own installer puts it: `MixItUp.Installer/MainWindowViewModel.cs`, `DefaultInstallDirectory`, in github.com/MixItUpBot/Desktop), and only an existing file named `MixItUp.exe`, detached, with no shell. **Choose MixItUp.exe...** opens a file dialog and saves the path (refused unless the file is called `MixItUp.exe`). **Start Mix It Up with TCG Bridge** (off by default) starts it when the app starts and nothing answers on port 8911.
  - **Diagnostics**: one log file a day in the app's logs folder (`bridge-YYYY-MM-DD.log` under Electron's `logs` path), files older than 7 days deleted on start. It records starts, pairing, the site, Mix It Up and OBS going up or down, each job (kind, ok, error, ms), alerts and errors. Every line goes through `Logger.log()`, which first removes the pairing token, the OBS password and the pair code (remembered while the app runs) and then, by pattern, overlay addresses, `Bearer` values and `key=`, `secret=`, `token=` and `password=` values. **Open log folder** opens it; **Copy diagnostics** puts on the clipboard the app, Electron and Windows versions, the statuses and the last 20 jobs as plain text, through the same redaction.
  - New IPC channels, all with fixed names in `preload.ts` and validated in `main.ts`: `alerts`, `test-mix` (the name must be a Twitch login), `test-chat`, `test-obs`, `start-mix`, `choose-mix`, `start-mix-with-bridge`, `open-logs`, `copy-diagnostics`, `check-update`, `open-release` (the address is built in the main process from the app version), `dismiss-updated`.
- **Look and start-up updater** (0.5.0, ROADMAP 55.6e; `bridge/src/startup.ts`, no Electron imports; `main.ts` wires it to `electron-updater`): every start opens a small frameless start-up window first (`renderer/splash.*`, its own sandboxed preload `splash-preload.ts` that can only listen), also when Windows starts the app minimised (it then leaves only the tray). The `Startup` state machine is fed the updater events and a clock: "Checking for updates", then "Downloading update x.y.z" with a bar, then "Installing update" (`quitAndInstall(true, true)`, so the app restarts by itself) or "Starting". No internet, or no answer after 8 s: it starts and the main window shows "Couldn't check for updates" (dismissible). A failed or stalled (30 s) download starts the current version and the 6-hour check tries again. An update found after the hand-over is never installed at start-up: it only sets "Version x.y.z is ready ... (restart to update)". In development (`npm start`) there is no check. The main window is frameless with its own minimise and close-to-tray buttons (quit stays in the tray menu), a rail (Status, Settings, About) and a card per link (Site, Mix It Up, OBS) with a status dot and a one-line state; the renderer is still plain HTML, CSS and JS, with Fredoka and Nunito bundled locally (SIL OFL) and Lucide icons inline (`renderer/LICENSES.txt`). The app icon and the three tray PNGs are drawn by `npm run icons` from the site's own icon (`public/brand/icon.png`); tray states differ by badge shape (dot, half ring, cross) as well as colour. Dev only: `npm start -- --demo-startup [--shots=<folder>]` (`src/demo.ts`, excluded from the installer).
- **Checks**: `bridge/scripts/check.ts` (a fake Mix It Up, a fake obs-websocket v5 server in `bridge/scripts/fake-obs.ts` and a fake site on local ports; `cd bridge && npm run check`). It also covers the start-up state machine with fake events (no update, update with progress, offline, slow check, failed download, late update) and the alert rules with a fake clock, the self-tests, the launcher (a fake `spawn`), log pruning, and greps the log file and the diagnostics text for the token, the OBS password, the overlay key and the pair code, failing if any appears. `scripts/check-bridge-app.mts` runs it with the root checks (and prints `skipped:` when `bridge/` has no `node_modules`, as in the root CI job), and the workflow typechecks and runs it on pull requests that touch `bridge/`. ## Webhook grants look like pulls
The incoming webhooks only accept a real Twitch login as `username` (3 to 25 letters, digits and underscores; a leading `@` is dropped; anything else is a 400), and the grant-card webhook only grants a card number that exists in a published pack of the active season (404 otherwise), so a bad Mix It Up variable fails loudly instead of creating a ghost viewer.

A card granted by the grant-card webhook (a Mix It Up reward) is recorded as `grant` with `source: 'webhook'` plus the facts of a pull (name, stars, pack, new or not, copies, collected, edition). It counts as a **pull** in the Live Activity categories and the Discord Pulls category (with the star and new-only filters), reads "X pulled Y (granted by webhook)" in the live feed and on the dashboard's Recent activity, and posts the same embed as a pull with a "Granted by webhook" line (`pullEmbed` in `lib/discord.ts`). The Live Activity numbers, the stream recap (`asPullEvent` in `lib/activity-view.ts`; there it is listed as a reward rather than a pack opened) and the stats counters behind the weekly digest and the dashboard charts (`recordStats`, from the day this shipped) count it as a pull too. Admin grants are unchanged (Grants & removals, the Cards Discord category, the `grant` counter). Events recorded before this change lack the extra facts and still post, with the card's stars looked up.

## Mix It Up chat commands (Mix It Up page, Commands tab)
ROADMAP 19.2. One incoming webhook, `POST /api/webhooks/command` (`{ secret, command, username, args? }`, the incoming secret), answers every chat command: `{ ok, message, vars }` plus each variable at the top level for Mix It Up's "JSON to special identifiers". A refusal is `{ ok: false, message }` with the command's own error text; an unknown or switched-off command is `{ ok: false, message: '' }` (silent). `/api/webhooks/show-card` still works unchanged.
- **Pure core** `lib/commands-core.ts`: the `ChatCommand` shape, the fixed action registry `COMMAND_ACTIONS` (each action's variables, sample values and error kinds: `showoff`, `card-stats`, `my-stats`, `collection`, `leaderboard`, `pulls-left`, `text`), `matchCommand` (name or alias, without the `!`), `interpolate` (unknown placeholders dropped), `tidyReply` (no Markdown marks, 400 characters), `cleanCommands` (max 30, unique names). **KV** `lib/commands.ts`: commands in `mixitup:commands` (the defaults `!showoff` and `!stats` are seeded on first read), run counts in `mixitup:cmdstats`, the last 20 runs in `mixitup:cmdlog` (shown on the Log tab, never posted to Discord), cooldowns `cmd:cd:<id>` and `cmd:ucd:<id>:<viewer>` with a TTL. `runCommand` is used by the webhook and by Try it.
- **Dry run**: Try it (the builder) runs the editor's draft with `dry`: no overlay event, no cooldown spent, no log line. `showoff` calls `prepareShowOff(user, args, { dry })`. A sandbox never queues an overlay event either.
- **Privacy**: hidden and private collectors (`getHiddenUsers`) show as "a private collector" in `topHolder` / `firstPulledBy`, are left out of `collectors`, and `my-stats` for them answers "This collector keeps their stats private" unless they ask about themselves.
- **FAQ**: the "Chat commands" section lists the enabled commands from `getCommands()`, then a fixed `!pack` line (it asks the stream to open a pack, and it is set up in Mix It Up rather than the command builder). `scripts/check-commands.mts` covers the builder. **Copy setup** (`commandSetups` in `lib/mixitup-setup.ts`) lists every switched-on command: the `!` name, `POST /api/webhooks/command`, the JSON body (the real incoming secret, `$username`, `$allargs`) and the `message` field for the Chat Message.

**Stream start / end** (`POST /api/webhooks/stream`, `{ secret, event: 'live' | 'offline' }`, the incoming secret): wire Mix It Up's Stream Start and Stream End events to it. `setLiveFromHint` (`lib/twitch-live.ts`) marks the stream live or offline at once (System notice, stream-start marker, recap on offline) and stores `twitch:live:hint`; for 5 minutes a Helix answer that disagrees is overridden, since Twitch's API lags a stream's start and end. The minute cron keeps checking Helix as a fallback.

## Stream Deck buttons
ROADMAP 55.2. A Stream Deck button is a Mix It Up command (run from the Stream Deck with Mix It Up's plugin) whose Web Request calls `POST /api/webhooks/buff` (`app/api/webhooks/buff/route.ts`, logic in `lib/streamdeck.ts`, `scripts/check-streamdeck.mts`). Body `{ secret, buff, target?, username? }` or `{ secret, action, amount?, target?, username? }`; the secret is the incoming one (a wrong one is 401, and a right one shows as "Stream Deck" in the connection health). It always answers `{ ok, message }` with a line for chat.
- **Buffs**: the Buff Editor has a "Stream Deck" checkbox per buff (`BuffDef.streamDeck`, off by default, never for grant-achievement). A buff that is unknown or switched off answers `{ ok: false, message: '' }`. `target`: `everyone` (the default for a community buff), `viewer` (needs `username`) or `last-pull` (the viewer of the newest `pull` in the activity log since the stream began, `currentStreamKey`; refused with "No one has pulled this stream yet."). A self buff needs `viewer` or `last-pull`; a community buff refuses a viewer. It runs through `applyBuff` with `source: 'streamdeck'`; refusals come back in words (already active, too many buffs, Mix It Up off or silent, no season). A success writes the audit log, which also posts to the Discord admin log ("Stream Deck: everyone +1 pull this stream"). It does not add a line to the live activity feed.
- **Quick actions** (`action`): `stream-pulls` with `amount` sets "Extra pulls this stream" (`pulls:stream-buff`, `0` clears); `free-pack` with `target` viewer or last-pull queues one pull with `queuePull(..., { free: true })`, which never charges and shows in the feed like a chat pull.
- **Happy hour** (`action: 'happy-hour'`, 55.4c): `amount` = minutes (1 to 240), optional `percent` (1 to 99; none = free packs); `amount` 0 ends it. Same 10 second cooldown (`streamdeck:cd:happy-hour`). Answers a chat line such as "Happy hour: 25% off packs for 45 minutes." It is on the Stream Deck tab as a Copy setup card.
- **Cooldown**: 10 seconds per button, a KV key `streamdeck:cd:<buff or action>:<target>` set with SET NX EX, so a double press applies once ("That button was just pressed. Wait a few seconds."). It is per target, so two different viewers can be rewarded back to back. Not configurable.
- **Page**: the **Stream Deck** tab (`StreamDeckTab.tsx`) lists the switched-on buffs and the three quick actions, each with a Copy setup card. The setup wizard's need and events steps link to it. No overlay toast. Each card has Download for Mix It Up (Command files below).

## Command files (Download for Mix It Up)
ROADMAP 55.5. Every Copy setup card for an incoming webhook (the wizard's `!pack`, each switched-on chat command, the Stream Deck buttons and quick actions, stream start and end) has a **Download for Mix It Up** button (`DownloadPreset` in `setup/SetupClient.tsx`). It links to `GET /api/admin/mixitup/preset?spec=<PresetSpec>` (`app/api/admin/mixitup/preset/route.ts`, `isAuthenticated`, `no-store`), which fills in the real incoming secret and `SITE_URL` and sends `<name>.miucommand` (one file per command, no zip). The file holds the secret: the button says so and links to making a new one (Settings, Webhooks). The link carries no secret, only the card's `PresetSpec` (kind, name, webhook path, body fields, reply fields), which `presetFile` validates (fixed webhook paths only).
- **Generator** `lib/mixitup-presets.ts` (pure, `scripts/check-mixitup-presets.mts`): `chatCommandFile`, `eventCommandFile`, `actionGroupFile`. One JSON line with `$type` first on every object and the key order of `scripts/fixtures/mixitup-chat-command.miucommand` (a real export); new UUIDs on each call. Chat command = `ChatCommandModel` (Type 1), stream start/end = `EventCommandModel` (Type 2, `EventType` 200 `TwitchChannelStreamStart` / 201 `TwitchChannelStreamStop`), Stream Deck button = `ActionGroupCommandModel` (Type 4). All hold a `WebRequestActionModel` (POST, JSON) and, when the answer has a `message`, a Chat Message that says `$reply`.
- **Reading the answer**: the Web Request action itself does it. Response type "JSON to special identifiers" maps a JSON field to an identifier (`message` to `$reply`; any other field `x` to `$tcgx`, since Mix It Up has its own `$message`). There is no Webhook Response action. Chat commands map `message` and the command's variables; `!pack` also `left` and `balance`.
- Bodies use Mix It Up's identifiers (`$username`, `$allargs`), never `{{...}}`. The download is the saved command (the Commands tab card downloads what is saved, not unsaved edits). No files for balance, deduct, add or viewers (nothing in stock Mix It Up can answer them, see TCG Bridge).
- Importing into real Mix It Up has not been checked from here; a file that fails to import means the sample layout changed.

## Control from the PC
ROADMAP 55.9. TCG Bridge 0.7.0 (the Control tab) lets the streamer drive the site from the stream PC. Every press ends at `POST /api/bridge/action` (`app/api/bridge/action/route.ts`, `bridgeGuard`, logic in `lib/bridge-actions.ts`, `scripts/check-bridge-actions.mts`). Body `{ action, ... }`, always answers `{ ok, message }`. The actions are fixed: `status` (also `paused` and the buffs with the Stream Deck switch on), `buff` (`id`; a community buff goes to everyone, a self buff to the last puller, through `runStreamDeck`, so its switch, cooldown and audit line apply), `last-buff` (re-runs the body stored in KV `streamdeck:last`, so the 10 s cooldown can refuse a quick repeat), `pause` (`on` or a toggle), `refresh` (queues the `obs-refresh` bridge job), `skip` and `clear-queue`. Pause, skip and clear write the audit log.
- **Stream Deck buttons without Mix It Up.** The app runs a web server on `127.0.0.1:47653` only (`bridge/src/control.ts`; a fixed, rarely used port so the saved buttons keep working; if it is taken the Control tab says so). A random key made on first run is the first path segment, `http://127.0.0.1:47653/<key>/<button>`, and a wrong key is a 404. Only GET is answered; a request with an `Origin` or `Sec-Fetch-Site` header (a web page) or a Host other than 127.0.0.1 or localhost is refused, so a web page cannot press a button. Buttons: `pause`, `refresh`, `last-buff`, `buff/<id>`. In the Stream Deck app use a "Website" action with "GET request in background". The Control tab lists every button with Copy.
- **Pause pulls.** KV `pulls:paused` (`lib/pull-pause.ts`), off by default. `queuePull` turns every viewer pull away first (paid and `!pack`, one route) with `{ ok: true, ignored: true, reason: 'paused', message: 'Packs are paused, back soon' }`, before Mix It Up is asked, so nothing is reserved. Test pulls and the streamer's free packs still go through. Switches: the **Pause pulls** form on the Overview, the Control tab, the tray menu and a Stream Deck button. Optional chat lines on pause and resume (`pulls:pausechat`, off by default, a `say` job through `bridgeSay`).
- **Hotkeys.** Electron `globalShortcut`, set in the Control tab, empty by default: refresh the overlay, pause or resume, last buff again. A shortcut another program holds, one used twice, or one Electron does not understand is reported next to its field.
- **Queue.** `GET /api/bridge/queue` (`bridgeGuard`) lists the overlay queue (`webhooks:queue`: who, pack, seconds waiting, next first, `lib/queue-control.ts`). The app reads it only while the Control tab's **Pull queue** section is open, at most every 5 s. **Skip next pull** and **Clear queue** pop events atomically and refund a paid pull the way a refused one is (`dropDraw` plus `releasePaidPull`: the ticket is dropped and the reservation released, so the viewer is not charged and keeps their allowance). The dashboard's Clear queue shares that core, so it refunds too.

### Staff notices and shortcuts (ROADMAP 55.13, TCG Bridge 0.11.0)
- **Notices.** A `notice` job (`StaffNotice` in `lib/bridge-core.ts`: kind, title, text, link path) is fire and forget: the app shows a Windows notification and a click opens the page in the browser. `sendNotice` (`lib/bridge.ts`) writes it only to PCs with staff on, one KV list per PC (`bridge:notices:<pcId>`, 60 s expiry), and queues nothing when no PC has staff on or in a sandbox. The poll route hands a PC its list only when its staff switch is on (`pollJobs(hash, version, pcId)`), so a PC without the switch never reads one (the cost is one extra LPOP a second per staff PC while it polls). A notice older than the job age limit is dropped: **one sent while the app is offline is lost**, and the app's Activity tab and settings say so.
- **Kinds**, each with its own switch in the app's settings (all on once staff tools are on): Needs attention (a Discord channel switched off, a failed backup, a data health crossing; `lib/system-notices.ts`, `lib/discord.ts`), New reports and feedback (`lib/feedback.ts`, links to `/admin/feedback?kind=<kind>#status-<id>`; there is no page per item), Paid pull refusals (`noteRefusal` in `lib/bridge-notice.ts`, called from `logMixItUp`; at most one per reason per minute through an atomic `bridge:refusal:<reason>` key with a 60 s expiry, and never `insufficient_balance`), Deploys (`noteDeploy`, from the bridge poll in production only: the first poll of a build claims `bridge:deployed:<commit>` with `nx`, so a build notifies once across servers; it lists the changelog lines of that PR when the build has any).
- **Links** are paths. The app opens one only when `siteUrl` (`bridge/src/notices.ts`) puts it on the paired site's own address, so a notice or a search result can never open another site.
- **Shortcuts.** The tray has Admin links (Dashboard, Mix It Up, Overlay Editor, Users). The Staff tab has **Back up now** (`POST` action `backup`: `runBackup` and `reportBackup`, the same as Admin Settings; it says when done or why it failed, and audits `Backup taken` or `Backup failed` via the PC) and a Quick search (`GET ?what=search`: the admin command palette's records through `paletteRecords` in `lib/palette-items.ts`, plus cards of the active season, each with its admin page). - **Check.** `scripts/check-bridge-notices.mts` (gating, stale notices, the refusal throttle, one notice per build, 403 and audit for Back up now, Activity and search); `npm run check` in `bridge/` covers the switches and the same-origin link rule.

## Setup wizard
ROADMAP 55.1. `/admin/mixitup/setup` (`app/admin/mixitup/setup/page.tsx`, `export const instant = false`) is a full-page wizard, one step per screen, selected by `?step=`: What you need, Mix It Up to the site, The site to Mix It Up, Pull rules, Stream events, Done. Back and Next are plain links and the step bar jumps to any step. There is no wizard state: `stepsDone` (`lib/mixitup-wizard.ts`, pure) reads the same status cards, health row and settings as the Overview, and `pickStep` opens the first step not done (Done when all are), so reopening resumes and a step can always be revisited.
- **Mix It Up to the site**: a Copy setup card for `!pack` (`incomingSetup` in `lib/mixitup-setup.ts`, address `/api/webhooks/pull`, the incoming secret in the body; `getWebhookSettings` makes the secret on first read, so it is never empty). The step re-reads itself every 3 s (`AutoRefresh`, `router.refresh()`, only while the tab is visible and the step is not green). It is green when the incoming card is (a request with the right secret reached any route); a wrong secret after the last good request shows "Mix It Up reached the site but the secret did not match" from `mixitup:seen`'s `badAt`.
- **The site to Mix It Up**: in bridge mode `BridgeCard` (download, pairing code, paired apps), the outgoing status card (TCG Bridge, Mix It Up found, currency; its "What to do" says how to switch on the Developer API), a currency select that posts the Connection form (`saveConnectionAction`), the Overview's balance check (`Quick` + `testBalanceAction`) and the OBS card with the TCG Bridge OBS password note. - **Pull rules**: the charge switch and `PaidPullFields`, posting `saveMixItUpAction`, the same form fields as the Paid pulls tab. Both save actions take a hidden `returnTo=setup` and then redirect back to their wizard step (errors included) instead of the Mix It Up tabs.
- **Stream events**: Copy setup cards for `/api/webhooks/stream` (`event` live and offline). Stream Deck buttons are on the Stream Deck tab.
- **Entry points**: the Connection tab and the Overview's setup banner (shown while a status card is not green) link to the wizard; the label is "Set up Mix It Up" until a bridge is paired or any request has reached the site, then "Run setup again".
- `scripts/check-mixitup-page.mts` covers `stepsDone`, `pickStep` and `incomingSetup`; `scripts/check-mixitup-health.mts` covers the health record (right secret, wrong secret, outgoing failure).
