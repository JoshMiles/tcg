## Mix It Up paid pulls
Viewers can pay a currency (Brie Bucks) for a pack. Settings live in KV `mixitup:settings` (`lib/mixitup-core.ts`, pure; `lib/mixitup.ts`, KV and calls; the page is described above, actions in `mixitup-actions.ts`). Off by default; while off nothing below happens. Design and decisions: ROADMAP Track 12.
- **Flow**: `POST /api/webhooks/pull` reserves the pull (`reservePaidPull`: viewer's pulls this stream, then a `balance` request to Mix It Up, counting pulls already in flight) and queues it with `paid: true`. The overlay sends the event id back as the pull's ticket; `POST /api/collection` claims the ticket and then the payment (once each; a reused payment = 409, nothing saved), sends the `deduct` request with the custom message **before** the print is written (so the edition number is not known yet and `{serial}` is empty), and only then adds the print. If Mix It Up does not confirm, no print is made, the pull allowance comes back and the System Discord channel is told (`noticeUnpaid`); if the print then cannot be saved, the charge is paid back through the add address (`refundPaidPull`, the same call the currency-grant buff uses) and staff are told to refund by hand when that fails too. Refusals queue nothing and answer `{ ok: true, ignored: true, reason, message }` (`insufficient_balance | limit_reached | mixitup_unavailable | bad_balance | cooldown | queue_full`) so the Mix It Up command can post `message` to chat. **Cooldown** (ROADMAP 55.4d): `cooldownSeconds` in `mixitup:settings` (whole seconds, 0 = off, max 3600, on the Paid pulls tab). `reservePaidPull` claims `mixitup:cd:<viewer>` with SET NX EX before the limit count and the balance request; if the key is there the pull is refused with `cooldown` and `{wait}` = the key's TTL (at least 1), leaving no limit count. Any later refusal (limit, balance, Mix It Up down) deletes the key again, and so does `releasePaidPull` (no pack to open, queue failure), so a pull that did not happen starts no cooldown. The channel login is exempt. Stream Deck free packs, event rewards, staff gifts and sandboxes never reserve, so they skip it; a test pull (55.14) goes through like it does for limits, so only a test viewer other than the streamer is held to it. An extra-pack credit bypasses it like it bypasses the limit.
- **The direct addresses answer in the HTTP reply** (Mix It Up has no action that answers a request; there is no Webhook Response action, so use TCG Bridge or a service of your own). Balance: JSON with a number at the balance field. Deduct: any 2xx counts unless the body sets `ok`, `success` or `applied` to false.
- **Price per role** (ROADMAP 55.4b): `priceByRole` in `mixitup:settings` holds an optional whole-number price for `subscriber` and `vip` (the same `role` the pull webhook sends for limits). Blank or missing = the base `cost`; 0 = free. `pullPrice(settings, { role })` in `lib/mixitup-core.ts` is the one place a price is worked out (a viewer with several roles pays the lowest); its comment lists the full price order the later 55.4 items add to (pack price, else role price, else base; then happy hour; first free makes 0). `reservePaidPull` works the price out once and stores it as `amount` on `mixitup:pay:<id>`; the balance check, the deduct, the refund, `{cost}` in replies and the `balance` / `left` fields all use that stored price, so a settings change while a pack waits on the overlay changes nothing. A reservation from before has no price and is charged the current `cost`. A price of 0 skips the balance request and sends no `deduct`, but still counts toward the viewer's limit. In-flight pulls: `mixitup:pending:<viewer>` is now the sum of the prices in flight (it was a count), and `decide` compares the balance with that sum.
- **Happy hour** (ROADMAP 55.4c): KV `mixitup:happyhour` = `{ kind: 'discount', percent } | { kind: 'free' }, endsAt (ms), by`, a live state apart from `mixitup:settings` (`lib/happyhour.ts`; the pure shape, `activeHappyHour`, `cleanHappyHourInput` and the price step are in `lib/mixitup-core.ts`). It ends by time: the key's TTL matches `endsAt` and a read after `endsAt` counts as off, so there is no cron. `pullPrice(settings, { role, happyHour, now })` takes it as an argument (it stays pure) and applies it after the role price: discount = price x (100 - percent) / 100 rounded up to a whole number, free = 0. `reservePaidPull` reads it with `getHappyHour()` and stores the result as `amount`, so `{cost}` in replies shows the happy hour price and a happy hour ending while a pack waits on the overlay changes nothing; a free one skips the balance check and the deduct but still counts toward the limit. Start (minutes 1 to 240, free or discount, percent 1 to 99) and End now are in the Happy hour box at the top of the Paid pulls tab (`HappyHourBox.tsx`, `happyhour-actions.ts`, admin only); starting while one runs replaces it. Starting or ending, from the page or the Stream Deck, writes one audit entry (`everyone`) and so one post to the Discord admin log (`startHappyHour` / `endHappyHour`).
- **Limit per stream**: Paid pulls has a number for regular, subscriber, VIP, moderator and broadcaster (all 0, no limit, until staff change them). The old single `limit` is the fallback when a role has no number, so a save from before role limits keeps working. The pull webhook may send `role` (`regular | subscriber | vip | moderator | broadcaster`); missing or unknown counts as regular, and `CHANNEL_LOGIN` is always the broadcaster. The site does not ask Twitch which role someone is. A gifted sub earns a pack and does not change a limit. A viewer's own limit (`user:<name>:pulllimit`, user page → Admin tab → Pull limit) replaces the role, and their temporary bonuses still add (ROADMAP 12.4). A base of 0 stays unlimited. **This stream, everyone:** Set / Clear on the same tab stores `{ amount, streamKey, by, at }` at `pulls:stream-buff`. It adds for every viewer only while `currentStreamKey()` still matches, and amount 0 deletes it. Counter `mixitup:cnt:<stream>:<viewer>` where the stream is the live Twitch stream's start (`getLiveStatus`), else the UTC day. Raised on reserve, lowered when a reservation fails or a pull is revoked. In-flight pulls: `mixitup:pending:<viewer>`; reservation `mixitup:pay:<id>` (1 h).
- Gifts from the dashboard, the extension and sandboxes never charge. Addresses are saved through `checkWebhookUrl` (public https only) and every call goes through `sendWebhook` (`lib/webhook-send.ts`: see ux-conventions, outgoing webhook addresses; an http address saved earlier still sends, a localhost one never does, so Mix It Up on the streamer's own machine needs an https tunnel); the last 50 requests (out and in) are in KV `mixitup:log` and shown on the Log tab. `scripts/check-mixitup.mts` covers it with a fake Mix It Up. **Copy setup** (`paidPullSetup` in `lib/mixitup-setup.ts`) shows the balance and deduct bodies from the saved settings, the addresses, which action should answer `{ "balance": n }` (the saved balance field), and which action takes the currency. An empty deduct address is the balance address, told apart by `action`.
- **Add address** (`addUrl`, optional): the Mix It Up command that gives currency, used only by the `currency-grant` buff (Buff Editor). `grantCurrency` in `lib/mixitup.ts` sends `{ action: 'add', secret, username, amount, currency }` and, like a deduct, counts a 2xx unless the body sets `ok`, `success` or `applied` to false; it is logged as `add`. **Chat viewers address** (`viewersUrl`, optional): answers `{ users: string[] }` (or a bare array); `fetchChatViewers` sends `{ action: 'viewers', secret, currency }`, lowercases, drops @, dedupes and caps at 5000. Community `score-bonus` and `currency-grant` buffs go to those viewers (players with no cards included, who have no leaderboard row until they pull) and fail with a clear error when Mix It Up is off, the address is empty, or the call fails. A `currency-grant` writes a record `buffgrant:<id>` first (user to pending/paid/failed), pays one viewer at a time saving after each, and never pays a viewer marked paid; unpaid grants are listed in `buffgrants:open` and shown on the Buff Editor with **Retry unpaid** (`runGrant`, `retryGrantAction`). The trigger (card) is spent once; a partial result tells the player some are unpaid. The buff refuses to apply (and the Buff Editor warns) while Mix It Up is off or `addUrl` is empty; sandboxes never call it.
- **Connection health** (`lib/mixitup-health.ts`, `scripts/check-mixitup-health.mts`): no longer shown on the Stream page (its status strip and the status cards on Connections use the same data). Two small hashes, written fire-and-forget (a failed write never touches the request). `mixitup:seen`: field = incoming route (`/api/webhooks/*` only), value `{ okAt?, badAt? }`; `incomingSecretValid` sets `okAt` on a right secret and `badAt` on a non-empty wrong one (the other field is kept; a missing secret records nothing). `mixitup:out`: field = `balance | deduct | add | viewers`, value `{ at, ok, detail }`; `callMixItUp` records the last result by the payload's `action` (`ok` = Mix It Up answered 2xx, `detail` = `HTTP <status>` or the plain-words error; a `test` message is not recorded). The chips: when Mix It Up last reached the site and through which route (`!pack`, chat commands, show-off, card reward, collection, stream start/end), a warning for any route whose `badAt` is newer than its `okAt`, and one chip per address (not set / set, not used yet / working / failing with the reason; an empty deduct address shows "uses the balance address"). `healthChips` is the pure part.
- `/api/collection` is locked down by server-rolled pulls (docs/overlay.md, ROADMAP 13.1).

## Replies and the request log (ROADMAP 55.3)
Every incoming route answers JSON with a `message` a Mix It Up Chat Message can say. Existing keys are unchanged.
- **`/api/webhooks/pull`**: queued `{ ok: true, message: "Opening a pack for <name>", left?, balance? }`. `left` = paid pulls left this stream after this one (only when the viewer has a limit); `balance` = what Mix It Up said just before (the price is taken when the pack is revealed). Neither is there for a free pull or an extra-pack credit; no extra Mix It Up call is made to learn them. Refused `{ ok: true, ignored: true, reason, message, balance? }` (`insufficient_balance | limit_reached | mixitup_unavailable | bad_balance | cooldown | queue_full | unknown_pack | blocked | paused | no_packs`, or the live gate's text with an empty `message`).
- **Queue cap** (ROADMAP 55.4e): `queueCap` in `mixitup:settings`, a whole number 0 to 100 (`QUEUE_CAP_MAX`), 0 = off (the default). Paid pulls card. `queuePull` (`lib/pull-queue.ts`) refuses a pull with `{ ok: true, ignored: true, reason: 'queue_full', message }` while `queueLength()` (the overlay queue list, `webhooks:queue`, which also holds show-offs) is at or over the cap. The check runs after the pause and block checks and BEFORE `reservePaidPull`, so a refusal charges nothing, starts no cooldown and counts toward no limit; it writes a `refused` line to the Mix It Up log. It is an explicit opt-in: only the pull webhook passes `chat: true`, so Stream Deck free packs, event rewards (55.4g), staff gifts, the extension, sandboxes and test pulls (which carry `test`) are never refused. It is a soft limit: the count is read and the pull queued without a lock, so two pulls arriving at the same moment can both pass. Check: `scripts/check-bridge-actions.mts`.
- **Pick a pack** (ROADMAP 55.4f): the pull webhook takes an optional `pack` (text, trimmed, 60 characters at most; `cleanPackArg`). The `!pack` download in the Mix It Up commands helper (and the setup wizard's `!pack` card) sends `"pack": "$allargs"`, so `!pack Base` asks for the Base pack; an empty `$allargs` sends an empty string, which counts as no pack. `queuePull` matches it (`pickPack` in `lib/mixitup-core.ts`) against the active season's openable packs (live packs that have cards, the same set `rollDraw` chooses from): the first exact name, case-insensitive, else the one pack whose name starts with it. No `pack` = `queuePull` rolls the pack itself, by the usual pack weights (`rollPack` in `lib/draw.ts`, the same roll `rollDraw` uses), among the same openable packs, still before the reservation. No match, or a prefix that fits several packs, refuses with `{ ok: true, ignored: true, reason: 'unknown_pack', message }`, the reply `unknown_pack` with `{packs}` = the openable pack names, comma separated, and a `refused` line in the log. It is checked BEFORE `reservePaidPull` (right after the pause and block checks, with the queue cap), so a refusal charges nothing, starts no cooldown and counts toward no limit; a name is checked for paid and free chat pulls alike, and every pull (free ones too) has its pack chosen here, so there is one way a pack is picked; a free pull just ignores the price (a season with no openable pack skips the whole step and answers `no_packs` as before). The chosen pack, asked for or rolled, goes to `issueDraw(..., onlyPackId)`, which rolls the usual card and version odds inside that pack only. **Price per pack:** an optional `price` on the pack (a whole number from 1, blank = none; `Pack.price`, set in the pack workspace's Pack settings, cleaned by `cleanPackInput`). The price order in `pullPrice` is pack price, else role price, else base price, then happy hour, and `queuePull` hands the chosen pack's price to `reservePaidPull`, which stores the result as `amount` on the reservation like any other price. **Every paid pull is charged the price of the pack it opens:** a plain `!pack` rolls a random pack from the season first and pays that pack's price (pack price, else role price, else base; then happy hour; a first free pack makes it 0), the same as `!pack <name>`. The `!pack` packs card (`PacksCard`) lists the openable packs with their prices (the base price where none is set) and a link to each pack's settings. Check: `scripts/check-pick-pack.mts`.
- **Editable replies** (ROADMAP 55.4a): `replies` in `mixitup:settings`, one optional text per key of `REPLY_DEFAULTS` in `lib/mixitup-core.ts`: `queued`, `queued_first_free` (blank uses `queued`, not its suggested text), `insufficient_balance`, `limit_reached`, `mixitup_unavailable`, `no_packs`, `cooldown`, `queue_full`, `unknown_pack` (the only one that uses `{packs}`). That table is also where today's text lives; a key that is missing or blank uses it, so a save from before keeps working. A new reply is one more entry there plus a label. `renderReply(template, values)` fills `{username}`, `{cost}`, `{currency}`, `{balance}`, `{limit}`, `{left}`, `{wait}` (seconds left, cooldown only) and `{packs}` (the pack names, unknown_pack only), drops a placeholder that has no value (a free pull has no `{left}`) and the double space it leaves, and caps the text at 400 characters. The Paid pulls form posts `reply_<key>` fields (trimmed, 400 characters each; a blank field clears a saved text). Only `message` changes: `reason` and every other key of the answer are as before, and the texts that were already empty (the live gate) or fixed (`bad_balance`, `blocked`, `paused`) are not editable. Checks: `scripts/check-mixitup.mts` (pure), `scripts/check-two-way.mts` (a saved text comes back from `/api/webhooks/pull`).
- **First pack free** (ROADMAP 55.4h): `firstPackFree` in `mixitup:settings`, off by default, a switch on the Paid pulls card. When on, a viewer's first paid chat pull has price 0: `pullPrice` takes `firstFree` as the last step (after pack, role and happy hour), so there is no balance request or deduct and the pull still counts toward the limit; the reply shows `{cost}` 0 and uses `queued_first_free` when it is not blank. **First ever** is decided in `reservePaidPull`: SET NX on `user:<name>:firstfree` (no expiry); if that wins, every season's collection is read for the viewer (`getUserCards`) and any card means they are not new. There is no lifetime pull counter, so the flag is also kept for such viewers: that makes the season read happen once per viewer, not on every !pack, and means a viewer who pulled before the setting existed never qualifies. An unreadable history frees the flag and charges normally. A refused pull (cooldown, limit, balance, Mix It Up down) deletes the flag again, and so does `releasePaidPull` when the pack never happened (the reservation carries `firstFree`); once the pull is claimed it stays forever. A print that cannot be saved after the claim does not give the free pack back. Event rewards, Stream Deck packs, gifts and sandboxes never reserve, so never touch the flag; a test pull (55.14) passes `test` and neither sets nor reads it. Check: `scripts/check-mixitup.mts`.
- **`grant-card`**: `{ ok: true, username, cardNumber, variant, message: "<name> got <card>" }`; errors (400, 404) `{ error, message }`. **`collection`**: `{ ok: true, message }`, or ignored with `message: ''`. **`stream`**: `{ ok: true, live, message }`. **`show-card`**, **`command`**, **`buff`** already answered with `message`. A wrong secret (401) or bad username (400) is `{ error, message }`.
- **`requestId`** (optional, on `pull`, `grant-card`, `buff`; `lib/webhook-reply.ts`): the first request claims `webhook:req:<route>:<id>` with SET NX (10 minutes), runs, and stores its status and body; a repeat inside 10 minutes answers that stored result and does nothing (a repeat arriving while the first still runs waits up to 3 s, then answers "already being handled"). If the first request throws the claim is dropped. No `requestId` always runs. The `!pack` and Stream Deck cards and files send `"requestId": "$randomnumber1:2000000000"` (`REQUEST_ID` in `lib/mixitup-setup.ts`): in Mix It Up's source `$randomnumber<min>:<max>` is drawn again every time a command reads it (`SpecialIdentifierStringBuilder`), so it differs per run; a duplicate is a 1 in 2 billion chance. Never a fixed word, which would ignore every request after the first.
- **Log**: each request on those three routes adds a `pull`, `grant` or `buff` line to the Mix It Up log (viewer, result, `reason: message` for a refusal, "repeat of an earlier request" for a replay). The log keeps the last 50 lines (incoming and outgoing together), never goes to Discord, and the Incoming and Refusals filters include the new lines.
- **Outgoing calls** time out after 5 seconds; the Log tab and the connection chip say "Mix It Up did not answer in 5 seconds". If the balance address fails 3 times in a row while the stream is live, the System Discord channel gets one "Mix It Up is not answering" post (`watchBalance` in `lib/mixitup-health.ts`; counter `mixitup:balance-fails`, one post per streak, a success resets both). In bridge mode a missing answer shows "TCG Bridge did not answer" after 8 s instead.
- Check: `scripts/check-two-way.mts`.

## TCG Bridge (site side)
ROADMAP 55.0. Mix It Up cannot answer an HTTP request with custom JSON, so the four outgoing addresses cannot work against stock Mix It Up. In **bridge mode** (the default for new settings) the site never calls Mix It Up: a desktop app on the stream PC, TCG Bridge (55.6), long-polls the site for jobs, runs them through Mix It Up's local Developer API and posts the results. `lib/bridge-core.ts` is pure (shapes, pair codes, token hashing, result to reply); `lib/bridge.ts` is the KV side; the routes are thin.
- **Settings**: `connection: 'bridge' | 'addresses'` and `currencyId` (the Mix It Up currency GUID; `currency` stays the display name, and the save copies it from the bridge's `hello` list). Settings saved with no `connection` read as `addresses` when any of the four addresses is set, else `bridge`, so an existing setup does not change. The Connection tab's form (`ConnectionSwitch`) shows either the currency select (filled from the last `hello`, "Pair TCG Bridge first" before one) or the four addresses, secret, balance field and currency name; both groups stay in the form so a save keeps the other mode's values. Switching on needs a currency in bridge mode and the balance address in addresses mode. `hasBalanceRoute / hasAddRoute / hasViewersRoute` (`mixitup-core.ts`) are the "is this possible" checks the buffs and the Try it buttons use.
- **Transport**: every outgoing call in `lib/mixitup.ts` goes through `callOut`, which is `callBridge` in bridge mode and `callMixItUp` otherwise; callers keep their logic and parse the same `Reply`. `callBridge` pushes a job (RPUSH `bridge:jobs`), then reads `bridge:result:<id>` every 250 ms for up to 8 s. No result is `ok: false`, "TCG Bridge did not answer", exactly like Mix It Up not answering, so a reservation is refused and released and nothing is charged. The balance is read from `balance` whatever the balance field says. Health (`noteOutgoing`) is noted as before. A sandbox or preview never creates a job. `bridgeSay(text)` queues a fire-and-forget `say` job (the stream start and end posts use it, see Chat and Brie Bucks). The Try it "Send test message" sends a `say` job with the rendered message and waits, so the bridge must post a result for `say` too.
- **Jobs** (`bridge:jobs`, a list): `{ id, kind: 'balance' | 'deduct' | 'add' | 'viewers' | 'say' | 'obs-refresh' | 'run-command' | 'pull-event' | 'backup' | 'ledger', username?, amount?, currencyId?, text?, commandId?, args?, phase?, at }`. `text` is the chat message of a deduct, or the line of a say; `commandId` and `args` are a `run-command` (below). A job older than 5 s is dropped when it is claimed (the waiter gives up after 8 s, so a claimed job has at least 3 s to run), as is anything malformed.
- **Results**: `POST /api/bridge/result` `{ id, ok, balance?, users?, error? }` writes `bridge:result:<id>` for 60 s. A `balance` result needs `balance` (a number, 0 or more), a `viewers` result needs `users` (strings, capped at 5000); `ok: false` carries `error`.
- **Late results**: when the waiter gives up (8 s) it writes `{ id, ok: false, error, late: true }` to `bridge:result:<id>` with NX, and a result that arrived first (the NX write fails) is used instead. The result route also writes with NX, so a result posted after the waiter gave up gets `409 { error, late: true }` and is dropped; a repeat of a stored result is a plain 200. The app's rule on a 409: for a `deduct` job it undoes the deduct (adds the amount back), for an `add` job it takes the amount back; `balance`, `viewers` and `say` need nothing. The site has already refused the pull (no print, allowance returned) or marked the grant unpaid, so this keeps the viewer from paying twice.
- **Endpoints** (Node, all POST JSON): `/api/bridge/pair` `{ code, name }` returns `{ token }` once; `/api/bridge/poll` `{ version? }` holds the request up to 25 s and returns `{ jobs }` (empty on timeout; LPOP is atomic, so a job reaches one poller; `maxDuration` 40); `/api/bridge/result`; `/api/bridge/hello` `{ version, currencies: [{ id, name }], commands?: [{ id, name }], commit? }` (commands since 0.4.0, see Big pulls; `commit` since 0.12.0 is the short sha of the commit the app was built from, kept by `cleanHello` only as trimmed lowercase hex of at most 40 characters and stored beside the version in `mixitup:bridge`, empty from an older app or a dev run) answers `{ ok, channel, currencyId }` (the channel name from `CHANNEL_NAME` and the chosen currency's id, which the app's self-tests use; an older app ignores both); `/api/bridge/report` (55.6b, below).
- **OBS report** (ROADMAP 55.6b): `POST /api/bridge/report` takes `{ type: 'stream', live }` (the stream output started or stopped, and once when the app connects to OBS) and `{ type: 'obs', connected, scene, overlay: { found, inProgram, visible, sourceName } }`; anything else is a 400. A stream report goes through `setLiveFromBridge` (`lib/twitch-live.ts`): it calls `setLiveFromHint` only when it differs from the current `twitch:live:hint`, so a reconnect does not refresh the 5 minute override and Mix It Up's own stream webhook still works the same way. An OBS snapshot is validated by `cleanObs` (strings capped at 100) and stored with the time in `bridge:obs`; the overlay address and key are never sent, only the source's name. The Mix It Up page chip row and Admin > Settings > OBS Overlay > Connection show it through `obsChip`: "OBS: overlay visible in <scene>", "OBS: overlay not in the current scene (<scene>)", "OBS: overlay hidden in <scene>", "OBS: overlay source not found", or "OBS not connected" (the snapshot says so, or the last one is over 60 s old; the app resends an unchanged snapshot every 30 s). Nothing shows until a bridge has reported OBS once, so a setup that never turns OBS on sees no change.
- **Refresh overlay in OBS**: the Connection panel on Admin > Settings > OBS Overlay has a button (only when a bridge is paired) that queues an `obs-refresh` job (`refreshOverlayInObs`, waits like `callBridge`) and shows the answer in words: refreshed, or "OBS is switched off in TCG Bridge", "TCG Bridge is not connected to OBS", "The overlay browser source was not found in OBS", "TCG Bridge did not answer". `requireAdmin`, audited. It is the same as right-clicking the browser source and choosing Refresh cache of current page, which is needed after a deploy.
- **Auth** (`POST /api/bridge/twitch-token`, 58.1, goes through the same guard; see Twitch channel below): every route but `pair`, `link` and `link/poll` needs `Authorization: Bearer <token>`; the sha256 of the token must be a field of `bridge:tokens` (value `{ id, name, createdAt, lastSeen, by?, staff?, userId?, login?, role?, roleCheckedAt? }` (`by` = the admin who paired it, or the login for a PC signed in with Twitch; `staff` = the per-PC staff switch, off by default, ignored for a signed-in PC; `userId`, `login`, `role`, `roleCheckedAt` only on a PC signed in with Twitch, 58.0); the token itself is never stored). Unknown, missing or revoked is a 401. All routes call `limitWebhook` first; `pair` also allows 10 tries per address per 10 minutes, `link` 10 per 10 minutes and `link/poll` 60 a minute (`linkGuard`). A poll notes `lastSeen` and `mixitup:bridge` at most every 10 s and ends with a 401 if its token is revoked meanwhile.
- **Pairing**: the TCG Bridge card on the Connection tab makes a code (`createPairCodeAction`: `requireAdmin`, audited, shown as `ABCD-EFGH` with its expiry, never put in a URL). `bridge:pair:<code>` lasts 600 s and the delete is the claim, so a code works once. Paired bridges list with name, paired and last seen, and **Unlink** (`ArmedButton`, `revokeBridgeAction`, audited; removed by the record's `id`, so no token or hash reaches the page). Pairing codes stay until the app can sign in with Twitch (`// shortcut:` in `lib/bridge.ts`).
- **Twitch channel (ROADMAP 58.1)**: the Connections section's **Twitch channel** card (`TwitchChannelCard.tsx`) connects the Twitch account whose events TCG Bridge will read (58.2 onwards). **Connect Twitch channel** (admins only) goes to `GET /admin/mixitup/twitch`, which puts a random `state`, `channel: true` and the admin's login in the `tcg_oauth` cookie and sends the admin to Twitch with scopes `channel:read:redemptions bits:read channel:read:subscriptions user:read:chat user:write:chat channel:bot` (the last three are the chat scopes of 58.6; a channel connected before them shows "Reconnect to allow chat" and keeps every other feature) and `force_verify` (so a spare account can be picked). Twitch returns to the site's existing `/auth/twitch/callback` (no new redirect URL to register on the Twitch app, no new public route): a cookie marked `channel` is handled by `channelReturn`, which needs the signed-in admin, checks the state against the cookie and that admin (`channelStateOk`), exchanges the code, looks up the account with Helix and refuses a grant missing a scope (the token is revoked, nothing changes). No viewer session is made. Any Twitch account can be connected; when its login is not `CHANNEL_LOGIN` the card says "Testing on <login>, not the live channel" (`isTesting`, `testing` in `ChannelStatus`; the app's Status tab and the checklist can read the same flag in 58.2). `twitch:channel-auth` = `{ userId, login, scopes, refreshToken, connectedAt, by }` with the refresh token encrypted by `encryptBackup` (`lib/backup-core.ts`, key `BACKUP_ENCRYPTION_KEY`, so the card needs that key and the Twitch client id and secret; changing the key makes the stored token unreadable and ends the connection). The access token is never stored; no token is logged or put in an error. `refreshAccessToken` (`lib/twitch-channel-core.ts`, pure, takes `fetch`) swaps the refresh token for an access token and returns the new refresh token if Twitch sent one (saved); a 400 or 401 is a rejection and `channelAccessToken` then deletes the key, writes the audit line "Twitch channel disconnected, Twitch rejected the token" and sends a staff notice (`attention`, "Twitch channel disconnected"); a 5xx or network error leaves the connection alone. One refresh at a time (`twitch:channel-auth:refresh`, NX, 15 s). **Disconnect** (`ArmedButton`, `disconnectTwitchChannelAction`: `requireAdmin`) makes an access token from the refresh token, revokes it at Twitch (best effort) and deletes the key. Audit lines (shown for everyone): "Twitch channel connected" (login, plus "testing" when it is not the live channel) and "Twitch channel disconnected" (login). **Bridge route**: `POST /api/bridge/twitch-token` (`bridgeStaffGuard`, then `staffRefusal` for the name `twitch-token`, which is not in `STAFF_CAPABILITY` and so needs an admin; an old paired PC needs its staff switch) answers `{ accessToken, expiresAt, userId, login, clientId, testing }` (58.2 added `clientId`, which the app needs for the Helix `Client-Id` header, and `testing`, the same flag as the card) with `Cache-Control: no-store`, 30 calls a minute per PC (`bridge-twitch-token`, 429), 404 when nothing is connected, 409 when Twitch ended the connection, 503 when Twitch could not be reached. `scripts/check-twitch-channel.mts` covers it against the mock KV and a faked Twitch.
- **Twitch events (ROADMAP 58.2, TCG Bridge 0.38.0)**: while a channel is connected the app opens Twitch's EventSub WebSocket, creates six Helix subscriptions per session (channel point redemptions, cheers, gifted subs, raids to the channel, stream online, stream offline; 58.6 adds a seventh, `channel.chat.message`, see Chat commands through TCG Bridge below) and hands every notification to the site. **Route**: `POST /api/bridge/twitch-event` `{ messageId, type, event }` (`bridgeStaffGuard`, then `staffRefusal` for the name `twitch-event`, so an admin PC only; 120 calls a minute per PC, 429; body at most 16000 bytes, 400 for bad JSON or a type or event that does not fit `cleanTwitchEvent`). `recordTwitchEvent` (`lib/twitch-events.ts`, pure shapes in `lib/twitch-events-core.ts`) answers 200 with `recorded`, `duplicate` or `ignored`: nothing connected and an event for another channel are ignored; the message id is claimed with `SET NX EX 600` (`twitch:event:<id>`, 10 minutes), so a repeat Twitch sends after a reconnect is a `duplicate`; the event goes on the capped `twitch:events` list (newest first, 30 kept) that the Twitch channel card shows, with the result of its award for a redemption (`result: { ok, text }`, shown after the line in brackets). **Channel point redemptions run their reward's award (58.3, see Event rewards, "Channel points"); gifted subs, cheers and raids run the Event rewards rules (58.4, see Event rewards, "Bits, gifted subs and raids from Twitch"); the result is stored with the event like an award's.** `stream.online` and `stream.offline` call `setLiveFromBridge` (the same live state OBS feeds), except when the connected account is a spare test account (`testing`), whose streams are not the live channel. The app shows them in its Live feed (58.5, TCG Bridge 0.41.0): a redemption's line and the stream online and offline lines go on the same `mixitup:events` list the Mix It Up event commands use (a redemption through `logMixItUp` as event `redeem`, with its award result; stream online and offline through `noteFeedEvent` as `stream-online` and `stream-offline`, no viewer, not for a test account's stream), so the app's existing `events` poll shows them under Events with no new route: E when nothing was refused, ! when the award failed (including "awards paused"). Cheers, gifted subs and raids already get their feed line from the 58.4 rules. A redemption of a reward with no award is still ignored and has no feed line. **Report**: `POST /api/bridge/report` takes `{ type: 'twitch', state, reason, login, testing, since, subs }` from an admin PC only (403 otherwise; `cleanEventSubReport`) and stores it in `twitch:eventsub`; the Connection tab's Twitch channel card reads it as "TCG Bridge listening on <PC> since <time>, last event <time>" (or "no event yet"; green, `listeningLine`), followed by the newest forwarded events, or otherwise the problem in amber (the app's reason, "TCG Bridge has not reported lately" or "TCG Bridge has not reported a Twitch connection yet"), and treats a report older than 3 minutes as stale (the app repeats it every minute while it runs). `scripts/check-twitch-events.mts` covers the route, dedupe, the list cap, the test account and the report against the mock KV (`scripts/check-twitch-event-rewards.mts` the 58.4 rules and switch-over); the app side is checked against a fake EventSub server and a fake Helix (`bridge/scripts/check-eventsub.ts`).
- **Chat commands through TCG Bridge (ROADMAP 58.6a, site half; 58.6b, TCG Bridge 0.42.0)**: chat commands run from Twitch chat instead of Mix It Up. **Command list**: `POST /api/bridge/chat-commands` (`bridgeStaffGuard`, `staffRefusal` for the name `chat-commands`, so an admin PC only; 30 calls a minute per PC, 429) answers `{ commands, chat }`: `commands` are the first words with their "!" and lowercased (`commandWords`, `lib/twitch-chat-core.ts`): `!pack`, `!showoff` and every switched-on Chat commands card command with its aliases; `chat` is false until the channel is connected with the chat scopes. **The app (58.6b, TCG Bridge 0.42.0)**: when EventSub connects or reconnects, and every 5 minutes while it is connected, the app fetches the command list (it keeps the last good list when a fetch fails, and a 403 or 404 means chat is off). Only when `chat` is true does it add a seventh subscription, `channel.chat.message` (version 1, broadcaster and user = the channel); otherwise it leaves it out, and the other six work as before. When `chat` flips, the app reconnects so the subscription matches. For each chat message it reads the first word of the text, lowercased, and forwards the event only if that word is in the list; all other chat is dropped on the PC, never forwarded or logged (the log keeps only the message id and the command word). The app's Twitch connection says "Chat commands: N commands, through TCG Bridge", or "Chat commands: reconnect the channel on the site to allow chat". **Receiving**: the app forwards `channel.chat.message` events to `POST /api/bridge/twitch-event` (`cleanChatEvent`: message id, chatter login, text at most 500 characters, at most 30 badges). `recordTwitchEvent` (after the envelope dedupe) hands it to `runChatMessage` (`lib/twitch-chat.ts`) and does not put it on the `twitch:events` list: no chat text is stored. A message whose first word is not a known command, and one sent by the bot account itself, is ignored. The chat message id is the dedupe key in place of `requestId` (`twitch:chat:<id>`, `SET NX EX 600`; the claim is released if the command throws). `!pack <rest>` runs `queuePull` with `chat: true` and `pack` from the rest of the message (after `liveGate('pull')`, logged to the Mix It Up log as "from Twitch chat"); a Chat commands card command runs `runCommand`; `!showoff` runs the Chat commands card's `showoff` command when it is there and switched on (it is by default, through `runCommand`), and otherwise falls back to `queueShowOff` (after `liveGate('collection')`). The role comes from the badges (`badgeRole`): broadcaster, moderator, vip, subscriber (a founder too), else regular. **Replies**: `sendChatReply` posts `POST https://api.twitch.tv/helix/chat/messages` `{ broadcaster_id, sender_id, message, reply_parent_message_id }` (the message id replied to), 500 characters at most, nothing for an empty message. At most 1 reply a second and 20 in 30 seconds (KV counters `rl:twitch-chat-1s:all` and `rl:twitch-chat-30s:all`); an extra reply is dropped with a console line and a Mix It Up log line, never queued. The sender is the channel account, or the bot account when **Reply as: bot** is chosen (`twitch:chat-reply-as`); if the bot's token or the send fails, the channel account sends it instead and staff get one notice "Chat replies fell back to the channel account" (`twitch:chat-bot-fallback`, 5 minutes). A channel without the chat scopes sends nothing ("Reconnect to allow chat"). **Bot account** (Connection tab, Chat replies): **Connect bot account** (`GET /admin/mixitup/twitch-bot`, admins only) starts a second OAuth with scopes `user:bot user:write:chat` and `force_verify`, the state cookie marked `bot: true` with the admin's login (`botStateOk`); the same `/auth/twitch/callback` finishes it (`botReturn`, `connectBot` in `lib/twitch-bot.ts`) and refuses the channel's own account. The refresh token is encrypted at `twitch:bot-auth` like the channel's (refresh lock `twitch:bot-auth:refresh`; a token Twitch rejects removes the connection and writes an audit line). **Disconnect bot** (`disconnectTwitchBotAction`) revokes the token, deletes the key and audits "Twitch bot account disconnected". **Switch-over**: while `twitchHandlesEvent('channel.chat.message')` is true (the live channel, not a test account, a connected report no older than 3 minutes with that subscription enabled), `/api/webhooks/pull` (a request without `event`), `/api/webhooks/show-card` and `/api/webhooks/command` answer `{ ok: true, ignored: true, reason: 'from_twitch', message: '' }` (`chatFromTwitch`); when it is false they work as before. `/api/webhooks/buff`, the event commands (a pull request with `event`) and the paid-pull currency calls are not affected. The Chat commands card, the helper, the `!pack` setup card and the setup wizard say "Chat commands now come through TCG Bridge; the Mix It Up commands are only a fallback" while it is true, and the wizard's `!pack` step becomes optional. `scripts/check-twitch-chat.mts` covers all of this against the mock KV, a faked Twitch and a faked Helix.
- **KV keys**: `twitch:channel-auth` (the connected Twitch channel, 58.1), `twitch:bot-auth` (the optional chat bot account, 58.6), `twitch:chat:<id>` (chat message id claim, 600 s), `twitch:chat-reply-as` (`channel` or `bot`), `twitch:chat-bot-fallback` (the fallback notice throttle, 300 s), `twitch:events` (the last 30 Twitch events, 58.2), `twitch:event:<id>` (message id claim, 600 s), `twitch:reward-awards` (channel points awards by reward id, 58.3), `bridge:award-failed` (the failed-award staff notice throttle, 60 s), `twitch:eventsub` (the app's last EventSub report), `bridge:jobs`, `bridge:result:<id>`, `bridge:pair:<code>`, `bridge:link:<id>` (a Sign in with Twitch request, 10 minutes, 2 once decided) and `bridge:link:<id>:claim` (the NX claim for its one Allow or Deny), `twitch:awards-paused` (`1` while channel point awards are paused from TCG Bridge, 58.5), `bridge:tokens` (hash), `mixitup:bridge` (hash: `at`, `appVersion` (the app's own, stored with each poll), `mixitupVersion` (Mix It Up's, from the `hello`), `commit`, `currencies`, `commands`; an older stored `version` was one or the other and is ignored; the health chip, the currency select and the Big pulls command select), `bridge:obs` (the last OBS snapshot with `at`).
- **Health row**: in bridge mode one chip replaces the four address chips: "TCG Bridge connected (...)" when `mixitup:bridge.at` is within 60 s, else "TCG Bridge not connected" (with the last seen time when there is one). The incoming chips stay.
- `scripts/check-bridge.mts` covers the settings default, pairing, auth, claiming, stale jobs, a fake bridge answering a reserve / charge / refund, the timeout and late results, the report route (shapes, caps, the live hint changing once) and the OBS chips.

## Big pulls (Mix It Up commands on big pulls)
ROADMAP 55.6d. A rule runs one of the streamer's own Mix It Up commands (a sound, lights, a chat line of Mix It Up's own) when a pull on stream is big. Page: the **Big pull rules** card (`PullRules.tsx`). Pure part `lib/pull-rules-core.ts` (`matchRule`, `cleanRulesInput`, `rulesFromForm`, `pullArgs`), firing in `firePullRules` (`lib/mixitup.ts`), the queue call `bridgeRunCommand` (`lib/bridge.ts`), actions in `mixitup-actions.ts`, `scripts/check-pull-rules.mts`.
- **Rules** live in the Mix It Up settings (`mixitup:settings`, `pullRules`): up to 10, each `{ id, on, when: { minRarity?, variants?, newToDex? }, commandId }`. There are none by default and a new rule starts switched on in the form. A pull meets a rule when it meets every condition that is set (`minRarity` = at least that many stars, 2 to 5, 1 star is every card so it is stored as nothing; `variants` = one of the ticked versions, none = any; `newToDex` = the viewer's first copy of that card). A rule with no condition meets every pull. **The first switched-on rule that matches runs and the rest are skipped.** The Paid pulls form does not carry the rules, so saving it keeps them; the settings are read through `normalizeRules`, which drops anything unusable.
- **Saving** (`savePullRulesAction`: `requireAdmin`, audited, `revalidatePath`): a command must be one of the ids TCG Bridge last reported (`mixitup:bridge.commands`); while that list is empty (the app is off for a moment) a rule may keep the command it already had but no new command is taken. Rarity must be 1 to 5, versions known, at most 10 rules, no repeated rule id. The card has one row per rule (rarity at least, run, versions, new to the dex, On, **Test**, **Delete**) plus an empty "Add a rule" row; a row with no command is skipped. With no command list the Run select says "Pair TCG Bridge to choose a command". **Test** queues the saved rule's command once with a made-up pull (`cheesyviewer`, Gouda Goat, Epic, Full Art Holo) and does not wait; **Delete** removes the saved rule and keeps no other edit on the form.
- **When it fires**: on the reveal. The overlay queues pulls in the browser and saves each one with `POST /api/collection` when it starts showing it, so the server-side moment is the save that claims a pull ticket, which is a few seconds BEFORE the card flips. So the command is held back to land on the flip: the overlay sends `revealInMs` (save to reveal, `at(R.reveal)` in `public/widget.js`, so it follows the style, speed and start delay), the route clamps it to 0..15000 (3000 when an old cached overlay sends none, `revealDelay` in `lib/pull-rules-core.ts`) and puts it in the job as `delayMs`; the Test button sends none. `POST /api/collection` calls `firePullRules` from the same `after()` as the `cardPulled` webhook, with the facts it already worked out for the activity event: the ticket's stars, the variant and `isNew` (no copy of that card before). So a pull saved without a ticket, a test-panel or "Don't save" pull (never saved), a refused or revoked paid pull and a webhook grant (`grant-card`) never fire, and a ticket works once, so a pull queues one job at most. A sandbox queues nothing and neither does a site with no paired bridge (checked with `listBridges`). The save never waits on it and a failure is swallowed.
- **The job**: `{ id, kind: 'run-command', commandId, args: [viewer, card name, rarity label, version label], delayMs?, at }`, at most 10 args of 200 characters. The app waits `max(0, min(delayMs, at + delayMs - now))` (at most 15 s, so time already spent in transit counts) before it runs the command, and a waiting `run-command` is handled apart from the job loop (`commandWait` in `bridge/src/jobs.ts`, `pollLoop` in `service.ts`) so a balance or deduct never queues behind a sound. It still posts its result when it has run; stopping the app cancels a wait. A 0.4.0 app from before this change ignores `delayMs` and runs at once. The site does not wait for a result (the app still posts one, which expires). A job older than 5 s is dropped when claimed, which is fine for fire and forget. TCG Bridge before 0.4.0 does not know the kind and ignores the job.
- **The command list**: since 0.4.0 the app sends `commands: [{ id, name }]` in `hello` (enabled Mix It Up commands with a name and a GUID id, at most 500, names cut at 100; `cleanHello` enforces the same) on start, every 5 minutes and when Mix It Up comes back. `storeHello` keeps it beside the currencies in `mixitup:bridge`; an older app sends none and the stored list stays.

### OBS actions on big pulls
ROADMAP 55.8, TCG Bridge 0.6.0. A rule can also act in OBS (all optional, all off until chosen; a rule may have only OBS actions and no command): **Save a clip**, **Switch scene** (to a chosen scene for N seconds, default 8, at most 60, then back) and **Show a source** (while the pack opens, hidden again at the reveal). Scene and source names are picked from the lists the app reports with each OBS snapshot (`scenes`, and `sources` = the items of the scene on air, overlay sources left out, capped at 100 and 200), and `cleanRulesInput` refuses any other name; the job carries only a name and the app checks it against its own last-read list again.
- **Timing**: `POST /api/collection` (the save, when the card starts to show) returns an `eventId`. `firePullRules(pull, delay, eventId)` runs the Mix It Up command as before (queued at save time with `delayMs`, left alone) and `bridgePullStart` queues a fire-and-forget `pull-event` job `{ phase: 'start', source, holdMs }` and keeps the scene and clip part under `bridge:pullevent:<eventId>` (120 s). When the overlay reveals the card, `public/widget.js` posts `{ id, reveal: eventId }` to `/api/overlay/heartbeat` (overlay key as always; it records no heartbeat). The route claims the key (the `DEL` count, so a repeat queues nothing) and queues `{ phase: 'reveal', scene, secs, clip }`. An old overlay never reports, so only the source part runs. Nothing waits for a result; a failure shows only in the app's log.
- **In the app** (`ObsWatcher.showSource / switchScene / saveClip`): the source is enabled in the scene on air and disabled again after `holdMs`; the scene is changed and put back after N seconds only if nobody changed it meanwhile; a clip is `SaveReplayBuffer` 5 s after the reveal, and when the replay buffer is off the job answers `The OBS replay buffer is off, so no clip was saved`. The OBS connection (Connections page, 0.31.0) has a switch **Start the replay buffer when the stream starts** (off by default; `obsStartReplay` in settings.json; applied when the stream goes live or on connecting to a live OBS).
- **Test** on a rule queues both phases at once (source for 3 s, then the scene switch and clip).
- **Overlay watchdog** (63.3: its own panel on Connections, `WatchdogPanel`, `saveWatchdogAction`; the switch **Refresh the overlay in OBS when it goes quiet**, `overlayWatchdog`, off by default; `lib/overlay-watchdog.ts`): while the stream is live, if the newest overlay heartbeat is over 30 s old and the last OBS snapshot shows the overlay source visible in the scene on air, the site queues an `obs-refresh` itself, at most once per 5 minutes (a `SET NX EX 300` lock, `mixitup:watchdog:lock`), writes a Log line (`watchdog`), and the health row says when it last did (`mixitup:watchdog`). It runs from `POST /api/bridge/report`, which the app calls at least every 30 s while connected, so there is no cron; with the switch off it costs one settings read per report.
- Checks: `scripts/check-big-pulls-obs.mts` (names, reveal path, once-only claim, watchdog rules) and, in `bridge/scripts/check.ts`, the fake OBS answering `SaveReplayBuffer`, `SetCurrentProgramScene` and `SetSceneItemEnabled`.

## Chat and Brie Bucks
ROADMAP 55.10, TCG Bridge 0.8.0. The **Stream start and end** card (`saveChatAction`) and the **Brie Bucks safety** panel on Connections (`saveChatSafetyAction`; 63.3, each saves only its own switches) ( `requireAdmin`, audited, `revalidatePath`) holds four switches, `chat` in the Mix It Up settings (`ChatSettings` in `lib/bridge-chat-core.ts`, pure). **All are off by default**, and nothing below runs in a sandbox or without a paired bridge. Server side `lib/bridge-chat.ts`, check `scripts/check-bridge-chat.mts`, app side `bridge/src/bucks.ts`.
- **Stream start and end** (`streamStarted`, `streamEnded`, called from `lib/twitch-live.ts` through a dynamic import because this file reads the Mix It Up settings): the start is the first sighting of a stream (`applyStatus` sets `twitch:live:since` with NX, so it happens once however many reports say "live"); the end is `finishStream`, after its lock. **Start post** is a `say` job, default "Packs are open: type !pack" (variable `{channel}`). **End post** is a `say` job with `{topPull}` (the rarest pull, "card by viewer"), `{topPullers}` ("name (packs), ..." for the top three, `topPullers` in the recap) and `{channel}`; it is skipped when nobody pulled. Wording is editable (300 characters, a blank falls back to the default, an unknown `{variable}` stays as typed).
- **Big pull shout**: a Big pulls rule has an optional **Say in chat** line (`say`, 300 characters, variables `{viewer} {card} {rarity} {edition}`; `{edition}` is the copy number as `#12`, empty when the pull has none). A rule may be only a chat line. It rides the 55.8 reveal path: `firePullRules` renders it and `bridgePullStart` keeps it as `text` under `bridge:pullevent:<eventId>`, the overlay's reveal report queues it in the `pull-event` reveal job, and the app says it before the scene and clip. It is never sent at the save, so chat never spoils a card the overlay has not shown. An old overlay that never reports a reveal says nothing. Test on a rule sends the line with the sample pull.
- **Brie Bucks backup**: at the start and end the site queues a `backup` job (`phase` `start` or `end`, `currencyId`; bridge mode with a currency only). The app reads every viewer from Mix It Up (`GET /api/users/top?count=100000`, 60 s timeout; Mix It Up has no list-all route and leaves bots out) and writes `brie-bucks-YYYYMMDD-HHMMSS-<start|end>.csv` (`username,twitch_id,amount`, only viewers with some) to `Documents\TCG Bridge\backups`, keeping the newest 30. The app's App page has **Open backups**. It runs apart from the job loop so a charge never queues behind it.
- **Brie Bucks check**: the app keeps a ledger (`ledger.json` in its data folder, the last 2000 rows) of every deduct and add it ran: job id, viewer, signed amount, the time the site queued it and Mix It Up's answer (a deduct it undid after a late result adds an `<id>:undo` row). The site keeps its own record, `bridge:charges` (a list, 2000 rows: id, viewer, signed amount, time), written by `callBridge` for every deduct and add (the Mix It Up log keeps only 20). At the end of a stream the site writes `bridge:check:pending` (the stream's window, 1 h) and queues a `ledger` job; the app answers by posting `{ entries }` to `POST /api/bridge/ledger` (bridge token, like every bridge route). `receiveLedger` claims the pending key (so one check per stream), compares the two lists for that window by job id and lists the jobs one side has and the other lacks, or has with another amount (`compareLedgers`). Balances are not compared. The result is `bridge:check:last`, shown on the tab ("Last Brie Bucks check") and written to the Log as a `check` line. A switched-off app, a bridge that is offline for the 5 s a job stays fresh, or a missing answer means no check that stream, silently.

## Streamer tools
ROADMAP 55.11, TCG Bridge 0.9.0. Switches are on the app's Notifications and App pages and are off by default; the app side is described in `bridge/README.md`.

ROADMAP 55.14. "Simulate a chat pull" on the Stream page's Test section (the **Test pulls** card) runs a chat `!pack` end to end and shows each step. - **Undo** (`undoTestPull`, per pull and in the last-five list): removes the edition from the test collection, pays a paid pull back through `grantCurrency` (the add route) and audits. It refuses anything that is not a saved test pull, and a second undo. It is not on the viewer's admin page.

## TCG Bridge app (the stream PC side)
ROADMAP 55.6a. `bridge/` is a small Windows app (Electron + TypeScript, its own `package.json`, app id `app.cheesytcg.bridge`) that sits in the tray on the stream PC, long-polls the site for jobs, runs them against Mix It Up's Developer API on `http://localhost:8911` and posts the results. It never fetches any address but the paired site and `localhost:8911`, and ignores job kinds it does not know. Since 0.2.0 (55.6b) it can also talk to OBS on the same PC; see "OBS in the app" below. Since 0.3.0 (55.6c) it also alerts, tests itself, can start Mix It Up and keeps a log; see "Reliability and self-help" below.
- **Install**: the TCG Bridge card on the Stream page's Connections section has **Download TCG Bridge** (the GitHub releases tagged `bridge-v*`, newest first). Under the card one line compares the running app with the latest release ("Out of date: 0.12.0 running, 0.13.0 available."), from the same lookup as the dashboard card (`lib/bridge-release.ts`, ROADMAP 56.2). The installer is **not code-signed**: Windows SmartScreen shows "More info", then "Run anyway". Per-user install, no admin rights. It starts with Windows (on by default, a checkbox in the window) and, once paired, starts minimised in the tray.
- **Sign in with Twitch** (TCG Bridge 0.35.0, ROADMAP 58.0b): the first thing on the app's Connect screen. Press it, the app shows a code and opens the site in your browser; sign in with Twitch there, check the code matches and press Allow. No code to type and no Admin page visit.
- **Pair** (the fallback, behind "Use a pairing code instead"): on the app's Connect screen (the whole window until the PC is signed in or paired, 0.31.0, ROADMAP 59.6) type the site address (default `https://cheesytcg.app`) and the code from **Pair TCG Bridge** (ABCD-EFGH, works once, 10 minutes). The app sends the computer name as its name. The token is stored with Electron `safeStorage` (Windows encryption, tied to the Windows user) in the app's user data folder and never leaves the PC. **Unpair** in the app (the TCG account connection on the Connections page; it asks twice; **Sign out** for a PC signed in with Twitch) forgets it there; **Unlink** on the site makes the app show "Sign in again" on the Connect screen.
- **Statuses**: tray icon green = site and Mix It Up both fine, amber = one of them, red = neither. The Connections page (0.31.0) lists TCG account (address, the account: "Signed in as <login> (<role>)" for a PC signed in with Twitch or "Paired as <name>" for one paired with a code, shown as **Account** in the detail; last poll; state: Connecting, Connected, Cannot reach the site, Not paired), Mix It Up (found, version, the currency the site last used), OBS and the Stream Deck plugin (0.34.0, ROADMAP 61.1: needs Stream Deck 7.1 or newer; "installed but not linked" says whether the link is off, the app is not listening or the plugin has not connected, and the status pill offers a Fix that opens it; 0.40.0 adds Refresh overlay and Run checklist keys, see OBS and overlay keys below), each with a dot and a one-line state, and numbered fix steps when one needs fixing; the jobs are rows in the Home live feed (the last 50) with their results. "Mix It Up: No" means nothing answers on port 8911: Mix It Up is closed, or its Developer API is off (Mix It Up > Services > Developer API > Connect). The app checks every 5 s and sends `hello` (version, currencies) on start and each time Mix It Up comes back.
- **Loop**: after a normal answer the app polls again at once; after an error it backs off 1 s, doubling to 30 s. A 401 anywhere stops the loop: the Home chip says "Sign in again" and the Connect screen shows "This PC was signed out on the site. Sign in again to carry on." A result is posted with up to 3 quick retries (network error or 5xx). A 409 `late` means the site gave up on the job: a `deduct` that went through is given back, an `add` is taken back, the others need nothing. Mix It Up not running answers each job "Mix It Up is not running" at once.
- **Jobs to Mix It Up** (V1 Developer API, PascalCase JSON; `username` is lowercased and must be a Twitch login, `currencyId` a GUID): `balance` = `GET /api/users/twitch/{name}`, the `CurrencyAmounts` entry with that `ID` (404 = 0). `deduct` = the same lookup, refused with "Not enough <currency>" when the balance is short (never negative), then `PUT /api/users/{user ID}/currency/{currencyId}/adjust` `{ "Amount": -n }`; the user ID from the lookup is used because that route resolves a name on the streamer's default platform, not necessarily Twitch. After a good deduct the job's `text` is posted to chat. `add` = the same adjust with `+n` (a viewer Mix It Up does not know is refused). `viewers` = `GET /api/chat/users`, the users with a `TwitchID`, lowercased and deduped. `say` = `POST /api/chat/message` `{ "Message", "SendAsStreamer": false }`. `hello` currencies = `GET /api/currency` (`ID`, `Name`); the version = `GET /api/status/version`.
- **Updates**: `electron-updater` checks the latest GitHub release on start (in the start-up window, installed at once) and every 6 hours (installed on quit). To release: bump `version` in `bridge/package.json`, merge, push the tag `bridge-v<version>`; `.github/workflows/bridge.yml` builds on `windows-latest` and attaches the installer, its blockmap and `latest.yml` to a release of that tag. The updater reads the repo's latest non-prerelease, so every full release in this repo must be a bridge release (mark anything else a pre-release). The window shows the app version and a **Check for updates** button (answers "You are up to date", "Downloading version x.y.z" or "Version x.y.z is ready ... (restart to update)"; only in the installed app). The last version the window saw is kept in the settings; after an update the window shows "Updated to x.y.z" with **See what changed** (opens `https://github.com/JoshMiles/tcg/releases/tag/bridge-vx.y.z` in the default browser) and **Dismiss**, until one of them is used. The first run ever says nothing.
- **OBS in the app** (0.2.0, ROADMAP 55.6b; `bridge/src/obs.ts`, no Electron imports): off by default. The OBS connection on the app's Connections page (0.31.0; an OBS card before) has a "Talk to OBS" switch, the address (default `ws://127.0.0.1:4455`; only `ws://localhost:<port>` or `ws://127.0.0.1:<port>` is accepted) and the password, which is stored with `safeStorage` like the token and never sent to the site. In OBS (28 or newer) it is Tools > WebSocket Server Settings > Enable WebSocket server, Server Password (leave the app's field empty if authentication is off). While on, the watcher uses obs-websocket v5 (JSON subprotocol) and reconnects with a 1 s to 30 s backoff; the window shows connected or why not ("Wrong OBS WebSocket password", "OBS is not running, or its WebSocket server is switched off"), the program scene, the stream state and the overlay check. The tray goes amber when OBS is on but not connected; OBS off does not count.
  - **Requests**: `GetStreamStatus`, `GetCurrentProgramScene`, `GetInputList` (`inputKind: browser_source`), `GetInputSettings`, `GetSceneItemList`, `GetGroupSceneItemList` and, for the refresh, `PressInputPropertiesButton` (`propertyName: refreshnocache`). **Events** (subscriptions Scenes, Inputs, Outputs, SceneItems): `StreamStateChanged` (only `OBS_WEBSOCKET_OUTPUT_STARTED` and `..._STOPPED` count), `CurrentProgramSceneChanged`, `SceneItemEnableStateChanged`, `InputSettingsChanged`, `InputCreated`, `InputRemoved`, `InputNameChanged`; the last six trigger a re-check after a 1 s debounce.
  - **The overlay check**: a browser source is the overlay when its URL is on the paired site's host (a leading `www.` ignored) with the path `/overlay.html`; the key and other parameters are ignored and never sent. It counts as in the program when it is an item of the current scene, or of a group in it (one level), and as visible when the item (and its group) is enabled. If several sources match, a visible one in the scene is reported. **Not seen**: an overlay inside a nested scene (a scene used as a source) counts as not in the scene.
  - **Reports** (`POST /api/bridge/report`, see above): `stream` when the output starts or stops and once on connect; `obs` on connect, on disconnect, on any change, at most once a second, and unchanged every 30 s as a heartbeat. Turning OBS off in the app or quitting sends a disconnected snapshot. A failed report is not retried; the next change or heartbeat tells the site.
  - **The `obs-refresh` job** presses "Refresh cache of current page" on every matching browser source and answers `ok`, or `ok: false` with a reason in words when OBS is off, not connected, or no overlay source exists. It gives up after 4 s.
- **Mix It Up commands** (0.4.0, ROADMAP 55.6d): `GET /api/commands` (`CommandV1Controller`, route `api/commands`) lists `[{ ID, Name, IsEnabled, Category, GroupName }]`; the app keeps the enabled, named ones and sends `{ id, name }` in `hello`. A `run-command` job is `POST /api/commands/{id}` with a JSON array of strings as the body (the command's arguments, `$arg1text` to `$arg4text`); Mix It Up queues the command and answers 200 at once. The app runs a `run-command` only for an id it reported itself in the last `hello` (case-insensitive) and answers anything else, a bad id or a missing one with "That Mix It Up command is not in the list this app reported"; non-string args are dropped. If the list cannot be read the last good one is kept. A site that sends a kind an older app does not know is skipped without an answer; the kinds are fixed.
- **Reliability and self-help** (0.3.0, ROADMAP 55.6c; plain modules `alerts.ts`, `selftest.ts`, `launch.ts`, `log.ts`, `diagnostics.ts`, `update.ts`; `main.ts` only wires them):
  - **Alerts**: a Windows notification when the site link, Mix It Up or OBS goes from up to down, and one when it comes back. A part counts as down only after 15 s down, so a missed poll never alerts; at most one drop alert per part every 2 minutes (a drop inside that time is shown once the 2 minutes pass, if it is still down); the "back" notice only follows a drop that was shown. Only while the stream is live: "live" is what OBS last said (kept if OBS is then lost; OBS never connected counts as not live). With OBS switched off in the app there is no live signal, so every drop alerts. A part that never came up since the app started, or a revoked site, is not a drop. The window's "Alert me when a link drops while live" switch (saved, on by default) only mutes the notification; the log still records the alert. The decision is the pure `Alerts` class, fed snapshots and a clock.
  - **Pre-stream checklist** (ROADMAP 57.1, TCG Bridge 0.13.0): the **Ready to go live** card (Home page, with **Run again**; since 0.30.0 it shrinks to "All N checks passed at 19:28" when the last run passed; "Checklist" in the tray menu) runs every check at once and shows one line each, green or red, with the reason: site answers, Mix It Up found / currency exists / balance readable, OBS connected (grey "Not used" when Talk to OBS is off), overlay source visible in the scene on air, active season, openable packs, pull queue empty, pulls not paused, happy hour (shown, never red). It only looks: no test chat message, no charge. Each check times out after 5 s. The season, packs, queue, pause and happy hour come from `GET /api/bridge/checklist` (`lib/bridge-checklist.ts`, bridge token, read only: `{ season: { name } | null, openablePacks, queueLength, paused, happyHour: { what, endsAt } | null }`). The app reports the lines back with `POST /api/bridge/report` `{ type: "checklist", lines: [{ label, tone: ok | bad | muted, text }] }`; the site cleans them (`lib/bridge-checklist-core.ts`, at most 12 lines), works out `ready` (no red line), stamps its own time and keeps the last one in KV `bridge:checklist`. The Overview tab's "Pre-stream checklist" panel shows it with "ran N minutes ago". Since 0.41.0 (ROADMAP 58.5) the app adds a **Twitch** line from its own EventSub state (no site call): green "Listening to <login>, all 6 subscriptions enabled", red with the reason when it is not connected (or "Listening, but N subscriptions are not enabled: ..."), grey when no Twitch channel is connected. Checks: `scripts/check-bridge-checklist.mts` (site), `bridge/scripts/check-checklist.ts` (app, with fakes).
  - **Self-tests** (each answers in words next to its button): **Test Mix It Up** checks the Developer API answers (and its version), finds the currency the site chose by id and reads its name, then reads the balance of a Twitch name (the box is prefilled with the channel name from the `hello` answer; a viewer Mix It Up does not know has 0). **Send test chat message** posts "TCG Bridge test message" through `/api/chat/message`. **Check OBS** runs the overlay check now and shows the scene, the stream state and the overlay, or why it cannot (OBS off, not connected).
  - **Start Mix It Up**: when Mix It Up is not found the Mix It Up connection (Connections page, 0.31.0) shows **Start Mix It Up** in its fix steps, and the **Start Mix It Up with TCG Bridge** switch is on that connection. It launches only the saved path, else the default `%LocalAppData%\MixItUp\MixItUp.exe` (where Mix It Up's own installer puts it: `MixItUp.Installer/MainWindowViewModel.cs`, `DefaultInstallDirectory`, in github.com/MixItUpBot/Desktop), and only an existing file named `MixItUp.exe`, detached, with no shell. **Choose MixItUp.exe...** opens a file dialog and saves the path (refused unless the file is called `MixItUp.exe`). **Start Mix It Up with TCG Bridge** (off by default) starts it when the app starts and nothing answers on port 8911.

## Webhook grants look like pulls
The incoming webhooks only accept a real Twitch login as `username` (3 to 25 letters, digits and underscores; a leading `@` is dropped; anything else is a 400), and the grant-card webhook only grants a card number that exists in a published pack of the active season (404 otherwise), so a bad Mix It Up variable fails loudly instead of creating a ghost viewer.

A card granted by the grant-card webhook (a Mix It Up reward) is recorded as `grant` with `source: 'webhook'` plus the facts of a pull (name, stars, pack, new or not, copies, collected, edition). It counts as a **pull** in the Live Activity categories and the Discord Pulls category (with the star and new-only filters), reads "X pulled Y (granted by webhook)" in the live feed and on the dashboard's Recent activity, and posts the same embed as a pull with a "Granted by webhook" line (`pullEmbed` in `lib/discord.ts`). The Live Activity numbers, the stream recap (`asPullEvent` in `lib/activity-view.ts`; there it is listed as a reward rather than a pack opened) and the stats counters behind the weekly digest and the dashboard charts (`recordStats`, from the day this shipped) count it as a pull too. Admin grants are unchanged (Grants & removals, the Cards Discord category, the `grant` counter). Events recorded before this change lack the extra facts and still post, with the card's stars looked up.

## Mix It Up chat commands (Stream page, What viewers get, Chat commands card)
ROADMAP 19.2. One incoming webhook, `POST /api/webhooks/command` (`{ secret, command, username, args? }`, the incoming secret), answers every chat command: `{ ok, message, vars }` plus each variable at the top level for Mix It Up's "JSON to special identifiers". A refusal is `{ ok: false, message }` with the command's own error text; an unknown or switched-off command is `{ ok: false, message: '' }` (silent). `/api/webhooks/show-card` still works unchanged.
- **Pure core** `lib/commands-core.ts`: the `ChatCommand` shape, the fixed action registry `COMMAND_ACTIONS` (each action's variables, sample values and error kinds: `showoff`, `card-stats`, `my-stats`, `collection`, `leaderboard`, `pulls-left`, `text`), `matchCommand` (name or alias, without the `!`), `interpolate` (unknown placeholders dropped), `tidyReply` (no Markdown marks, 400 characters), `cleanCommands` (max 30, unique names). **KV** `lib/commands.ts`: commands in `mixitup:commands` (the defaults `!showoff` and `!stats` are seeded on first read), run counts in `mixitup:cmdstats`, the last 20 runs in `mixitup:cmdlog` (shown on the Log tab, never posted to Discord), cooldowns `cmd:cd:<id>` and `cmd:ucd:<id>:<viewer>` with a TTL. `runCommand` is used by the webhook and by Try it.

## Stream Deck buttons
ROADMAP 55.2. A Stream Deck button is a Mix It Up command (run from the Stream Deck with Mix It Up's plugin) whose Web Request calls `POST /api/webhooks/buff` (`app/api/webhooks/buff/route.ts`, logic in `lib/streamdeck.ts`, `scripts/check-streamdeck.mts`). - **Buffs**: the Buff Editor has a "Stream Deck" checkbox per buff (`BuffDef.streamDeck`, off by default, never for grant-achievement). It runs through `applyBuff` with `source: 'streamdeck'`; refusals come back in words (already active, too many buffs, Mix It Up off or silent, no season). It is a Quick actions download in the Mix It Up commands box (`QUICK_ACTIONS` in `lib/viewers-helper.ts`).

## Event rewards
ROADMAP 55.4g. A Mix It Up event command (gifted subs, bits, a raid, a channel point redeem) calls `POST /api/webhooks/pull` with `{ secret, event, username, amount }`, `event` being `gifted-subs`, `bits`, `raid` or `redeem`. A request with `event` takes this path (`runEventReward`, `lib/event-rewards.ts`; the pure rules and Copy setup text are in `lib/event-rewards-core.ts`, `scripts/check-event-rewards.mts`); one without is the chat `!pack`, unchanged. `username` is who gets the reward (the gifter, cheerer, raider, redeemer); `amount` is a whole number from 1 (subs, bits or raid viewers; a redeem may leave it out), as a number or as text.
- **Settings**: `eventRewards` in `mixitup:settings`, one entry per event `{ on, reward: 'packs' | 'buff', buffId?, every? }`, all off by default. The **Event rewards** card (`saveEventRewardsAction`) changes the four events and the **Raid shout-out** card (`saveRaidShoutoutAction`) changes `raidShoutout`, both through `saveEventRewards` in `lib/viewers-save.ts`; each keeps the other's fields and the other forms keep them all.
- **Packs**: gifted subs 1 per sub; bits `floor(amount / every)` (`every` = bits per pack, default 500); raid 1 pack when `amount >= every` (default 1 viewer); redeem 1. At most 10 per request (`EVENT_PACK_CAP`). 0 packs answers `{ ok: true, message: '' }` and queues nothing. Each pack is `queuePull(username, { free: true, reason })`, never `chat`: no charge, no limit count, no cooldown, no queue cap, no pause or block. The `reason` ("3 packs for 300 bits", "a pack for a raid of 12") shows in the live activity feed ("got a free pack (...)") and, with the chat line, in the Mix It Up log.
- **Buff**: `reward: 'buff'` applies the chosen buff once to `username` with `applyBuff(..., { source: 'event' })`. Only a self buff with the Stream Deck switch on can be chosen (same list as the Stream Deck buffs card); one that is later switched off, deleted or made community answers `ignored` with reason `buff_unavailable`. Refusals (already active, too many buffs, Mix It Up off) use the Stream Deck's words. No cooldown; the audit log gets an "Event reward" line.
- **Answers**: success `{ ok: true, message }` ("cheesy got 3 packs for 300 bits!"); off `{ ok: true, ignored: true, reason: 'event_off', message: '' }`; a bad `event` or `amount` is 400 `{ error, message }`. `requestId` works as on the chat pull (`answerOnce`), so a retry queues nothing more. A failure part way through a batch of packs leaves the earlier ones queued, and a retry would queue them again.
- **Redeem while Twitch handles redemptions (ROADMAP 58.3, decision 3)**: when the live channel is connected (not a test account, `testing` false), at least one channel points reward has an award (below) and the Redeem event is on, a `redeem` request answers `{ ok: true, ignored: true, reason: 'twitch_handles_redeem', message: '' }` (the reason shows in the Mix It Up log, the empty message keeps the command quiet in chat), so a redemption never counts twice. `twitchHandlesRedemptions` (`lib/twitch-awards.ts`; the rule is `twitchHandlesRedeem` in `lib/twitch-awards-core.ts`) is read on each request, no extra setting. With a test account connected, no channel connected, or no award set, the Redeem event works as above. The other event commands (gifted subs, bits, raid) have their own switch-over, next.
- **Bits, gifted subs and raids from Twitch (ROADMAP 58.4, site only)**: `recordTwitchEvent` (after the duplicate message id drop) runs `channel.subscription.gift` (`total` subs, the gifter `user_login`), `channel.cheer` (`bits`, `user_login`) and `channel.raid` (`viewers`, `from_broadcaster_user_login`) through `rewardEvent` in `lib/event-rewards.ts`, the same function the Mix It Up request (`runEventReward`) uses, so packs per sub, bits per pack, the raid threshold, the buff and the cap of 10 are one set of rules and the Event rewards card switches and numbers apply to both (`rewardTwitchEvent`; the `gifted-subs`, `bits` and `raid` entries). Anonymous gifters and cheerers (`is_anonymous`), an amount under 1 and a name that is not a Twitch login get nothing and no result. An event switched off records nothing extra. Otherwise the result (`{ ok, text }`, for example "gift_a got 3 packs for 3 gifted subs", "no pack (under the minimum)", or "raid shout-out shown") is stored with the event on `twitch:events` and shown on the Connection tab, and the Mix It Up log and event feed (57.7) get the same line the request path writes, starting "from Twitch, ". The "only when live" overlay switch (`liveGate('pull')`) applies first, as it does to the request. **Raid shout-out**: a Twitch raid calls `raidShoutout` (57.6) exactly as the Mix It Up raid request does, after the reward and whether or not it earns a pack. **Switch-over (decision 3)**: while Twitch delivers the event, the Mix It Up `gifted-subs`, `bits` and `raid` requests answer `{ ok: true, ignored: true, reason: 'from_twitch', message: '' }` (the reason is in the Mix It Up log; the empty message keeps the command quiet in chat) and the Mix It Up raid does not run the shout-out, so nothing counts twice and a raid is shouted out once. Twitch delivers the event (`twitchHandlesEvent`, `lib/twitch-eventsub.ts`; rule `twitchHandles` in `lib/twitch-events-core.ts`) only when the connected channel is the live one (`testing` false, and the report says so too), the app's latest `twitch:eventsub` report is fresh (not older than 3 minutes, `REPORT_STALE_MS`), its `state` is `connected` and that event's subscription (`channel.subscription.gift`, `channel.cheer`, `channel.raid`) has status `enabled`. Stale, disconnected, reconnecting, off, a missing or failed subscription, nothing connected or a read error all mean the Mix It Up requests work as before, so a dropped WebSocket never loses rewards; each event is judged on its own subscription. The redeem request has its own rule (above). **A test account never switches Mix It Up off**: its events still run the rules, so they can be tried on a spare account, but its Mix It Up requests keep working, so a viewer rewarded by both a test event and a Mix It Up command is rewarded twice during a test. A test account's raid or cheer comes from its own channel, so a raid shout-out it triggers shows on the live overlay and says its line in chat; keep the minimum raid size high or the shout-out off while testing. Check: `scripts/check-twitch-event-rewards.mts`.
- **Channel points (ROADMAP 58.3, site only)**: the **Channel points** card lists the connected channel's rewards, all of them and read-only, from Helix `GET /helix/channel_points/custom_rewards?broadcaster_id=<id>` (`fetchRewards`, `lib/twitch-awards.ts`: `channelAccessToken` and the client id; the URL is a constant base with `URLSearchParams`; fetched on each open of the tab). It says so in words when no channel is connected, Twitch refuses (401, 403), has no rewards to list (400, 404), fails or cannot be reached. When a `channel.channel_points_custom_reward_redemption.add` event arrives at `POST /api/bridge/twitch-event`, `recordTwitchEvent` (after the duplicate message id drop) runs the award of that reward id for `user_login` (`awardRedemption`; the login is cleaned like any viewer name, and no viewer record needs creating: pulls and buffs are keyed by the name, a show-off needs cards). A failed award (no packs, buff already active, happy hour already running, a viewer with no cards, a bad name) sends a staff notice "Refund <viewer>'s <reward> by hand" at most once a minute (`noteAwardFailed`, `lib/bridge-notice.ts`, claim `bridge:award-failed` with `SET NX EX 60`). A test account's redemptions run awards too, so they can be tried on a spare account. **Pause channel point awards (ROADMAP 58.5, TCG Bridge 0.41.0)**: the bridge action `pause-awards` (`on` or a toggle; `status` also answers `awardsPaused`) sets KV `twitch:awards-paused` (`awardsPaused()` / `setAwardsPaused()` in `lib/twitch-awards.ts`) and writes the audit line "TCG Bridge: channel point awards paused" or "resumed" (only when the state changed). While it is on, a redemption is still recorded and gets its feed line, but no award runs: the event result is "<reward> failed: awards paused" and the staff notice (still at most once a minute) says "awards paused", so the viewer is refunded by hand. Nothing changes on Twitch (the rewards stay as they are). The Twitch channel card on the Connection tab shows an amber line while it is on. Check: `scripts/check-twitch-pause.mts`, and `scripts/check-twitch-awards.mts` for the awards.
- **Mix It Up identifiers** (read from github.com/MixItUpBot/Desktop, `EventTypeEnum` in `Services/EventService.cs` and `Services/Twitch/TwitchEventService.cs`; not yet fired from a real Mix It Up): Subscription Gifted (`TwitchChannelSubscriptionGifted`) with `$username` the gifter, one run per lone gifted sub, so `amount` 1; Mass Subscriptions Gifted (`TwitchChannelMassSubscriptionsGifted`) with `$username` the gifter and `$subsgiftedamount`; subs inside a mass gift do not run the lone event (`fireEventCommand: false`), so the two cards do not double count; Bits Cheered (`TwitchChannelBitsCheered`) with `$bitsamount`; Channel Raided (`TwitchChannelRaided`) with `$raidviewercount` and `$username` the raider; Channel Points Redeemed (`TwitchChannelPointsRedeemed`, runs for every redeem; `$rewardname`, `$rewardcost`). Overlay and OBS page, **Live stats in OBS**: each of six stats (packs this stream, last big pull, top puller, happy hour countdown, pack goal progress, queue length) can be mapped to one OBS text source (GDI+ or FreeType, from the list the app read from OBS; a name OBS did not report is refused in `acceptStatMap`). Off by default (`obsStats` in settings.json, nothing mapped), and an unmapped stat is never written. Bridge action `stats` (`{ stats: [keys] }`, `lib/bridge-stats.ts`) answers only what was asked, read-only, with no new KV writes: `queueLength()`, and one `getActivity({ limit: 500 })` for the rest (test pulls excluded; a very long stream is a floor because the log is capped). A big pull is 4 stars or more, as in the feed default; the stream start is `currentStreamKey()`. The app asks every 5 s only while OBS is connected and a stat is mapped, or a Stream Deck plugin key that shows a stat is on a deck (61.2); the happy hour is counted down in the app from the `endsAt` the action returns. Writes are obs-websocket `SetInputSettings` with `text` only, at most once a second per source and only when the text changed (`TextWriter` in `bridge/src/obsstats.ts`); the watcher ignores `InputSettingsChanged` for text sources so its own writes cause no re-read. Texts: "Packs: N", "viewer: card", "Top puller: name (N)", "Happy hour: free packs, 12:34 left", "Pack goal: 37 / 50" (the site sends the finished text, `goal` in the answer, null = no goal for this stream; TCG Bridge 0.18.0, see Community pack goal below), "Queue: N"; a stat with nothing to show clears its source. Unmapping leaves the source's text as it was. Checks: `scripts/check-bridge-stats.mts` and `bridge/scripts/check-stats.ts`.
- **Community pack goal** (ROADMAP 57.5, `lib/pack-goal-core.ts`, `lib/pack-goal.ts`, TCG Bridge 0.18.0). Mix It Up, Paid pulls, **Community pack goal**: a target of packs (1 to 100000), a label (default "Pack goal") and a reward: none, a community buff (scope community, not grant-achievement; applied with `applyBuff`, source "pack goal"), or extra pulls for everyone this stream (added to the stream bonus, capped at the pull limit maximum). Off by default: with no goal set a pull costs one KV read. The goal is stored at `packgoal:goal` with the stream key it was set in; a goal for an earlier stream key reads as no goal, so it resets with `currentStreamKey()` and needs no cron. The count starts when the goal is set (setting again starts from 0): `countPackGoalPull()` runs from `POST /api/collection` inside the `!test` branch (the one place every chat, Stream Deck, event and bridge pull ends), so test pulls never count and a sandbox counts nothing. One `INCR` per pull on `packgoal:n:<setAt>`; the pull whose count equals the target takes `packgoal:done:<setAt>` (`SET NX`) and so is the only one to give the reward, queue one chat line through the bridge (`bridgeSay`) and write the audit line "Pack goal reached", however many pulls land together. A reward that cannot be given (the buff was deleted) is written in that audit line and the chat line is still sent. Progress shows in OBS as the `goal` live stat ("Label: 37 / 50", sent by the site as finished text) and, optionally, as a Pack goal layer in the Overlay Editor. Check: `scripts/check-pack-goal.mts`.
- **Event feed in the app** (ROADMAP 57.7, TCG Bridge 0.19.0). Every event request (`POST /api/webhooks/pull` with an `event`, including a refused or ignored one) is also written, by `logMixItUp` with the same `detail` as its Mix It Up log line, to `mixitup:events` (`LPUSH` + `LTRIM` 30; the log's own 50 lines are mostly chat pulls, so it is a separate short list): `{ at, username, event, amount?, ok, detail }`. Bridge action `events` (`{ after }`, read only) answers the lines newer than `after` (ms), newest first. The app asks every 5 s while its window or the pull feed window is open and every 30 s otherwise, merges by time, viewer and event, and shows the last 30 as rows of the live feed on the Home page and the Feed and history page (since TCG Bridge 0.30.0, ROADMAP 59.5; before that an **Events** card) and, under its **Events** chip, in the pull feed window (since TCG Bridge 0.33.0, ROADMAP 59.8; before that an **Event rewards** section of that window). Check: `scripts/check-event-feed.mts` and `bridge/scripts/check-events.ts`.
- **Command check** (ROADMAP 57.8, TCG Bridge 0.20.0). `lib/mixitup-command-check-core.ts` (pure, `scripts/check-mixitup-command-check.mts`) builds what the site expects: the built-in `!pack`, every switched-on chat command, every buff with the Stream Deck switch on (named like its download), and the event commands of the switched-on event rewards (the cards' titles; the Raid one also for the raid shout-out). The Stream Deck quick actions and the stream start and end events have no switch on the site, so they are not expected. It compares them by name (case and a leading `!` ignored) with the commands in `mixitup:bridge`. The app sends the enabled commands with an id and a name only, no Web Request address, so matching is by name and a missing command cannot be told from a switched-off one ("missing or switched off"). `lib/mixitup-command-check.ts` `readCommandCheck(buffs)` returns null until the app has reported commands. The Connection tab shows it as the **Mix It Up commands** card (`CommandCheckCard.tsx`); `status` on `/api/bridge/action` and `/api/bridge/checklist` carry `commandsMissing` (the names to fix; absent until reported, empty when all are found) for the app's Home page (one line in its Ready to go live card) and checklist line. Read only: nothing is written to Mix It Up.
- **Bridge errors** (ROADMAP 57.9, TCG Bridge 0.21.0). The app posts `{ type: 'error', part, message, version, commit }` to `/api/bridge/report` (parts: `job`, `reconnect`, `obs`, `mixitup`; a part off the list or an empty message is a 400). `lib/bridge-errors-core.ts` (pure) cleans it (message one line, 300 characters, version `x.y.z`, commit 7 hex characters, the PC name from the token and the site's clock); `lib/bridge-errors.ts` keeps the last 50 in `bridge:errors` (LPUSH and LTRIM), counts a day in `bridge:errors:day:<date>` (INCR, 8 day TTL), and counts a 10 minute window in `bridge:errors:window`. The 10th report in a window takes the `bridge:errors:posted` flag (SET NX, 10 minutes) and posts once to the System Discord channel through `notifySystem`; single errors never post. The Connection tab shows the list (`BridgeErrorsCard.tsx`: time, PC, part, message, version, commit, and the last 7 days' counts). The Data health panel on Admin > Settings warns "TCG Bridge reported N errors in the last 24 hours" (counted from the kept 50) and links to the list. Tested in `scripts/check-bridge-errors.mts`.
- **Hotkeys.** Electron `globalShortcut`, set on the Buttons and hotkeys page, empty by default: refresh the overlay, pause or resume, last buff again. A shortcut another program holds, one used twice, or one Electron does not understand is reported next to its field.
- **Queue.** `GET /api/bridge/queue` (`bridgeGuard`) lists the overlay queue (`webhooks:queue`: who, pack, seconds waiting, next first, `lib/queue-control.ts`). The app reads it only while the Home page's **Pull queue** card is on screen, at most every 5 s (it shows the first 4 rows and "and N more"). **Skip next** and **Clear queue** pop events atomically and refund a paid pull the way a refused one is (`dropDraw` plus `releasePaidPull`: the ticket is dropped and the reservation released, so the viewer is not charged and keeps their allowance). The dashboard's Clear queue shares that core, so it refunds too.

## Staff tools in TCG Bridge
ROADMAP 55.12. TCG Bridge 0.10.0 added the staff tools (since 0.29.0 the Staff pages, Viewers and cards and This stream, and tray items; reworked in 0.32.0, ROADMAP 59.7: **Find a viewer** opens a viewer card that holds every action for that viewer, and This stream has a card each for extra pulls, scene, trading, preview, search and backup) for the streamer's own PC. It is off until an admin turns on **Staff tools on this PC** for that PC on the Mix It Up page (`setBridgeStaffAction`, which writes `staff` on the `bridge:tokens` record; the record also keeps `by`, the admin who paired it). Revoking the PC ends the powers with the token. A PC signed in with Twitch (ROADMAP 58.0, below) has no switch: its role decides.
- **Sign in with Twitch (58.0; the app half is TCG Bridge 0.35.0, ROADMAP 58.0b: the Connect screen's big Sign in with Twitch button; pairing with a code stays behind "Use a pairing code instead").** `lib/bridge-link.ts`. The app asks `POST /api/bridge/link` `{ name }` (no token; `linkGuard`: the webhook limit plus 10 requests per address per 10 minutes) and gets `{ id, code, secret, url, expiresAt }`: `id` is in the page address, `code` (6 easy-to-read characters) is shown in the app and on the page, `secret` is returned only here (KV keeps its sha256). `bridge:link:<id>` lives 10 minutes. The app opens `/bridge/link?id=...` (`app/bridge/link/`, noindex, exempt from the closed-site gate): not signed in goes to `/auth/twitch` and back; signed in shows "Link TCG Bridge on <PC>? Code <code>" with Allow and Deny (server action `decideLinkAction`; the account is the session's, never the form's). Allow reads the role live (`liveRole` in `lib/staff.ts`); no staff role denies the request with "This account has no staff role on the TCG site". A staff role mints a token like pairing does (`mintToken`: only the hash stored) with `userId` (Twitch numeric id), `login`, `role` and `by` = the login; the plain token waits on the request (2 minutes) for one pickup. An NX `bridge:link:<id>:claim` lets only one Allow or Deny act. Audited ("TCG Bridge linked with Twitch", refused, denied). The app polls `POST /api/bridge/link/poll` `{ id, secret }` (60 a minute per address) and gets `{ status: 'pending' }`, `{ status: 'denied', message }`, `{ status: 'expired' }` (also for a wrong secret: constant-time compare of the hashes) or `{ status: 'allowed', token, login, role }` once (the delete is the claim). The `status` action also answers `account: { login, role }` for a linked PC. In the app (0.35.0) the poll runs every 2 seconds for up to 10 minutes and stops on Cancel or when the window closes to the tray; the app opens only `<configured site>/bridge/link?id=<id>` (it builds the address itself from a well-formed id and ignores the `url` the site sends), keeps the secret in memory only, saves the token like a pairing token and stores the login and role in its settings, and re-reads them from every `status` answer. Its **Sign out** only forgets the token on the PC (there is no unpair route); the site's Unlink removes it server side, and the next call from the app then gets 401 and the Connect screen says "This PC was signed out on the site". A mod-linked PC hides the staff things a mod cannot do (the app mirrors the role map; the site still decides).
- **Permissions from the role (decision 2026-10-28).** A linked PC has the staff tools on when it has a role (`isStaffPc`); an old paired PC keeps the admin's switch. `STAFF_CAPABILITY` in `lib/bridge-core.ts` maps every staff action and read to the site capability; `staffRefusal` runs first in `runStaffAction` and `runStaffRead` and answers "Your account (Mod) cannot do that on the TCG site: it needs an admin." A name not in the map needs `admin`. Super admin and admin may do everything. A mod may only do what the mod panel lets a mod: `trading`, `block`, `unblock`, `scene` (audit line only), and the reads `state`, `users`, `activity`, `viewer`. Admin only (the admin panel, not the mod panel): `gift`, `show-collection`, `show-card`, `preview-url`, `test-pull`, `grant`, `stream-extra`, `backup` and the reads `cards`, `search`. A new staff action must be added to the map (`scripts/check-bridge-link.mts` fails when one is missing).
- **Role re-read.** `bridgeGuard` calls `recheckRole` for a linked token: at most once a minute per token (`roleCheckedAt` on the record, so a normal call adds no read). A lost role deletes the token and answers 401 `Unknown token`, exactly what an unlink gives; a changed role is saved on the record; a failed KV read keeps the PC. The Connection tab shows "Signed in as <login> (<role>)" and "Staff tools on this PC: from role" instead of the switch; **Unlink** stays for every PC.
- **Route.** `GET` and `POST /api/bridge/staff` (`app/api/bridge/staff/route.ts`), both behind `bridgeStaffGuard` (`lib/bridge.ts`): the usual bridge checks, then 403 `Staff tools are off for this PC.` without the switch (for a PC signed in with Twitch: without a staff role, `isStaffPc`; an action its role may not do is refused by `staffRefusal`), and always 403 in a sandbox. Logic in `lib/bridge-staff.ts`: `runStaffAction` (gift, show-collection, show-card, grant, stream-extra, trading, block, unblock, scene) and `runStaffRead` (state, users, cards, viewer).
- **Same code as the admin pages.** Each action calls the function the admin page uses (`issueDraw`, `grantCard`, the show-card webhook helper, `setStreamPullBuff`, the trade settings, `lib/pull-block.ts`). Gift packs gifts across the active season like the dashboard (no pack picker).
- **Audit.** Every action writes a `recordAudit` line ending `via TCG Bridge on <PC>, paired by <admin>`, or `via TCG Bridge on <PC>, signed in as <login>` for a PC signed in with Twitch.
- **Blocking a viewer from pulls.** KV `pulls:blocked` (hash of `PullBlock`, `lib/pull-block.ts`), for this stream or until lifted. `queuePull` (paid and `!pack`) and `queueOverlayEvents` (gifts, so the dashboard obeys it too) refuse with reason `blocked`, logged to the Mix It Up log with detail `blocked`. The Stream page's Live section lists blocks (Blocked from pulls) with **Lift** (`liftPullBlockAction`).
- **Pause trading** is `TradeSettings.enabled === false`; the app confirms with a native dialog first.
- **Scene.** The overlay has no active scene, so the app switches the OBS program scene on the PC and only posts an audit line (`action: scene`).
- **Panels** read only while their page is open, at most every 5 s. Brie Bucks in the viewer lookup are read on the PC from Mix It Up, never through the site.
- **Viewer card and refusals (TCG Bridge 0.32.0, ROADMAP 59.7).** "Find a viewer" lists names from the cached `?what=users` list (a mod may read it), so it needs no admin-only read; the card's facts come from `?what=viewer` plus the Brie Bucks. A read the site refuses (`{ error }` from `staffRefusal`, for example the admin-only `cards` search for a mod) is shown in the card's result line, and so is an action's refusal message. The app still shows every button; `staffActionsFor(role)` in `bridge/src/staffpages.ts` repeats `STAFF_CAPABILITY` for the sign-in update (58.0b) to hide what a role cannot do, and `bridge/scripts/check-staffpages.ts` fails when the two lists differ.
- **Preview overlay** (ROADMAP 57.10, TCG Bridge 0.23.0). Actions `preview-url` (a read-only preview key and path, expiring after 2 hours) and `test-pull` (the 55.14 simulated free pull; `username` optional, else the first test viewer; `force` queues it with no overlay connected). Details: docs/overlay.md, Overlay preview. Check: `scripts/check-overlay-preview.mts`.
- **Check.** `scripts/check-bridge-staff.mts` (403 without the switch, an audit line per action, blocks, sandbox, revocation).

### Staff notices and shortcuts (ROADMAP 55.13, TCG Bridge 0.11.0)
- **Notices.** A `notice` job (`StaffNotice` in `lib/bridge-core.ts`: kind, title, text, link path) is fire and forget: the app shows a Windows notification and a click opens the page in the browser. `sendNotice` (`lib/bridge.ts`) writes it only to PCs with staff on, one KV list per PC (`bridge:notices:<pcId>`, 60 s expiry), and queues nothing when no PC has staff on or in a sandbox. The poll route hands a PC its list only when its staff switch is on (`pollJobs(hash, version, pcId)`), so a PC without the switch never reads one (the cost is one extra LPOP a second per staff PC while it polls). A notice older than the job age limit is dropped: **one sent while the app is offline is lost**, and the app's Feed and history page and Notifications page say so.
- **Kinds**, each with its own switch in the app's settings (all on once staff tools are on): Needs attention (a Discord channel switched off, a failed backup, a data health crossing; `lib/system-notices.ts`, `lib/discord.ts`), New reports and feedback (`lib/feedback.ts`, links to `/admin/feedback?kind=<kind>#status-<id>`; there is no page per item), Paid pull refusals (`noteRefusal` in `lib/bridge-notice.ts`, called from `logMixItUp`; at most one per reason per minute through an atomic `bridge:refusal:<reason>` key with a 60 s expiry, and never `insufficient_balance`), Deploys (`noteDeploy`, from the bridge poll in production only: the first poll of a build claims `bridge:deployed:<commit>` with `nx`, so a build notifies once across servers; it lists the changelog lines of that PR when the build has any).
- **Links** are paths. The app opens one only when `siteUrl` (`bridge/src/notices.ts`) puts it on the paired site's own address, so a notice or a search result can never open another site.
- **Shortcuts.** The tray has Admin links (Dashboard, Mix It Up, Overlay Editor, Users). The This stream page has a **Back up** card (0.32.0) with **Back up now** (`POST` action `backup`: `runBackup` and `reportBackup`, the same as Admin Settings; it says when done or why it failed, and audits `Backup taken` or `Backup failed` via the PC) and a **Search the admin** card (formerly Shortcuts; a Quick search, `GET ?what=search`: the admin command palette's records through `paletteRecords` in `lib/palette-items.ts`, plus cards of the active season, each with its admin page). The Feed and history page reads `?what=activity` (the dashboard's pulls, grants and trades) every 5 s while open.
- **Check.** `scripts/check-bridge-notices.mts` (gating, stale notices, the refusal throttle, one notice per build, 403 and audit for Back up now, Activity and search); `npm run check` in `bridge/` covers the switches and the same-origin link rule.

## Setup wizard
ROADMAP 55.1. `/admin/stream/setup` (`app/admin/stream/setup/page.tsx`; `/admin/mixitup/setup` redirects here, `export const instant = false`) is a full-page wizard, one step per screen, selected by `?step=`: What you need, Mix It Up to the site, The site to Mix It Up, Pull rules, Stream events, Done. Back and Next are plain links and the step bar jumps to any step. There is no wizard state: `stepsDone` (`lib/mixitup-wizard.ts`, pure) reads the same status cards, health row and settings as the Overview, and `pickStep` opens the first step not done (Done when all are), so reopening resumes and a step can always be revisited.
- **Mix It Up to the site**: while chat comes through TCG Bridge (58.6) this step is optional: it says "Chat commands now come through TCG Bridge; the Mix It Up commands are only a fallback", the title reads "(optional)" and the step stops re-reading itself. Otherwise a Copy setup card for `!pack` (`incomingSetup` in `lib/mixitup-setup.ts`, address `/api/webhooks/pull`, the incoming secret in the body; `getWebhookSettings` makes the secret on first read, so it is never empty). The step re-reads itself every 3 s (`AutoRefresh`, `router.refresh()`, only while the tab is visible and the step is not green). It is green when the incoming card is (a request with the right secret reached any route); a wrong secret after the last good request shows "Mix It Up reached the site but the secret did not match" from `mixitup:seen`'s `badAt`.
- **The site to Mix It Up**: in bridge mode `BridgeCard` (download, pairing code, paired apps), the outgoing status card (TCG Bridge, Mix It Up found, currency; its "What to do" says how to switch on the Developer API), a currency select that posts the Connection form (`saveConnectionAction`), the Overview's balance check (`Quick` + `testBalanceAction`) and the OBS card with the TCG Bridge OBS password note. With direct addresses it shows the card and a link to the Connection tab instead.
- **Pull rules**: the charge switch and `PaidPullFields`, posting `saveMixItUpAction`, the same form fields as the Paid pulls card. Both save actions take a hidden `returnTo=setup` and then redirect back to their wizard step (errors included) instead of the Mix It Up tabs.
- **Stream events**: Copy setup cards for `/api/webhooks/stream` (`event` live and offline). Stream Deck buttons are on the Stream Deck buffs card.
- **Entry points**: the Connections section (its Set up button) and the status strip's fix links link to the wizard; the label is "Set up Mix It Up" until a bridge is paired or any request has reached the site, then "Run setup again".
- `scripts/check-mixitup-page.mts` covers `stepsDone`, `pickStep` and `incomingSetup`; `scripts/check-mixitup-health.mts` covers the health record (right secret, wrong secret, outgoing failure).
