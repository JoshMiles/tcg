# Discord activity feed

> Read this when you touch Discord channels, event kinds, share images, the stream recap or the weekly digest.

## Discord activity feed
Settings live in KV `discord:settings` as `{ enabled, channels: DiscordChannel[] }` (max 8; edited in Settings → Webhooks). A channel is one webhook with its own On switch, category boxes and pull filters (min rarity, new-only, and for Feedback a kind filter `feedbackKinds`: idea / bug / deletion / report, absent = all, cleaned by `cleanFeedbackKinds`, applied in `sendToCategory`; the Reports tick is on the channel card); `enabled` is the master switch. The first version stored one webhook at the top level: `normalize()` in `lib/discord.ts` reads that as one channel called "Activity" with the same settings, so there is no migration. `recordActivity()` forwards every event via `after()` to `notifyDiscord()`, which builds the embed once (rarity colour, static card thumbnail, link to the viewer's collection) and POSTs it to every enabled channel whose `shouldSend(e, channel)` passes, in parallel with each failure isolated. Only real discord.com webhook URLs are accepted (the server POSTs to the stored URL; a plain `http://localhost` stand-in is accepted outside production for testing); `allowed_mentions` is empty and names are Markdown-escaped because event text comes from unauthenticated endpoints. Browser-safe types, presets and the "Deploys & code" steps live in `lib/discord-config.ts`, client components must import from there, not `lib/discord.ts`. The form (`DiscordConfig`) sends the whole settings object as one JSON field; `discordAction` validates it with `cleanDiscordInput`, and each channel's Test / Send-last-activity buttons use the channel as currently typed, so it can be verified before saving. Under them, **Test a category** has one button per ticked category (intent `sample:<channelId>:<category>`): `sampleMessage()` in `lib/discord-samples.ts` posts the newest real example (the newest activity event of that category, any staff event for the admin log, the latest feedback item, the stored recap or digest) and falls back to made-up data, the footer saying which. Listings and system notices are not stored, so they are always made up. `scripts/check-discord.mts` runs the whole thing against a local fake webhook endpoint. **Categories** per channel: pulls, cards (grants / removals), upgrades, trades, stream, resets, **admin**, **system** (a channel saved before upgrades and trades had boxes gets them ticked wherever `cards` was). Upgrade and pull embeds link to the print (`copyHrefFor`). **The admin log is the one place staff names appear in Discord** (the form says to keep that channel private): it gets every activity event with `e.staff` (built with `showStaff`, other channels get the nameless message) plus `notifyAdminLog()` from `recordAudit`, the staff change log, season activation / publishing, pack publishing, scoring changes, trading paused / resumed / closed, every emergency password login (by "password") and the password login locking (`app/api/auth/login`, pinned to production so a sandbox header cannot silence it), and a trade reversal's reason as its own line (`reverseTradeAction`; the reversal event itself names the staff member but not why) (audit entries that have an activity twin, such as a grant or removal, are skipped so nothing posts twice). **System** notices come from `notifySystem()`: backup result and data-health crossing (`lib/system-notices.ts`, called by the nightly cron and the manual backup), sandbox created / deleted, the stream going live / offline (`lib/twitch-live.ts`, noticed when the cached status flips). Both are silent in a sandbox and post after the response. **Delivery log**: every send goes through `deliver(channel, body, kind)`, which keeps the last 20 results (time, kind, HTTP status, Discord's error text) in KV `discord:log:<channelId>`; the channel card shows a red dot when the last send failed and a "Recent sends" list. A channel whose last 20 sends all failed (a deleted webhook answers 404) is switched off (`offReason` on the channel, cleared when it is ticked On again), the admin log hears of it and the dashboard's Needs attention panel lists it (`autoDisabledChannels`).

**Shares** (category `shares`, off for existing channels, preset "Shares"): the owner's Share tab has **Post to Discord**. The browser builds the PNG and `POST /api/account/share` sends it. `postShareImage` in `lib/discord.ts` posts a multipart webhook, this category only: the file (capped at 4 MB) plus one line with the collector's name, The Cheesy TCG, `SITE_URL`, and `CHANNEL_NAME` / `CHANNEL_URL` from `lib/site.ts`. No enabled Shares channel, or the master switch off, means no request, and the button says the streamer has not turned this on. One post per collector per minute (`discord:share:<user>`). A sandbox refuses. Each send is written to that channel's delivery log with kind `shares`. The category test button still sends a short message, not a file, so Test works before anyone has posted an image. `recordAudit` is not used. A copy page's share image has no button.

**Stream recap** (category `recap`, off for existing channels): `lib/twitch-live.ts` stores `twitch:live:since` (from Twitch's `started_at`) whenever it sees the channel live. When it sees it offline, `finishStream()` reads that marker (none means the transition was missed: no recap), takes a 60s KV lock `twitch:recap:lock`, deletes the marker so the stream is never recapped twice, then builds the recap with the pure `buildStreamRecap(events, from, to)` in `lib/stream-recap.ts` from the activity log (capped at 500 events, so a very long stream is marked as minimums). A stream with no pulls or rewards posts nothing. It holds packs opened (real pulls only), rewards granted (webhook grants), staff grants (admin grants), upgrades, different cards, collectors, new collectors (a viewer's first card), first-ever pulls (print 1 of a card), the rarest pull linked to its print, the top puller, trades completed, and the overlay requests (`trigger` events: packs, collections and cards shown) split into webhooks and chat commands versus staff quick actions, a staff pull counting each pack it queued. A webhook grant also counts as a pull for collectors, new collectors, first-ever, rarest and top puller; an admin grant counts only as a staff grant. `getLatestRecap()` fills the newer counts with zeros for a recap stored before they existed; the biggest rank climb is left out because the log cannot replay leaderboards cheaply. The latest recap is kept in `stream:recap:latest` for the dashboard's **Last stream recap** widget and the channel card's **Stream recap** test button (sample numbers from `sampleRecap()` when there is none). Silent in a sandbox. The recap is noticed by any live lookup: the minute cron, a site visit, or at once when Mix It Up calls `POST /api/webhooks/stream` (docs/admin/mixitup.md). `scripts/check-stream-recap.mts` covers it.

**Weekly digest** (category `digest`, off for existing channels, preset "Weekly digest"): the weekly cron (`app/api/cron/weekly`) calls `digestOncePerWeek()` in `lib/weekly-digest-store.ts` right after the edition of the week is picked. It takes `digest:week:<yyyy-Www>` (NX, 21 days; released if building fails so a retry can run), builds the digest with the pure `buildWeeklyDigest()` in `lib/weekly-digest.ts` and posts it with `postDigest()` (awaited, not `after()`). Numbers: the last 7 days of the season's `stats:h:` counters (pulls, `newViewer`, upgrades, trades); the top 3 and the movers come from `getSeasonLeaderboard`, which already leaves out hidden and private collectors, and from the snapshot `digest:ranks:<seasonId>` (`{ user: [rank, points] }`) that EVERY run saves, even a skipped week; the first run has none and says "Movers start next week". Most traded cards are counted from accepted trades in `trades:history` (400 kept: when it is full and its oldest trade is newer than the week start the heading says "at least"); most wanted is the biggest `watch:idx:<card>` set (`watcherCounts`, set sizes only). A week with no pulls and no trades is skipped (no post, no `digest:latest`). The last posted digest is kept in `digest:latest` and shown by the **Weekly digest** dashboard widget; a channel with the box ticked gets a **Weekly digest** test button (the last posted digest, or made-up numbers from `sampleDigest()`). Check: `scripts/check-weekly-digest.mts`.

**Weekly admin digest (TRIAL, ROADMAP 51.10, four weeks from the first send)**: the same weekly cron then calls `adminDigestOncePerWeek()` (`lib/weekly-digest-store.ts`), guarded by `digest:admin:week:<yyyy-Www>` (NX, 21 days; released on error), inside its own try/catch. `buildAdminDigest()` (`lib/weekly-digest.ts`) writes plain lines from `audit:all` (actions per staff login over 7 days, distinct big trade reversals), `lastEmergencyLogin()` (the last emergency password login, shown as "this week" or not) and `backupStatus()`; `postAdminDigest()` (`lib/discord.ts`) posts it to channels with **Admin log** ticked only (staff names, keep it private). It always sends, even a quiet week, so the trial shows it arrives. Failed jobs are not recorded anywhere (no job log), so the backup's age and problem are the only job signal, and the message says so. Check: `scripts/check-admin-digest.mts`.
