# Discord activity feed

> Read this when you touch Discord channels, event kinds, the stream recap or the weekly digest.

## Discord activity feed
Settings live in KV `discord:settings` as `{ enabled, channels: DiscordChannel[] }` (max 8; edited in Settings → Webhooks). A channel is one webhook with its own On switch, category boxes and pull filters (min rarity, new-only, and for Feedback a kind filter `feedbackKinds`: idea / bug / deletion / report, absent = all, cleaned by `cleanFeedbackKinds`, applied in `sendToCategory`; the Reports tick is on the channel card); `enabled` is the master switch. The first version stored one webhook at the top level: `normalize()` in `lib/discord.ts` reads that as one channel called "Activity" with the same settings, so there is no migration. `recordActivity()` forwards every event via `after()` to `notifyDiscord()`, which builds the embed once (rarity colour, static card thumbnail, link to the viewer's collection) and POSTs it to every enabled channel whose `shouldSend(e, channel)` passes, in parallel with each failure isolated. Only real discord.com webhook URLs are accepted (the server POSTs to the stored URL; a plain `http://localhost` stand-in is accepted outside production for testing); `allowed_mentions` is empty and names are Markdown-escaped because event text comes from unauthenticated endpoints. Browser-safe types, presets and the "Deploys & code" steps live in `lib/discord-config.ts`, client components must import from there, not `lib/discord.ts`. The form (`DiscordConfig`) sends the whole settings object as one JSON field; `discordAction` validates it with `cleanDiscordInput`, and each channel's Test / Send-last-activity buttons use the channel as currently typed, so it can be verified before saving. `scripts/check-discord.mts` runs the whole thing against a local fake webhook endpoint. **Categories** per channel: pulls, cards (grants / removals), upgrades, trades, stream, resets, **admin**, **system** (a channel saved before upgrades and trades had boxes gets them ticked wherever `cards` was). Upgrade and pull embeds link to the print (`copyHrefFor`). **The admin log is the one place staff names appear in Discord** (the form says to keep that channel private): it gets every activity event with `e.staff` (built with `showStaff`, other channels get the nameless message) plus `notifyAdminLog()` from `recordAudit`, the staff change log, season activation / publishing, pack publishing, scoring changes and trading paused / resumed / closed (audit entries that have an activity twin, such as a grant or removal, are skipped so nothing posts twice). **System** notices come from `notifySystem()`: backup result and data-health crossing (`lib/system-notices.ts`, called by the nightly cron and the manual backup), sandbox created / deleted, the stream going live / offline (`lib/twitch-live.ts`, noticed when the cached status flips). Both are silent in a sandbox and post after the response. **Delivery log**: every send goes through `deliver(channel, body, kind)`, which keeps the last 20 results (time, kind, HTTP status, Discord's error text) in KV `discord:log:<channelId>`; the channel card shows a red dot when the last send failed and a "Recent sends" list. A channel whose last 20 sends all failed (a deleted webhook answers 404) is switched off (`offReason` on the channel, cleared when it is ticked On again), the admin log hears of it and the dashboard's Needs attention panel lists it (`autoDisabledChannels`).

**Stream recap** (category `recap`, off for existing channels): `lib/twitch-live.ts` stores `twitch:live:since` (from Twitch's `started_at`) whenever it sees the channel live. When it sees it offline, `finishStream()` reads that marker (none means the transition was missed: no recap), takes a 60s KV lock `twitch:recap:lock`, deletes the marker so the stream is never recapped twice, then builds the recap with the pure `buildStreamRecap(events, from, to)` in `lib/stream-recap.ts` from the activity log (capped at 500 events, so a very long stream is marked as minimums). A stream with no pulls or rewards posts nothing. It holds packs opened (real pulls only), rewards granted (webhook grants), staff grants (admin grants), upgrades, different cards, collectors, new collectors (a viewer's first card), first-ever pulls (print 1 of a card), the rarest pull linked to its print, the top puller, trades completed, and the overlay requests (`trigger` events: packs, collections and cards shown) split into webhooks and chat commands versus staff quick actions, a staff pull counting each pack it queued. A webhook grant also counts as a pull for collectors, new collectors, first-ever, rarest and top puller; an admin grant counts only as a staff grant. `getLatestRecap()` fills the newer counts with zeros for a recap stored before they existed; the biggest rank climb is left out because the log cannot replay leaderboards cheaply. The latest recap is kept in `stream:recap:latest` for the dashboard's **Last stream recap** widget and the channel card's **Send test recap** button (sample numbers when there is none). Silent in a sandbox. The recap is only noticed when someone causes a live lookup (site visit, dashboard), same as the live indicator. `scripts/check-stream-recap.mts` covers it.

**Weekly digest** (category `digest`, off for existing channels, preset "Weekly digest"): the weekly cron (`app/api/cron/weekly`) calls `digestOncePerWeek()` in `lib/weekly-digest-store.ts` right after the print of the week is picked. It takes `digest:week:<yyyy-Www>` (NX, 21 days; released if building fails so a retry can run), builds the digest with the pure `buildWeeklyDigest()` in `lib/weekly-digest.ts` and posts it with `postDigest()` (awaited, not `after()`). Numbers: the last 7 days of the season's `stats:h:` counters (pulls, `newViewer`, upgrades, trades); the top 3 and the movers come from `getSeasonLeaderboard`, which already leaves out hidden and private collectors, and from the snapshot `digest:ranks:<seasonId>` (`{ user: [rank, points] }`) that EVERY run saves, even a skipped week; the first run has none and says "Movers start next week". Most traded cards are counted from accepted trades in `trades:history` (400 kept: when it is full and its oldest trade is newer than the week start the heading says "at least"); most wanted is the biggest `watch:idx:<card>` set (`watcherCounts`, set sizes only). A week with no pulls and no trades is skipped (no post, no `digest:latest`). The last posted digest is kept in `digest:latest` and shown by the **Weekly digest** dashboard widget; a channel with the box ticked gets a **Send test digest** button (made-up numbers from `sampleDigest()`). Check: `scripts/check-weekly-digest.mts`.
