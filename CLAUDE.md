# TCG Admin — CLAUDE.md

## What this project is

**The game runs only on the Cheesygidds Twitch channel (https://www.twitch.tv/cheesygidds) and nowhere else** — the Twitch Extension is only installed there and packs are opened live on that stream. Say so in public copy (FAQ, Terms, Privacy, home, footer); use `CHANNEL_NAME` / `CHANNEL_URL` from `lib/site.ts` rather than hard-coding it.

A Twitch stream overlay + admin panel for a trading card game. Viewers pull cards live on stream via OBS browser source. An admin panel manages seasons, packs, and cards. A public collection viewer lets viewers see their cards. A Twitch Extension Panel lets viewers see their collection inside Twitch.

## Tech stack
- **Next.js 15** App Router — server components, server actions, dynamic routes
- **Vercel KV** (Redis) — all data persistence
- **Vercel Blob** — image uploads
- **Vercel Analytics + Speed Insights** — `<Analytics />` + `<SpeedInsights />` in root layout; raw script tag in static panel HTML
- **Tailwind CSS** — styling (dark theme: gray-950 bg, gray-900 cards, yellow-500 accent)
- **TypeScript** — strict, no `any` unless unavoidable
- Client components only when truly required. Current uses: AdminNav (`usePathname`), modal/dialog trigger buttons, dialog components themselves

## Data architecture

Three-tier hierarchy: **Seasons → Packs → Cards**

- **Seasons** (`season:{id}` in KV, index at `seasons:list`): metadata + `packIds: string[]`. One season active at a time.
- **Packs** (`pack:{id}`, index at `packs:list`): globally managed, not owned by any season. Cards stored at `pack:{id}:cards`. Packs can be assigned to multiple seasons.
- **Cards** (`pack:{id}:cards`): array of Card objects stored per-pack. Each card has a `soundUrl` field pointing to `/assets/sounds/{n}.mp3` for the 25 Season 1 cards.
- **Legacy collection** (`tcg_{collectionName}`): `{ username: number[] }` — card numbers owned, **with duplicates**. Duplicates represent multiple pulls of the same card (pull count). This is what the OBS widget writes to via `/api/collection`. Powers the mini-list in the overlay and the admin dashboard stats. **This is the source of truth for user data** — `addUserPull`/`getUserPulls` exist but are never called by anything.
- **User profiles** (`user:{username}:profile`): display name, Twitch username mapping, notes.
- **Twitch opaque mapping** (`twitch_opaque:{opaqueId}`): maps Twitch Extension opaque user ID → lowercase username string.

### Pull count / duplicate cards
The collection array stores duplicates intentionally. To get unique card count: `new Set(array).size`. To get pull count per card: build a `Map<number, count>` by iterating the array. Everywhere that shows cards (collection page, Twitch panel, widget mini-list) uses this countMap and displays a `×N` badge when count > 1.

KV normalizers (`normalizeSeason`, `normalizePack` in `lib/kv.ts`) handle legacy data shapes on read — never need manual KV migrations.

## Drafts & wizards
- `Pack.status` / `Season.status` are `'draft' | 'published'` (missing = published, via the normalizers). **Drafts are never drawn or activated**: `getActiveSeason` ignores draft seasons, `setActiveSeason` throws for one, `getActivePacksForSeason` skips draft packs, the public leaderboard hides draft seasons. A published season may have a draft pack attached; it just isn't drawn until published.
- The wizards create the draft record when the first step is completed (`createDraftPack` / `createDraftSeason`), rewrite the URL to `?draft=<id>` with `history.replaceState`, then **autosave** (`useAutosave`: ~0.9s debounce, serialised, `flush()` before navigating). Resume = open the same URL (the lists link to it). Publishing re-validates on the server (`validatePack` / `validateSeason`).
- **Don't add `revalidatePath` to autosave actions and don't put a changing `key` on the wizard element** — either re-renders/remounts the page mid-edit and bounces the user back to step 1. List pages are `force-dynamic` so they don't need it.
- `saveCards` replaces a pack's card list; existing cards **keep their numbers** (viewer collections point at them), new cards get the next free number, and the assigned numbers are returned to the editor.
- **Season lifecycle (`lib/season-wrap.ts`)**: a season can have `startsAt` / `endsAt` (set with the timezone-safe `DateTimeField`, stored as ms) and `autoStart`. **There is no background job**: `getActiveSeason()` in `lib/kv.ts` calls `applySeasonSchedule()` (via a dynamic import, to avoid a cycle) the first time anything asks after a date has passed, so the overlay, panel and site all trigger it. A due start activates the season (the latest due start wins) and clears `autoStart`; a due end ends the active season. **Activation always goes through `activateWithWrapUp(id)`** (the Activate buttons, the settings checkbox, publishing with "activate"): it wraps up the season it replaces first (`takeSnapshot`: final standings + awards saved at KV `season:<id>:wrap`, `endedAt` set, `tradingFrozen` set) and clears `endedAt` / the freeze on the one it starts, so **Reactivate** is also how an ended season returns. **End season** (`endSeason`, from the season page's Wrap-up panel) does the same without starting another; **Reopen** clears the ended mark and the freeze. `Season.tradingFrozen` makes `createTrade` / `acceptTrade` refuse for that season (cancelling still works). **Awards** (`buildAwards`, pure): Champion / Runner-up / Third by score, Completionist, Biggest collection, Most cards pulled, Shiny hunter, Full Art collector; they show on the ended season's leaderboard page (a Final standings box) and as badges on `/collection/[username]` (`getUserAwards` reads every season's snapshot). The Activate confirmation (`getActivationPreview`) names the season that will be wrapped up and lists warnings (no live packs, empty packs, cards with no image / 0 odds, an end date already past). **Duplicate** (`duplicateSeasonAction`) copies a season's packs into a draft with a fresh collection name. The season page has an Overview (`getSeasonStats`, a pulls-per-day chart from `lib/stats.ts`, top collectors), the pack **LineupEditor** (drag or arrows to reorder, inline draw weights with each pack's share of draws — weight is the PACK's own setting, shared by every season using it) and the Wrap-up panel. `scripts/check-seasons.mts` (needs the mock KV) covers awards, timing, the scheduler, wrap-up on activation and the trading freeze.
- Season `collectionName` must be unique across seasons (a clash would merge two seasons' viewer collections) — validated live and on publish.
- Published packs can be moved back to drafts from the pack page (`unpublishPack`).
- Published **seasons** can be moved back to drafts from the season page (`unpublishSeason`, with a confirmation). It also deactivates the season (so the overlay / Twitch panel see "no active season" until another is activated) and hides it from the public site; viewers' collections, packs and settings are kept, and it is republished from `/admin/seasons/new?draft=<id>`.

## Variants, upgrades & leaderboard

Packs can opt in to **variants**: every card can be pulled as Regular / Reverse Holo / Full Art / Shiny Full Art, and viewers upgrade duplicates in the Twitch panel. Season 1's pack has `upgradesEnabled: false`, so it behaves exactly as before.

- **Entry encoding (`lib/variants.ts`)**: a collection entry is `cardNumber + 1_000_000 × variantIndex` (regular = plain number, so all legacy data is valid). Always go through `encodeEntry` / `decodeEntry`; card numbers must stay < 1,000,000. `public/widget.js` and `public/twitch-panel/panel.js` mirror the constant (no build step there) — keep in sync. `countPulls()` / `uniqueCount()` decode, so "a card" is one card regardless of variant.
- **Config**: `Pack.upgradesEnabled`, `variantWeights` (default 100/25/5/1, relative — rolled *after* the card, normalised), `upgradeCosts` (5 regular→reverse, 3 reverse→full, 3 full→shiny). `Card.upgradesEnabled` (undefined/true = follow pack; false opts the card out) and `Card.fullArtImageUrl` (art for Full Art + Shiny). Reverse Holo and Shiny are the holo effect on the Regular / Full Art image — there is no separate holo art. Effective check: `upgradesAllowed(pack, card)`. All edited in admin (pack settings, card editor).
- **Upgrades**: strictly one step up, same card, same variant, active season only; no downgrades. `lib/upgrade.ts` → `POST /api/twitch/upgrade` (JWT → opaque ID → username; dev mode accepts any bearer).
- **Upgrade ceremony**: a successful upgrade plays an animation — the spent copies spiral into the middle, a flash and ring, then the new variant is revealed with its holo / glow (sparkles for Full Art and Shiny), its label, the cost and (on the website) the projected points. Website: `UpgradeCeremony.tsx` (portal, `.ug-*` rules in `globals.css`), played by `UpgradeButton` when it is given the card's art (`card` prop); the page refreshes when the ceremony closes, not before, because the upgraded row may vanish and cut it short. Twitch panel: `playUpgradeCeremony()` in `panel.js` with the same rules copied into `panel.css` (the stage is designed at 340×520 and scaled to fit the small frame). Both use **the `to` variant and `cost` the server returns** (not "next on the ladder"), since a switched-off variant is skipped. Reduced motion skips the movement and shows the result; click / Esc / Enter closes after ~1.8s, and it closes itself after 9s. **Holo is the Overlay Editor's holo, everywhere.** The shimmer on the website, in the upgrade ceremony and in the Twitch panel is driven by the SAME per-variant settings as the overlay (Overlay Editor → Variants → Holographic shimmer: on / off / auto by the pack's min-stars, colours, strength, sweep time, angle, blend, loop; global values with the pack's overrides on top). `lib/holo.ts` (`getHoloResolver()`, server) resolves them per card into a `HoloSpecs` ({ on, style: CSS variables } per variant, built by `buildHoloSpecs` in the client-safe `lib/holo-core.ts`, which mirrors `applyLook` in `widget.js`); pages pass it to the art (`holoClass()` + `holoVars()`, `.holo-fx`), and `/api/twitch/season` sends it on every card for `panel.js` (`applyHolo()`). The CSS (`globals.css`, `panel.css`) keeps the overlay's geometry — an 8-band gradient tile 5 card-widths wide and tall, sliding 8 card-widths in one sweep (a loop slides exactly one tile) — clipped to the art's silhouette with `--art-mask`. `.holo-live` sweeps by itself (detail views, the ceremony's reveal card and spent copies); grid tiles sweep on hover only. The glow / rocking (`.vfx-full`, `.vfx-shiny`) are separate from the holo. If you add a holo property, add it in `buildHoloSpecs` and the CSS too.
- **Switching variants off**: `Pack.disabledVariants` and `Card.disabledVariants` (Reverse / Full / Shiny; **Regular can never be switched off**, `cleanDisabled()` enforces it). Always go through the helpers in `lib/variants.ts`: `allowedVariants(pack, card?)` (pack and card switches combine), `effectiveWeights(pack, card?)` (switched-off weights zeroed — used by every odds display and `variantMultipliers`) and `upgradeStep(pack, card, from)` — an upgrade goes to the next variant that is **on**, and skipping a switched-off one costs the **product of every step crossed** (regular → full with Reverse off = reverse × full copies), so skipping is never a shortcut. The overlay (`rollVariant(weights, off)`) never rolls a switched-off variant; the Twitch panel gets `pack.disabledVariants` and each card's allowed `variants` from `/api/twitch/season` and mirrors the step maths in `panel.js`; the collection page precomputes `variants` / `steps` per card. Admin: pack-level switches in Pack Settings and the wizard's Upgrades step; per-card switches in the card editor, the bulk card editor (chips) and **inline on the pack page** (`CardToggles`: a per-card upgrades switch plus variant chips, saved immediately), a "Variants & odds" panel (pack-level switches with the resulting odds) and **Variant tools** (`bulkCards`: switch off Full Art & Shiny where a card has no full-art image, upgrades on/off for all, clear per-card switches). Server-rendered forms carry `variant_on_*` checkboxes plus a `variant_switches=1` marker; a form without the marker never touches the stored switches. `scripts/check-upgrades.mts` covers all of this.
- **Locking**: the collection is one JSON blob per season. Every read-modify-write goes through `withCollectionLock` / `addCollectionEntry` in `lib/kv.ts` (Redis `SET NX EX`). `POST /api/collection` with a `pull` now **appends server-side** (the overlay's in-memory copy goes stale after upgrades/grants and used to overwrite them) and returns `{ owned }`, which the widget adopts.
- **Grants**: webhook (`variant` in the body, default regular), admin quick action and admin user page all take a variant.
- **Scoring settings (Admin → Settings → Scoring)**: every scoring number is a field of `ScoringSettings` in `lib/scoring.ts`, stored in KV (`scoring:settings`), clamped by `sanitizeScoring()` (ranges in `SCORING_LIMITS`), and defaulting to the original behaviour (`DEFAULT_SCORING`): `baseScore` (10), `rarityExponent` (1), `scarcityMin/Max` (0.5 / 2), `scarcitySmoothing` (1), `upgradeMargin` (1.2), `completionBonusPct` (25), `completeSetBonusPct` (50), `leaderboardSize` (100). They are **global** — changing them re-scores every season immediately (values are always computed live; nothing is stored per season). `getSeasonLeaderboard()` loads them and `SeasonValues.settings` carries them to everything downstream (`collectionBonuses`, `projectUpgradeGain`, the FAQ numbers, My Stats). The pure functions in `lib/leaderboard.ts` take `settings` as a parameter defaulting to `DEFAULT_SCORING`, so they stay testable (`scripts/check-upgrades.mts`). Add new tunables to `ScoringSettings` + `DEFAULT_SCORING` + `SCORING_LIMITS` and a `ScoringField` in the settings page.
- **Value & leaderboard (`lib/leaderboard.ts`)**: per-copy value = `baseScore (10) × rarity^rarityExponent × scarcity × variantMultiplier`. rarity = 1/(pull rate × cards in season); **scarcity is per variant** — copies of *that exact version* of the card vs the average card's copies of that version (a Shiny is compared with other Shinies), `(avg+k)/(copies+k)` (k = `scarcitySmoothing`) clamped to `scarcityMin`–`scarcityMax`, so spending copies in an upgrade makes the version you spent scarcer (its remaining copies are worth more) while the new version adds to its own count; variant multiplier = max(odds ratio, previous × cost × 1.2). Because scarcity moves, an upgrade is *usually* but not always a net gain, so the My Stats "± pts" is a **projection** (`projectUpgradeGain` recomputes the whole season's values with the upgrade applied) and can be negative — never re-promise "always a net gain". Score = sum over every copy owned **plus two collection bonuses** (`collectionBonuses()` in `lib/leaderboard.ts`), both measured against the *set value* (what one Regular copy of every card is worth right now): a **completion bonus** of `completionBonusPct` (default 25%) × set value × the share of the set owned, and a **complete-collection bonus** of `completeSetBonusPct` (default 50%) × set value once the viewer owns at least one of every card (duplicates / better versions don't count towards completeness). `LeaderboardRow` carries `cardPoints`, `completionBonus`, `setBonus`, `complete` alongside the total `score`; `scoreFor()` (used by `projectUpgradeGain`) includes the bonuses. The leaderboard shows a 🧀 Complete chip, My Stats a points breakdown, the FAQ the live numbers. Per season. Surfaces: `/leaderboard[/seasonId]`, `GET /api/twitch/leaderboard`, a Leaderboard tab in the panel, a rank/"Full leaderboard" link on `/collection/[username]`, and links from the admin dashboard (header button + Top Collectors panel). The leaderboard page opens with a "How are points worked out?" expandable at the top (`?how=1` opens it; the collection card details link there).
- **Holo masking**: the holographic shimmer must sit *exactly* on the art and follow its silhouette (the card art is 600x891 with transparent rounded corners). On the overlay, `.holographic-overlay` is a child of `.main-card` (`inset: 0`, so it follows the art's pop / rock transforms) and is clipped with `mask-image: var(--card-mask)` — set in `widget.js` to the shown art's **static thumbnail** (same shape, tiny, never animated; full-art thumbnail for Full Art / Shiny). On the website and panel the `.vfx-reverse` / `.vfx-shiny` `::after` sheen uses `--art-mask` the same way (`CardTile`, the detail art, `setArtMask()` in `panel.js`). Don't move the overlay back outside the card or size it with fixed offsets (it used to be 21px too wide and bled past the corners).
- **Overlay effects**: `variant-reverse|full|shiny` classes on the theater wrapper (`widget.css`). **Shiny cards rock gently left to right** everywhere they appear (`.vfx-shiny` on the site and panel, `variantRock` on the overlay) using the standalone `rotate` property so it layers on hover/pop transforms; disabled under `prefers-reduced-motion`. Test panel (`?dev`, see below): pick pack / card / variant, draw several, or draw all four variants of a card.
- **Trading (website only; Twitch panel later)**: direct offers to one viewer and an open board of listings, any copy in any variant. **Escrow**: offering removes the copies from the offerer's collection into the trade (`Trade.escrowed`), so collections + escrow is conserved; accept swaps (`settleTrade`), decline / cancel / expiry / counter refund. Escrowed copies don't count towards score or scarcity while open. Storage in KV: `trades:open`, `trades:history` (capped 400), `trade:settings`, `trade:cd:<user>`. Pure logic in `lib/trade-core.ts` (client-safe), engine in `lib/trades.ts`, every mutation under `withLock('trades')` then a collection lock (always that order). **No background job**: expired offers are refunded lazily by `sweepTrades()`, called from `/trade`, `/trade/new`, `/account`, `/collection/[username]` and `/admin/trades`; call it from any new page that shows collections. The viewer always comes from the session (`requireViewer` in `lib/trade-api.ts`), never the body. API: `POST /api/trades`, `POST /api/trades/[id]` (`accept|decline|cancel|counter`), `GET /api/trades/holdings`. Pages: `/trade`, `/trade/new[?to=|?counter=]`, `/admin/trades` (settings, pause switch — cancelling still works while paused —, open offers with cancel & refund, log). Settings: `TradeSettings` (expiry 48h, 5 open offers, 20s cooldown, 8 stacks per side). **Notifications**: every outcome notifies whoever needs to know (`lib/trade-notify.ts`: new offer / counter → recipient; accepted / declined / admin cancel / expired → offerer; withdrawn / expired → recipient) into the KV list `notif:<user>` (30 newest) with `notif:<user>:seen` marking what is read; `GET/POST /api/notifications` (session only) feed the **bell** in `SiteNav` (`NotificationBell`, polls every 45s and on tab focus). The engine queues events while it holds the trade lock and sends them after it is released (`queueEvent` / `flushEvents` in `lib/trades.ts`; building them reads the season, which must not hold the lock) — add new outcomes through `closeTrade` / `createInLock` so they are announced. **Trade animation** (`TradeCeremony.tsx`, `.tr-*` CSS): plays for the accepter when `POST /api/trades/[id]` returns `swap`, and for the offerer when the bell finds a fresh `accepted` notice (once, remembered in `localStorage` `tcg_trade_played`; "Replay" in the bell). Cards keep their holo (`SwapCard.holo`, via `buildSwap`). **Activity / Discord**: every action (offered, countered, accepted, declined, cancelled, expired) is a `trade` activity event carrying both sides' cards as readable lines plus points, the note and kind; Discord posts offers, counters, completed trades and admin cancels (not declines / withdrawals / expiries) as an embed with a field per side. The card popup on someone else's collection has an **Offer a trade** button (`/trade/new?to=<user>&want=<card>.<variant>` pre-selects the card you ask for). Sandbox-testable like everything on `kv`. `scripts/check-trades.mts` (needs the mock KV) checks conservation, races, expiry, caps.
- `npx tsx scripts/check-upgrades.mts` sanity-checks encoding, roll odds, and the value maths.

## Admin routes
- `/admin` — the **widget dashboard** (see "Admin dashboard (widgets)"): stats, quick actions, top collectors, leaderboard, rarity mix, packs, card ownership, recent activity, trading, overlay status, activity pulse, variant mix, most valuable cards, cards nobody owns, stream status, shortcuts and notes, arranged by the admin
- `/admin/seasons` — season list (drafts first)
- `/admin/seasons/new[?draft=id]` — season wizard / resume a draft
- `/admin/seasons/[id]` — season settings + pack assignment
- `/admin/packs` — global pack library: search (matches season names too, `/` focuses it), status filters (All / Live / Inactive / Drafts) and sorting via `PackToolbar` (tiles opt in with `data-pack` + `data-*` attributes; it toggles `hidden` / CSS `order`, no re-render); each tile shows the seasons it is used in (a warning when a published pack is in none, so it can never be drawn), an Upgrades chip, a one-click Active/Inactive switch (`setPackActive`) and a link to that pack's overlay overrides (`/admin/overlay?scope=<id>`)
- **Pack library extras**: every published tile shows a **health** badge (`packHealth()` in the client-safe `lib/pack-health.ts`: no cards, 0-odds cards, missing images / names, duplicate card numbers, Full Art cards without art, Regular weight 0, duplicate names, no cover, not in any season; links to `/admin/packs/[id]#health`) and the pack's **usage** (`pulls · % of draws`, from the per-pack counters `p:<pack name>` in `lib/stats.ts`, so it counts from when tracking began and follows the pack's name). Tiles also have **Duplicate** (`duplicatePackAction`: a draft copy named "<name> (copy)" with the same settings and cards under new ids; card numbers are copied, so renumber if both packs go in one season) and **Archive / Restore** (`Pack.archived`: hidden under the Archived filter, never drawn, can't be switched on, its cards stay so collections keep working; restore brings it back inactive). The actions live in `app/admin/pack-actions.ts`.
- **Pack page extras**: header Duplicate / Archive, a Pack health panel, and an **Odds & simulator** panel (`OddsPanel.tsx`): edit every card's weight in one table with live chance / "1 in N", Normalize to 100, Balance by rarity (set the share of pulls per star tier; cards in a tier share it equally), a share-by-rarity chart, and a draw simulator (1,000 / 10,000 / 100,000 packs from the weights typed, saved or not, with the variant roll and a 300-trial estimate of the packs needed to find every card). Saving goes through `savePackOddsAction`.

## API routes

### OBS / collection
- `GET /api/seasons/active` — active season + packs + cards (used by widget)
- `POST /api/collection` — save card pull to legacy collection (widget writes here)
- `GET /api/collection?name={collectionName}` — read collection (widget reads here)

### Twitch Extension
- `GET /api/twitch/season` — active season + packs + cards (public, used by panel)
- `GET /api/twitch/collection?username=foo` — user's owned card numbers across all seasons, as `{ collections: [{ seasonId, seasonName, active, ownedNumbers }] }`
- `GET /api/twitch/user?opaqueId=xxx` — look up username by Twitch opaque ID
- `POST /api/twitch/login` — **primary login endpoint**: verifies Extension JWT, gets the viewer's numeric ID via `getTwitchUserId()` (`user_id` after an identity grant, or `channel_id` when the signed `role` is `broadcaster`), resolves via Helix API, saves opaque→username mapping, creates user profile if needed, returns `{ username }`
- `POST /api/twitch/link` — JWT-validated, links opaque ID to username; also creates user profile if not present
- `POST /api/twitch/unlink` — JWT-validated, deletes opaque ID → username mapping (logout)
- `POST /api/twitch/upgrade` — JWT-validated; body `{ seasonId, cardNumber, from }`; spends the pack's upgrade cost in `from` copies for one of the next variant
- `GET /api/twitch/leaderboard?seasonId=&username=` — public per-season ranking, the viewer's own rank, and per-card point values
- `GET /api/twitch/resolve-username?userId={numericId}` — resolves Twitch numeric user ID → login name via Helix API (requires `TWITCH_CLIENT_ID` + `TWITCH_CLIENT_SECRET`)

### Admin (one-time / utility)
- `GET /api/admin/import-legacy?secret={ADMIN_SECRET}` — seeds `tcg_CheesyStarterDeck` with Season 1 legacy player data. Add `&dry=1` to preview, `&overwrite=1` to replace existing user data. Also creates user profiles for imported users.

### Overlay
- `POST /api/overlay/heartbeat` — the OBS overlay (`public/widget.js`) pings this every 10s with `{ id, streaming, recording, obs, dev }`; strictly validated, unauthenticated like the rest of the overlay's endpoints
- `GET /api/admin/overlay-status` — admin-only; `{ connected, clients, streaming, recording, lastSeen, queued }`

### Webhooks
- `POST /api/webhooks/grant-card` — MixItUp integration: body `{ secret, username, cardNumber }` → appends card to user's active season collection

## OBS widget data flow
1. Widget calls `GET /api/seasons/active` on load → returns `{ season, packs: [{ pack, cards }] }`
2. Widget picks pack by weight, then card by probability
3. Widget calls `POST /api/collection` to save card number to legacy collection (duplicates allowed — pull count)
4. Widget reads `GET /api/collection?name={collectionName}` to show mini-list with ×N badge for duplicates

The widget reads per-pack visual settings (accentColor, tearBorderColor, holoMinStars, cardTime, cooldownTime, soundVolume, coverImageUrl) directly from the pack object. Card sounds come from `card.soundUrl` (e.g. `/assets/sounds/1.mp3`).

## Conventions
- **No emoji in the UI — use icons.** `app/components/Icon.tsx` is the one icon set (Lucide, plus the custom `cheese` brand glyph): `<Icon name="trophy" />`, sized in `em` so it matches the surrounding text unless you give it `w-* h-*`; `<RankMedal rank={n} />` for podium places. Anything data-driven (nav items, the widget registry, notification kinds, overlay editor categories) stores an `IconName` string, never an emoji. Add a new icon by importing it from `lucide-react` and adding it to `ICONS`. Text glyphs such as ★ (rarity stars), ✓ in a `<option>` and the ✦ particles are fine; Discord messages keep emoji because Discord renders them. Shiny's short label is "SH" (Reverse Holo "RH", Full Art "FA"). The stream overlay's own look (e.g. the default `✨ Shiny Full Art` label and sparkle particles) is a design choice made in the Overlay Editor, not part of this rule.
- `force-dynamic` on every admin page (KV reads must be fresh)
- `revalidatePath` after every mutation in server actions
- Server actions use `.bind(null, fixedArg)` to pre-fill arguments before passing to `<form action={}>`
- Image uploads go through `ImageUploadField` component → Vercel Blob
- Auth: `ADMIN_SECRET` env var checked against `admin-auth` cookie in middleware
- **Wizards, not modals, for multi-step creation.** Packs and seasons are created in full-page flows (`PackFlow`, `SeasonFlow`) — see *Drafts & wizards*. Dialogs remain for small one-shot forms (add one card).
- **Modal pattern**: pages stay as server components; a thin client wrapper component (e.g. `NewPackButton`) owns only the open/close boolean and renders the dialog. The dialog itself uses `<form action={serverAction}>` — redirects still work correctly.
- **NEVER add `onClick` or other event handlers to JSX in server components** — Next.js will throw at runtime even if the element is inside a client component's children prop. This applies to `<a>`, `<button>`, or any element rendered directly in a server component file.
- Users page reads from `getAllCollectionUsers()` in `lib/kv.ts` which aggregates across all seasons' legacy collections. `listAllUsers()` and the per-user pull-record helpers were removed — nothing wrote to them.

**Critical: `auth.userId` is always an opaque ID — it never becomes a numeric ID on the client**, even after `requestIdShare()`. The real Twitch numeric user ID only appears in the JWT payload's `user_id` field (server-side). All login resolution goes through `POST /api/twitch/login` which reads it from there.

**Twitch auth flow (current implementation):**
1. Panel loads → `onAuthorized` fires → `init()` called
2. If `identityRequestPending` flag is set (user just responded to Twitch identity popup) → call `loginFromJwt()` → on success: login; on fail: show the failure reason on the login screen
3. Load season data; if none → show no-season state
4. If `isExplicitlyLoggedOut()` (localStorage flag) → show login screen
5. Try `tryAutoLogin()` — `GET /api/twitch/user?opaqueId=...`; if mapping exists, silent login
6. Try `loginFromJwt()` — `POST /api/twitch/login` with current JWT; if JWT already contains `user_id` from a prior identity grant (or the viewer is the channel owner), silent login without any user interaction. A 403 ("identity not shared yet") shows a plain login screen; any other failure shows its reason on the login screen
7. Otherwise → show login screen with teaser grid and "Login with Twitch" button
8. Login button pressed → **if the JWT role is `broadcaster`, call `loginFromJwt()` directly** (Twitch's `requestIdShare()` is a documented no-op on your own channel, so waiting for it hangs forever); otherwise call `requestIdShare()`, show a status hint, set `identityRequestPending = true`, 20s timeout fallback
9. Twitch re-fires `onAuthorized` after user responds → `init()` re-enters with `identityRequestPending = true` → `loginFromJwt()` resolves via `/api/twitch/login`
10. Logout: set localStorage flag + `POST /api/twitch/unlink` → show login screen

## Card art
Card images are animated WebP in `public/assets/cards/` (600px wide, ~1–4MB each) with a static first-frame thumbnail of each in `public/assets/cards/thumb/` (~15KB). The original 800px GIFs were 20MB+ each and were removed. `getPackCards` rewrites legacy stored URLs (`/assets/GIF/X.gif` → `/assets/cards/X.webp`) on read, so old KV data keeps working.

- **Grids use `CardTile`** (`app/components/CardTile.tsx`, client component): shows the thumbnail and loads the animated file only while hovered. Used on `/collection/[username]` and the admin user detail page. `cardThumbUrl()` in `lib/card-art.ts` maps an image URL to its thumbnail (returns the URL unchanged when none exists, e.g. external images).
- **The Twitch panel** (vanilla JS) does the same: `/api/twitch/season` returns a `thumbUrl` per card (from `cardThumbUrl()`), and `addCardImage()` in `panel.js` shows that static thumbnail, mounting the animated `imageUrl` as an overlay only while the card is hovered (skipped for `prefers-reduced-motion`). Never put full animated images directly in the panel grid — 25 of them at once makes the iframe crawl.
- **Processing** lives in `lib/card-image.ts` (sharp), shared by the CLI and uploads. To convert GIFs locally: `node scripts/optimize-cards.mjs <inDir> <outDir>` (Node ≥ 22.18). With no GIFs present it just regenerates thumbnails.
- **Admin GIF uploads** (`ImageUploadField`): the browser uploads the raw GIF straight to Blob via `/api/upload/token` (Vercel functions cap request bodies at 4.5MB), then `/api/upload/optimize` fetches it, stores `cards/<uuid>.webp` + `cards/<uuid>.thumb.webp`, and deletes the original. The `<uuid>.thumb.webp` naming is what lets `cardThumbUrl()` derive the thumbnail from the stored URL — keep `optimizedCardPaths()` and `cardThumbUrl()` in sync. Non-GIF uploads still go through `/api/upload` unchanged. Needs `BLOB_READ_WRITE_TOKEN`; the optimize route sets `maxDuration = 60`.

## User avatars
Admin pages (dashboard Top Collectors, users list, user detail) show each user's Twitch profile picture. `getAvatars(usernames)` in `lib/avatars.ts` batches Helix `users?login=…` lookups (`fetchTwitchAvatars` in `lib/twitch-helix.ts`, up to 100 per request) and caches results in the KV hash `twitch:avatars` (login → `{ url, at }`; 7 days for found, 1 day for "no avatar"). It never throws — without `TWITCH_CLIENT_ID`/`TWITCH_CLIENT_SECRET`, or if Twitch is down, users just get the initial-letter fallback, and a failed lookup is not cached. Logins that can't be Twitch names (e.g. `mrbeast#`) are skipped. Use `sizeTwitchAvatar(url, px)` to request the right size and the `Avatar` client component (`app/components/Avatar.tsx`) to render it; it falls back to the initial if the image fails to load.

## Live activity (`/admin/activity`)
An event log of everything that happens: widget pulls (new vs duplicate, copies, unique owned), card grants/removals (admin + webhook), resets/deletes, incoming webhook triggers, and "collection shown" notices. `recordActivity()` in `lib/activity.ts` appends to the KV list `activity:log` (newest first, capped at 500) and bumps the counter `activity:seq`; it never throws and must be `await`ed in serverless routes. Call it from any new code path that changes a collection.

The page is a server-rendered snapshot plus a client component (`ActivityFeed`) that polls `GET /api/admin/activity?after=<seq>` every 3s while the tab is visible (pausable). With nothing new that is one KV GET; new events come back with avatars. Polling rather than SSE because serverless functions can't hold long connections cheaply. **The page** (`ActivityFeed.tsx`, helpers in the client-safe `lib/activity-view.ts`): a summary strip (pulls per minute / hour, viewers, rare pulls, a 30-minute bar chart, and a "busy right now" banner when the last 2 minutes are at least 3× the usual, all computed from the loaded events), a search box (`plainText()` of each event) and a click-a-viewer filter, multi-select category chips plus More filters (rarity, version, pack, new-only), **Group bursts** (`groupEvents`: pulls by one viewer within 8s, or admin gifts to one viewer, collapse into one expandable row), **Notable moments** (`notableReason`: Shiny / Full Art / 5★ pulls, completed collections, upgrades to Full Art / Shiny, admin trade cancels and mass resets) highlighted and optionally pinned, a compact view, a sound chime (WebAudio, no asset) and desktop notifications for notable events that arrive while the page is open, and CSV / JSON export of the filtered events. Clicking a row opens `EventDetail` (side panel: the full record plus Gift packs, Grant again, Remove a copy via the existing `quickAction` / `removeUserCard` actions, open the viewer). Filters, view and alert choices persist in `localStorage` `tcg_activity_prefs`. History is still the latest 500 events (export keeps what is shown); for longer history use the dashboard's time-series counters (`lib/stats.ts`). `pull` events come from the unauthenticated `/api/collection` POST (the widget's payload), so treat their contents as untrusted display text.

## Admin UX conventions
- **Destructive actions use `ConfirmButton`** (`app/admin/components/ConfirmButton.tsx`): wrap the submit button of a `<form action={serverAction}>` and it opens a confirmation dialog first, then calls `form.requestSubmit()`. Never ship a bare delete/reset button. For a button outside its form, pass `formId`.
- **Tiny card icons use `cardThumbUrl()`**, never the animated `imageUrl` (a 28px icon should not download 2MB).
- **Assets page** (`lib/assets.ts` + `app/admin/assets/`): groups by purpose (card art / pack covers / sounds / unused), not file type. Flags `legacy-gif`, `missing`, `no-thumbnail`, `heavy`. Sizes come from the Blob `list()` for Blob files and same-origin HEAD requests for bundled `/assets/…` files. "Unused" = Blob files no card/pack references (a card's companion thumbnail counts as referenced; files under 10 minutes old are hidden in case they're mid-optimize). `deleteUnusedBlobs()` re-verifies on the server — it only deletes files that are in our store and unreferenced — so a stale page or crafted form can't delete live art.
- The users list has a client-side search (`UserSearch`, press `/`); rows opt in with a `data-search` attribute.

## Overlay status & quick actions
- **Connection indicator**: each overlay page load picks a random id and sends a heartbeat every 10s (`lib/overlay.ts`, KV hash `overlay:clients`); a client counts as connected for 25s after its last heartbeat. `OverlayStatusProvider` (in the admin layout) polls `/api/admin/overlay-status` once every 5s and `OverlayStatus` (sidebar + dashboard header) and `QuickActions` read it. Open the overlay in a normal browser tab and it shows as "browser tab".
- **Live detection**: if OBS grants the browser source *Page permissions → "Read access to OBS status information"*, the widget calls `window.obsstudio.getStatus()` and reports `streaming`/`recording` (and re-reports on the `obsStreamingStarted/Stopped` events). Without that permission those stay `null` and the UI says only "connected". It cannot know the stream is live any other way.
- **Quick actions** (dashboard): `quickAction` in `actions.ts` dispatches on the submit button's `intent` (gift packs, show collection, grant card); `clearQueueAction` empties the overlay queue. Gift/show enqueue the same events the webhooks do (`enqueueEvent`) and are refused with a "queue anyway" option when no overlay is connected, so packs can't pile up unseen. They return an `ActionResult` shown inline via `useActionState`. Keep form fields controlled — React resets uncontrolled fields after a form action. `/admin?gift=<username>` prefills the viewer (the users list 🎁 link uses it).
- **Users list**: rows are one stretched link to `/admin/users/[username]` (profile editing lives there), sortable via `?sort=cards|pulls|active|name`; "last active" comes from the latest 500 activity events.

## Admin dashboard (widgets)
The dashboard is a 12-column grid of widgets the admin can add, remove, drag to rearrange and resize ("Customize dashboard"). **Registry and layout model**: `lib/dashboard.ts` (client-safe) — `WIDGETS` (title, icon, description, default span, allowed spans), `DashboardLayout = { widgets: { type, span }[] }`, `sanitizeLayout()` (known types only, each at most once, spans snapped to the widget's allowed set), `DEFAULT_LAYOUT` and `SPAN_CLASS` (spelled out for Tailwind; everything stacks on phones, spans ≤ 6 pair up on tablets). **Storage**: KV `admin:dashboard` (one layout for the whole admin; sandbox-namespaced like everything else) and `admin:dashboard:notes`; server actions in `app/admin/dashboard/actions.ts` re-check the admin cookie and re-sanitise. **Data**: `loadDashboardData(season, packs, needs)` in `lib/dashboard-data.ts` computes only what the widgets in the saved layout need (the leaderboard, activity log, trades and live status cost extra reads). **Rendering**: `renderWidget(type, data)` in `app/admin/dashboard/widgets.tsx` (server components, each wrapped in `Panel`); `DashboardGrid.tsx` (client) receives the rendered nodes and owns edit mode — HTML5 drag and drop (drag a widget, or one from the library, onto another: it lands before / after depending on which half you hover), ↑ ↓ / ◀ ▶ buttons as the keyboard and touch route, ✕ remove, Reset to default, Save / Cancel. A widget added in edit mode has no node yet, so it shows a placeholder until the layout is saved and the page refreshes. **Season and range**: `/admin?season=<id>&range=24h|7d|season` (the `DashboardControls` pickers) choose which published season the widgets describe (default: the active one) and the time range for the chart / pulse / viewers widgets; non-active seasons use all of their published packs. **Presets**: named layouts in KV `admin:dashboard:presets` (max 12); `Customize` has a Presets bar (save the current draft under a name, apply, delete) and view mode shows the preset names as chips that switch the saved layout. **Resizing**: drag a widget's right edge in edit mode (the span snaps to the widths the widget allows; the card's `draggable` is switched off for the gesture). **Time series (`lib/stats.ts`)**: `recordActivity` also calls `recordStats`, which bumps hourly counters (`pull`, `newCard`, `newViewer`, `upgrade`, `trade`, `grant`, `v:reverse|full|shiny`) in the hash `stats:h:<collection>` (field `<UTC hour>|<metric>`) and adds the viewer to the day's set `stats:u:<collection>:<UTC day>`; `getSeries()` aggregates them into 24 hourly or up to 90 daily buckets and the widgets compare with the previous equal period. The activity log (500 events) cannot answer "per day this season", hence the counters; they only count from `stats:since:<collection>`, and the widgets say so. **Needs attention** (`computeAttention` in `lib/dashboard-data.ts`) is a list of plain checks (live but no overlay, queue backlog, no active packs, published packs in no season, Full Art without art, trading paused, expiring trades, drafts, missing Twitch credentials) — add a check there. **Overlay controls** flips the two "only when live" switches (`setLiveGateAction`). **To add a widget**: add its type to `WIDGET_TYPES` and `WIDGETS`, render it in `renderWidget`, and (if it needs extra data) compute that in `loadDashboardData` behind `needs.has(...)`.

## Admin responsiveness
Admin pages use the full width of the page (no `max-w-*` caps on page wrappers; keep it that way — use responsive grids such as `xl:grid-cols-2` for forms instead of narrowing the page). The admin works on phones: below `lg` the sidebar is a drawer opened from a top bar (closes on navigation, Esc or the backdrop) and `main` has smaller padding and top padding for the bar; on desktop the sidebar collapses to an icon rail. Wide tables scroll horizontally inside `main` (`overflow-auto`) — the Assets and pack detail pages are the known examples. The Overlay Look tab is full width (`max-w-none`): a big sticky preview on the left and a 24rem scrollable properties panel on the right at `xl`, stacked (preview first) below that. A collapsed desktop sidebar **expands over the page on hover or keyboard focus** (`peek` in `AdminShell`; the sidebar is `lg:fixed` and `main` carries the margin, so nothing reflows).

## Overlay layout (Overlay Editor → Layout)
The overlay is drawn on a fixed **design stage** (default 1280×720, `lib/overlay-layout.ts`) and scaled to fit the real OBS browser source, so a differently sized source never cuts the animation off (the pack opening spans about -425px..+208px around its centre, which `.pack-fit` re-centres). The browser-source size is shared, but **the pack opening and the collection view are placed independently**: `OverlayLayout = { width, height, pack: Placement, collection: Placement }` (`Placement` = `scale`, `offsetX`, `offsetY`, design px) in KV `overlay:settings.layout`; `sanitizeLayout()` upgrades the old single-placement shape (both views inherit it, so nothing moves). `GET /api/overlay/config` serves it and `widget.js` `applyLayout()` writes `--stage-scale` (the fit, on `.container`) plus `--pack-*` / `--col-*`; each theater wrapper gets `.is-pack` or `.is-collection`, which place themselves with the standalone `translate` / `scale` properties (so they stack with the animations' own `transform`s). The editor (the **Layout** category of `OverlayEditor`) has a Pack opening / Collection switch (each with size, X/Y, Center, Reset), drag-on-the-canvas + arrow-key nudging (one screen pixel = `1/fit` design pixels), browser-source size presets, and shows the real overlay in an iframe (`/overlay.html?preview`), pushing changes by `postMessage` (`layout`, `static`, `pack`, `collection`). While nothing animates the preview shows a **still** of the settled pack opening or of the collection view (`showStatic()` in `widget.js`, wrapper class `.static-preview`) so it can be sized and moved; **Play** runs the real animation and the still comes back when the queue goes idle. The editor re-sends the layout on every iframe `load` (an iframe starts as a blank page that already reads "complete", so a one-off ready flag races); **preview mode never touches the queue, heartbeat or collections** (no polling, no saving, no sound, fake `preview` user) — keep it that way. `sanitizeLayout()` clamps everything, server-side too. The collection grid still wraps at 800px (`.card-wrapper { max-width: 800px }`).

## Overlay properties (Overlay Editor)
Every adjustable aspect of the overlay's look is a **property** in one registry, `lib/overlay-props.ts` (`PROPS`, grouped by `PROP_GROUPS`): a dotted key (`collection.perRow`, `reveal.style`, `variant.shiny.holoSpeed`), a type (`number` / `boolean` / `select` / `color` / `colors` / `text`), default, limits, help text, optional `experimental`. **The defaults reproduce the original look exactly**, so an untouched install is unchanged. The editor UI, validation, reset, presets and import/export are all generated from the registry — to add a property: add one entry there, then consume it in `widget.js` (read it with `pv(P, key, fallback)`); add a `dependsOn()` rule in the editor if another switch turns it off.
- **Storage is sparse**: only values that differ from the default are saved (`sanitizePropValues`, which also drops unknown keys / invalid values). Global values: KV `overlay:settings.props`. **Per-pack overrides**: KV `overlay:packprops` (`{ [packId]: values }`, kept off the Pack object because pack forms rewrite the whole pack) — these use `{ keepDefaults: true }` because an override equal to the default must survive when the global value isn't the default. Named presets: KV `overlay:presets` (max 30; saving an existing name replaces it). All in `lib/overlay-settings.ts`.
- `GET /api/overlay/config` returns `{ layout, defaults, props, packOverrides }`; the widget (`loadLayout()`) merges defaults → global → the pack's override in `effectiveProps(packId)`. The **collection view uses global values only** (it isn't pack-specific; the editor hides that group in pack scope). The config is read once at load, so OBS needs a browser-source refresh after saving (the editor says so).
- **Categories** (`PROP_GROUPS`): **Pack opening** (`reveal.*`: animation, card size, label incl. `labelOwned`, name/stars bar, "got:" line, start delay, pack size, and the row of cards under the revealed card — its own `reveal.strip*` settings), **Variants** (`variant.regular|reverse|full|shiny.*`, each `PropDef` carries `variant`: label, a per-variant **reveal animation override**, holo, glow, pop, 3D tilt, rocking, **light burst** (on/off, strength, size, ray count, spin time, colour, hue cycle), sparkles, time and sound) and **Collection** (`collection.*`, the "show collection" view, global only). The strip and the collection view deliberately do NOT share keys. Group membership is metadata only — stored values are keyed by the dotted key, so regrouping never migrates data (note: `collection.*` card-look values saved before the strip got its own keys no longer affect the strip).
- **Reveal styles** (`REVEALS` in `widget.js`): classic (the original), simple (zoom), slide, flip (card back = the pack cover, `.card-back`, edge-on at 55% of the keyframes), and the experimental **rip-shake** (pack trembles, tear strip flies off, card bursts out) and **rip-peel** (tear strip peels back from one end). Each style names its keyframes plus when (seconds at 1×) the card is revealed / info / label appear; `reveal.speed` divides every duration *and* timeout. Hold time = `label time + 0.8s + pack.cardTime` (classic = the old `cardTime + 4s`). More styles: **rip-slice** (tear strip slides straight off sideways), **rip-explode** (pack swells, flashes white, bursts), and the pack-less **drop**, **spin**, **impact** and **deal**. `variant.X.style` (default `inherit`) overrides the pack opening's style per variant (e.g. Shiny always rips); `reveal.startDelay` adds seconds to every animation delay and timeout (`D` in `drawCard`); `reveal.packScale` uses the standalone `scale` on `.package-container`. The light burst is per variant: `burstSpec()` / `buildRays()` rebuild the rays (`--ray-step`) and size the container (`reveal.showBurst` / `reveal.burstOpacity` no longer exist; unknown keys are dropped on read, so old values vanish harmlessly).
- **Per-version looks are CSS variables** written on each theater wrapper by `applyLook()` (`--label-bg`, `--holo-*`, `--glow-*`, `--pop-*`, `--rock-amt`, `--burst-a/b`), and `mainCardAnimation()` composes the card's `animation` list from the generic keyframes (`variantPop`, `variantGlow`, `variantRock` — rock uses the standalone `rotate` so it layers on the pop). The old per-variant CSS rules are gone. Holo: `--holo-gradient` is built from up to 8 colours cycled into the original 8-slot geometry; loop mode uses `rainbowLoop` (slides exactly one gradient tile so it joins seamlessly). The website / Twitch panel holo is separate and unaffected.
- **Editor (a Photoshop-style workspace)**: the rail has **Layout** (stage size + per-view placement, global so it is hidden in pack scope; the canvas becomes drag-to-position while it is open) plus the registry categories. One **Save** posts only what changed (`saveOverlayEditorAction`, payload `{ layout?, global?, packs? }`). An options bar (scope: Everything / Override for pack X; Presets and Import/Export popovers; Revert/Save), a **canvas** that fits the whole stage into the available space both ways (never scrolls; View: Pack opening / Collection, "Show as" version, Play) and a **docked properties panel** (category rail, search across every setting; **Variants** opens a picker (one card per variant, "Previewing" marked) and then edits that variant under a `← Variants / Shiny` breadcrumb with "copy the look of…", collapsible sections with changed counts, per-property and per-section reset — `inherit` in pack scope). One `version` state drives both which variant is edited and which the preview shows. **Clicking an element in the preview opens its settings**: the widget (preview only) tags the still's elements with `data-edit` (card, label, bar, got, strip, heading, collection), highlights them on hover and `postMessage`s `{ type: 'select', target }`; the editor maps that to a category + section and scrolls it into view (the Layout drag surface covers the iframe, so clicks only reach it outside Layout). The workspace is `xl:h-[calc(100vh-4rem)]` and `main:has([data-workspace])` is `overflow: hidden` there so the page doesn't scroll; below `xl` it stacks. It **auto-collapses the admin sidebar** while mounted without touching the saved choice: it sets `window.__tcgSidebarForce` and fires a `tcg:sidebar` event that `AdminShell` listens for. the preview gets `postMessage` `props` (unsaved effective values + `packId`), `variant`, `static`, `pack`, `collection`.
- **Glow follows the art's silhouette**: a `.glow-layer` behind the card (inside `.main-card`, whose art is now the `.card-art` child) is a blurred copy of the art — blur on the OUTER element, the `--card-mask` thumbnail mask on the INNER `.glow-fill`s, because CSS applies `filter` before `mask` and masking the blurred layer would cut the halo at the edge. Rounded corners and holes in the artwork therefore stay clear; only opacity/transform animate (no per-frame blur). **3D tilt** animates the card box's standalone `rotate` (`variantTiltx|y|xy`, `perspective` on the wrapper via `.tilt-on`), so it doesn't fight the entrance transform or the 2D rock. `mainCardAnimation()` returns `{ anim, start }`; `--fx-start` delays glow/tilt until after the pop. Card-styling vars, collection `sort`, per-version `holdExtra` / `volume` / sparkle burst (`burstSparkles()`) are as before.
- Testing tip: to inspect an animation at an exact moment, start a draw, then `document.getAnimations().forEach(a => { a.pause(); a.currentTime = ms })` and screenshot (set `PACKS[0].pack.cardTime = 120` first so the card stays up). Screenshots lag by a second or two, so don't time them against the live animation.

## Sandbox (test without touching production)
A **sandbox** is a key namespace in the same KV (`sbx:<id>:*`) plus an entry in `sandbox:registry` (production namespace). Enter one at `/admin/sandbox`; while in it, every admin page and website page in that browser reads and writes only that sandbox, and a purple **Sandbox pill** (`SandboxPill`, in `AdminLayout` and `SiteShell`) is always visible.
- **Isolation is one choke point.** `lib/db.ts` wraps the KV client: `currentSandboxId()` resolves the sandbox from (1) a `runInSandbox()` override (AsyncLocalStorage), (2) the `x-tcg-sandbox` request header (the overlay, when its URL has `?sandbox=<id>`), (3) the `tcg_sandbox` cookie (set when an admin enters one), and prefixes every key. **An id that is junk or no longer exists maps to a dead `__missing__` namespace, never to production**; commands that aren't key-first are refused in a sandbox rather than risk an un-prefixed key. Because it reads headers/cookies, anything using KV is dynamic — every page/route that matters is already `force-dynamic`. `scripts/check-sandbox.mts` (needs the mock KV) proves production is byte-identical after sandbox writes, test tools, resets and deletes.
- **The outside world is silenced**: `recordActivity` skips Discord (decided before `after()`, where the request's sandbox isn't visible), `fireOutgoing` doesn't call outgoing webhooks, and `deleteUnusedBlobs` refuses to delete files (the Blob store is shared and a sandbox's data can lag production). Images/sounds are shared; the Twitch Extension panel always talks to production (test on the website instead).
- **Creating one** (`createSandbox`): copy production's setup (seasons, packs, cards, overlay + scoring settings; optionally every viewer's collection) INTO the namespace by reading production and writing prefixed keys, or start empty. Discord / webhook settings and sessions are never copied. **Reset** wipes the namespace (`wipeKeys`, SCAN + a prefix check before every delete) and re-copies; **Clear test data** drops only viewer data; **Delete** wipes and unregisters.
- **Driving it** (`lib/sandbox-tools.ts`): `simulatePulls` (pack by weight → card by odds → variant roll with `effectiveWeights`, exactly like the overlay), `grantCopies` (e.g. exactly enough Regulars for an upgrade), test users, and **Log in as** — a signed `tcg_session` with `sandbox: <id>` that `getSession()` ignores anywhere else, so no Twitch login is needed to test /account, upgrades and (later) trades. Each sandbox action re-checks the admin cookie itself (`requireAdmin`) because server actions can be invoked outside their page. `POST /api/sandbox/exit` (public, harmless) clears the sandbox and session cookies. **Seed a crowd** (`seedUsers`): up to 300 test viewers with realistic pull histories (a long tail of light collectors and a few heavy ones, or an even spread), drawn in memory and written in ONE locked read-modify-write (so 100 users is instant, not thousands of per-pull locks). **Card values** (`listCardValues`) shows every card's pull odds, copies out there per variant and points per variant, so you can see rarity × scarcity × variant at work. **Preview the upgrade animation** plays the viewer-facing ceremony for any card and step without a real upgrade.
- **Fake Twitch (`/admin/sandbox/[id]/twitch`)**: tests the Twitch Extension panel without Twitch. It stands in for a channel page (a pretend stream with the sandbox's overlay) and runs the REAL `panel.html` / `mobile.html` / `video_component.html` in an iframe with `?mock=1`, which makes `public/twitch-panel/mock-twitch-ext.js` (loaded after Twitch's helper; a no-op without `?mock`) replace `window.Twitch.ext` with a pretend helper: `onAuthorized`, `onError`, and `actions.requestIdShare` (a stand-in for Twitch's share-identity prompt, after which it re-authorises like the real helper). Tokens come from `POST /api/admin/sandbox/ext-token` (admin only, needs a sandbox): `signMockTwitchJwt` signs with a key derived from `SESSION_SECRET` (never the extension secret) and names the sandbox, and the Extension routes (`login`, `link`, `unlink`, `upgrade`) verify with `verifyExtensionAuth`, which accepts a fake token ONLY while the request is inside that same sandbox (so it can never touch production). The fake login names the user in the token (no Helix call). The panel's own API calls reach the sandbox through the `tcg_sandbox` cookie because the iframe is same-origin. Viewer choices: not logged in to Twitch (login screen, nothing to share), a test user who must share their identity (the prompt), or the broadcaster (direct login, as on the real channel); views: panel 318×500, mobile 375×667, video component over the stream. `scripts/check-sandbox.mts` covers token scoping. New panel features can be tested here before they ever reach Twitch.
- **Future features**: build them against `kv` from `lib/db.ts` and they are testable in a sandbox for free. Anything that reaches outside (HTTP calls, Blob deletes, emails) must check `inSandbox()` first.

## Only-when-live switches
Settings → OBS Overlay has two checkboxes (KV `overlay:settings`, `lib/overlay-settings.ts`): ignore incoming **pack** triggers and/or **collection** triggers unless the stream is live. `liveGate(kind)` is called by `/api/webhooks/pull` and `/api/webhooks/collection` before enqueueing; blocked triggers are dropped (not queued) and answered `{ ok: true, ignored: true, reason }`. "Not live" = no overlay connected, or a connected overlay reports `streaming === false`. If OBS hasn't granted the browser source status permission, `streaming` is `null` and triggers are allowed (we can't tell). Dashboard quick actions deliberately bypass the gate. It fails open on any error.

## Discord activity feed
Settings live in KV `discord:settings` (edited in Settings → Webhooks). `recordActivity()` forwards every event via `after()` to `notifyDiscord()` in `lib/discord.ts`, which applies the category toggles + pull filters (min rarity, new-only), builds an embed (rarity colour, static card thumbnail, link to the viewer's collection) and POSTs it. Only real discord.com webhook URLs are accepted (the server POSTs to the stored URL); `allowed_mentions` is empty and names are Markdown-escaped because event text comes from unauthenticated endpoints. Browser-safe types live in `lib/discord-config.ts` — client components must import from there, not `lib/discord.ts`. The form's Test / Send-last-activity buttons use the URL currently typed, so it can be verified before saving.

## Git & PR workflow
- Work on a feature branch off an up-to-date `origin/main` (`git fetch && git checkout -b <branch> origin/main`), push it, and open a PR with `gh pr create --base main`. `gh` is installed and authenticated. Don't push to `main` directly and don't merge/close PRs unless the user asks.

If a fix lands on a branch *after* its PR merged, it is not in `main` — open a new branch/PR with it.

## Testing locally
There is **no automated test suite**. Verification is: `npx tsc --noEmit` (run `rm -rf .next` first if you switched branches — stale `.next/types` give false errors), `node --check public/widget.js` (syntax only! it does not catch undefined identifiers — actually load the overlay), `npm run build`, and exercising the app by hand.

**Run the app against a fake database (never develop against production KV):**
1. `node scripts/mock-kv.cjs` — in-memory Upstash REST fake on `:4111`. Data is lost when it stops.
2. Create `.env.local` (gitignored; **delete it when you're done**):
   ```
   KV_REST_API_URL=http://localhost:4111
   KV_REST_API_TOKEN=dev
   KV_URL=redis://dev
   ADMIN_SECRET=testsecret
   ```

   - **Test panel (`?dev`)**: Pack / Card / Variant pickers (blank = random, exactly as a real draw), a count + **Draw**, **All 4 variants** (one card shown Regular → Shiny; random card if none picked), Show Collection, Clear queue, and switches: **Don't save (dry run — on by default)**, Mute, Quick timing (≤1.5s on screen). Reset buttons live in a collapsed Danger zone. Draw options are passed as `queueDraw(username, { packId, cardNumber, variant, dry })`; the `DEV` object in `widget.js` only changes behaviour when set from the panel.

   - **Website login locally**: also run `node scripts/mock-twitch.cjs` (fake Twitch on `:4222`) and add to `.env.local`: `SESSION_SECRET=any-16+-char-string`, `TWITCH_CLIENT_ID=x`, `TWITCH_CLIENT_SECRET=x`, `TWITCH_ID_URL=http://localhost:4222`, `TWITCH_API_URL=http://localhost:4222`, `SITE_URL=http://localhost:3111`. "Log in with Twitch" then approves instantly as `tester`; `curl "http://localhost:4222/__as?login=other"` changes who the next login becomes, and `/__revoked` shows revoked tokens. `curl "http://localhost:4222/__live?on=1"` (or `0`) makes the fake channel live/offline for the live indicator (the result is cached in KV for ~45s, so delete the `twitch:live` key to see a change immediately). The URL overrides are ignored in production builds.

**Things that bite:**
- **Never turn off "Don't save" in the test panel (or call `drawCard` without `dry`) on the production overlay** — a saved draw `POST`s to `/api/collection` and writes a real pull for that username (once left a stray `tester` user in production data). The panel defaults to dry runs and shows a red warning while saving is on; still prefer the mock KV or `?preview`. The panel's Reset buttons always write real data.
- Run server-side TypeScript with `npx tsx script.mts` and **extensionless imports** (`../lib/kv`); plain `node --experimental-strip-types` can't resolve them. Set `KV_REST_API_URL` etc. *before* the dynamic `import()`.
- The Claude app's built-in browser pane is often **hidden**: `requestAnimationFrame` is paused, CSS background images aren't fetched and animations don't advance, so frame rate/smoothness can't be measured there. Instead scrub animations (`document.getAnimations()` → `pause()`/`currentTime`) and measure bounding boxes, or inspect computed styles. ## Local dev
`npm install` then `npx tsc --noEmit` / `npm run build` work locally. `node_modules/` is gitignored.

## Overlay performance
The OBS overlay must stay smooth, so keep these rules when editing `public/widget.js` / `widget.css`:
- **The collection grid uses thumbnails, never the animated WebPs.** `/api/seasons/active` adds `thumbUrl` to every card (`cardThumbUrl()`); the widget maps it to `card.thumb` and `buildMiniList` uses it. `preloadThumbs()` decodes them all on load, and `drawCard` calls `warmImage(card.image)` as soon as a card is picked so the reveal doesn't hitch on decode.
- **Animate only `transform`/`opacity`.** The holographic shimmer slides a pre-painted `::before` layer with `translate3d` instead of animating `background-position` (which repaints every frame). No `filter: blur` on animated layers.
- **Keep images small.** `public/assets/pack-cover.png` is drawn ~287px wide but used 3× per pack theater, so it is stored at 640px wide (~0.4MB). Don't replace it with a full-resolution original.
- `/assets/cards/*` and `/assets/sounds/*` are served with a day of `Cache-Control` (see `next.config.ts`) so OBS refreshes don't re-download the art.
