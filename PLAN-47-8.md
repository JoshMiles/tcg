# PLAN 47.8: profiles tied to the Twitch account ID (plan only, nothing coded)

Decision (Josh, 2026-10-26): a new account signing in with a login an old profile holds (stored ID differs) MOVES THE OLD PROFILE ASIDE; the new account starts fresh under the login. Fixes security M-1 and X-3.

## 1. Where the account ID is recorded, and old profiles

Today `UserProfile.twitchId` (lib/types.ts) is only backfilled when empty, by `ensureUserProfile(login, id)` (lib/kv.ts:227), and never compared. Callers with an ID: website callback (`app/auth/twitch/callback/route.ts:45`) and the panel `POST /api/twitch/login` (`app/api/twitch/login/route.ts:25,39`; the ID comes from the verified extension JWT, the login from Helix). Without an ID: overlay pulls and bot webhooks (`/api/webhooks/pull|grant-card|...`, `/api/collection` tickets), admin tools (`serial-actions.ts`, `users-actions.ts`, `actions/users.ts`), and the admin profile form, which writes free text ("Twitch username") into `twitchId` (`actions/users.ts:30`). So some stored values are not numeric IDs.
- Treat only `isTwitchId` values (`/^\d{1,20}$/`, lib/staff-core.ts) as an ID. Sandbox sessions (`sandbox-<user>`) and non-numeric values count as "no ID" and skip all conflict logic.
- New pure `lib/account-id.ts`: `classifySignIn(profile, id) -> 'new' | 'claim' | 'same' | 'conflict'`. `claim` = profile has no valid ID: first sign-in writes it (also overwriting a non-numeric admin-typed value), as today for empty ones. `same` = nothing to do.
- New hash `acct:ids` (id -> login that owns it, written once per id with `hsetnx`, through the namespaced `kv` so a sandbox has its own). It is the reverse index: it lets sign-in ask "does this ID already own a profile under another name?" without a scan, and it records who the ID belongs to for the reclaim path (section 2). Backfilled lazily on each sign-in; no migration.
- One shared function `bindAccount(login, id)` replaces the bare `ensureUserProfile(login, id)` at both sign-in call sites (website and panel) and returns the classification. Phase 1 only logs/counts it; later phases act on it.
- Overlay and webhook pulls cannot be verified (the bot sends a login only). Accepted limit for the first two phases: until the new owner signs in on the website or panel, a pull under the reused login still credits the old profile. Closing it: accept an OPTIONAL `userId` field in the incoming pull/grant webhooks (additive; Mix It Up and most bots have it) and run the same check. Needs Josh's input (Q3). A nightly Helix sweep (`users?login=` in batches of 100, compare ID with `acct:ids`) is the alternative that needs no bot change.

## 2. What "moved aside" means

Aside key: `<login>~<n>` (`~` can never occur in a Twitch login, which is `[a-z0-9_]{1,25}`), n = 1, 2, ... first free. The renamed account is a full account under that key, so every public page already works for it with no schema change, and nobody can sign in as it (OAuth can only produce a valid login). Display: `~` keys show as "<login> (former)" and are hidden from the leaderboard, search and dex holder lists (extend the hidden sets below), with `/u/<login>~1` still resolving for staff and for the owner.

One primitive `moveAccount(from, to)` in new `lib/account-move.ts` (idempotent, journalled), used three ways: move aside (`x` -> `x~1`), reclaim (`x~1` -> new login `y` when the same person signs in under a new name, only if `y` is empty; else use admin Merge), and optionally rename (profile `x` has ID i, i signs in as `y`: same call; this is the common real case today, where the player gets a second empty profile and strands the first. Q2).

Steps in order, all under a single `acct-move` lock plus the existing 'trades' lock then each collection lock (lock order rule in lib/trades.ts):
0. Journal `acct:move:<from>` = `{ to, id, startedAt, done: [] }` (the resume point). Re-running a half-done move continues from `done`; each step is "copy if target absent, then delete source".
1. `cancelOpenTrades({ username: from }, 'The account moved to a new owner')` (as `deleteViewerAccount` does, lib/account-deletion.ts): refunds escrow to the old owner's collection first, cancels offers they made and offers made to them.
2. `takeUserSnapshot(from, 'Before moving aside')` (lib/user-admin.ts, 14-day restore point; the safety net if anything is wrong).
3. Collections: for every season, `tcg_<collectionName>` blob: re-key `data[from]` to `data[to]` inside `withCollectionLock` (pattern of `mergeUsers`, lib/user-admin.ts). Do NOT go through `saveCollection` retire/mint logic (it would retire and re-mint every print): write the blob directly, then step 4.
4. Copy ledger (docs/serials.md), per collection: `copies:<c>:o:<from>` hash -> `copies:<c>:o:<to>` with each `Copy.owner` rewritten; `copies:<c>:idx` (id -> owner) repointed for those ids. Retired copies in `copies:<c>:ret` keep their owner and `ev[].who/to` strings (history stays as it was; known limit: an old event "x traded to z" now links to the new x. Not rewritten, a scan of every copy is too costly).
5. Trades (one blob each, under the 'trades' lock): rewrite `from`, `to`, `resolvedBy` equal to `from` in `trades:history` (lib/trades.ts), so the new `x` cannot open the old player's private direct offers (`tradeVisibleTo` is by login); `trades:open` has none left after step 1. `trade:cd:<from>` deleted.
6. Per-user keys, moved with `GET -> SET new -> DEL old`: `user:<u>:profile` (lib/kv.ts; `username` field rewritten, `twitchId` kept on the moved one), `user:<u>:settings` (lib/user-settings-store.ts; includes favourites, pinned and watches), `user:<u>:ach`, `user:<u>:scorehist:<seasonId>` per season, `user:<u>:pulllimit`, `user:<u>:buffs`, `user:<u>:discord` (and repoint the back-reference `discord:user:<discordId>` to the new key), `notif:<u>`, `notif:<u>:seen`, `notif:<u>:v`, `push:<u>` (alert devices; the new person must not get the old person's notices), `audit:user:<u>` (list), `user:<u>:snaps` / `user:<u>:snap:<id>` (restore points travel with the owner), `showoff:cd:<u>` deleted, `mixitup:pending:<u>` moved.
7. Membership in shared sets/hashes (field rename or remove): `users:hidden` (list in KV, admin-set) and `users:hidden:self` (set), `watch:idx:<card>` sets (via `syncWatchIndex(from, settings, DEFAULT)` then re-add under `to`, lib/watch-index.ts), `access:testers` (hash in `prodKv`; tester access must not pass to the new owner: move or drop the record), `twitch:avatars` (delete the field so the new person's picture is fetched), `twitch_opaque:*` links pointing at `from` (a scan, `removeOpaqueLinks` in lib/account-deletion.ts; skipped in sandboxes), `pronouns:<login>` cache deleted, `tcg_board_ranks:<seasonId>` and `digest:ranks:<seasonId>` entries for the login dropped, feedback items' `username` rewritten (`feedbackOf`, lib/feedback.ts).
8. Registry: `acct:ids[id] = to`; `acct:aside` hash `<to>` -> `{ id, login: from, movedAt, reason }` (what Data health and the admin user page list); audit lines on both keys (`recordAudit`) and one `recordActivity`. Clear the journal.
9. Staff: `staff:members` / `staff:ids` / `staff:seen` are NOT moved; they are already ID-bound (`resolveRole`). One addition before step 3: if a staff record exists for `from` with no bound ID but the old profile has one, bind it with `hsetnx` on `staff:ids`, so the new owner cannot inherit the role. `SUPER_ADMINS` is by ID already.
10. Then the new account: `saveUserProfile({ username: from, displayName, twitchId: id, createdAt: now })`, `acct:ids[id] = from`. It starts empty.

What the old owner sees: they come back under a new login `y` with ID i. `bindAccount` finds `acct:ids[i]`/`acct:aside` pointing to `x~1`, and (decision Q1) either auto-reclaims `x~1` -> `y` when `y` has no cards/settings, or shows a one-time "We found your earlier collection as x. Restore it?" on /account. If `y` is already in use, the page says to contact staff (admin Merge exists). If they still hold a session cookie for `x` (30 days, signed with the OLD ID), `getSession` callers must not treat it as the new owner's: add one check, `session.twitchId` equals the stored profile ID (the profile is already read by most account routes; do it in a per-request `cache()`d helper, not a new KV read per hit), else clear the cookie. Staff cookies (`tcg_staff`) carry the ID already.

## 3. In-flight things
- Open trades and escrow: cancelled and refunded in step 1 (never moved). Listing-board rows and Discord listing posts become dead links to cancelled trades (the trade page shows the outcome). Trade history rewritten (step 5).
- Notifications and push devices: moved with the old owner (step 6); the new owner starts empty.
- Leaderboard rows: computed from collections and the hidden sets, so `x` disappears on the next cache refresh (20 s per-instance cache); `x~1` is added to the hidden list. Cached rank snapshots dropped (step 7).
- Public URLs: `/u/x` and `/collection/x` now show the new, empty profile (correct). Old share links to the old collection break; `/u/x~1` still works for the owner and staff. Copy pages `/copy/<seasonId>/<copyId>` and `/c/<uid>` are keyed by copy id, so they follow the copy to `x~1`; holder name shows "x (former)". Copy-page history lines keep the name `x` (limit above). Share images are rendered on demand, nothing stored.
- Race: an overlay pull saving into `x` during step 3 is serialised by the collection lock (the ticket claim then writes under `x`, the new empty key). Accepted: one pull may land on the new owner.
- Failure mid-move: journal resumes on the next sign-in of that login or from a Data health "finish moves" button (add to the existing Data health list with `acct:aside`).

## 4. Twitch panel freeze
`/api/twitch/login` keeps its request and response shape: it still returns `{ username }`. The only changes are server-side (call `bindAccount`, move aside before saving the opaque link). Panel routes resolve the viewer through `twitch_opaque:<opaqueId>` -> login; after a move-aside, the old owner's opaque link must be removed (step 7) so their panel asks them to log in again, which creates the link for whatever login Helix now gives them. If any new field is ever useful (e.g. `moved: true`), it is added to the JSON, never replaced or removed. No other `/api/twitch/*` file changes.

- New `scripts/check-account-move.mts` on the mock KV (each check file gets a fresh KV; add to `npm run verify` by name): seed two seasons with serials on, a profile with settings, notices, an open offer and an accepted one; assert classification table (new, claim incl. non-numeric admin value, same, conflict, sandbox skipped); assert move-aside leaves collections + escrow conserved (print counts unchanged, `idx` consistent), the new `x` is empty, `trades:history` rewritten, hidden sets updated, staff record not inherited; kill the move after each step (inject a throw) and rerun to prove it resumes to the same end state; reclaim by ID; session mismatch rejected. Extend `check-staff.mts` for the pre-bind. Run `node scripts/run-checks.mjs account-move staff serials trades`, then `npm run verify`.
- PR 1 (trial, small, safe to ship alone): `lib/account-id.ts` + `bindAccount` at the two sign-in sites; write `acct:ids`; on `conflict` only `console.warn` and increment a counter hash `acct:conflicts` (login, id, seen), and list it on the admin Data health page. No behaviour change for players. Matches ROADMAP 47.8 "record the ID for a month" and X-3. Docs: public-site/accounts.md, data-architecture.md.
